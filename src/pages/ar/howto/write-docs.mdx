## انسخ هذا أولًا

<Copy id="doc-tw" title="كتابة ملف README" code="/technical-writing اكتب ملف README لأداة Node CLI هذه. أخبرني أولًا بنوع التوثيق المناسب لكل قسم، وابدأ الكتابة بعد أن أؤكّد لك." />

غالبًا ما تخلط ملفات README التي يكتبها الذكاء الاصطناعي كل شيء معًا: خطوات التثبيت، والفلسفة، وجدول الخيارات. فيضطر المبتدئون والباحثون عن خيار محدد إلى القفز بين الأقسام.

القاعدة الأولى في `/technical-writing`: <mark><strong>المستند الواحد يؤدّي مهمة واحدة.</strong></mark> فهو يصنّف كل قسم ضمن واحد من أربعة أنواع:

- **دليل تعليمي (Tutorial)**: تتبعه مرة واحدة، وترى نتيجة في كل خطوة.
- **دليل عملي (How-to)**: خطوات لحل مشكلة محددة واحدة.
- **شرح (Explanation)**: لماذا صُمِّم بهذا الشكل، وما المفاضلات فيه.
- **مرجع (Reference)**: الخيارات، ومعاملات الأوامر (flags)، ورموز الأخطاء. حقائق فقط.

إذا احتاج ملف README إلى عدة أنواع، فقسّمه إلى أجزاء يشير بعضها إلى بعض بروابط.

## مثال لأداة Node CLI

أداة CLI تصدّر ملاحظات Markdown دفعة واحدة إلى HTML، وتحتاج إلى ملف README على GitHub:

<Copy id="doc-cli" title="مثال لأداة Node CLI" code={`/technical-writing اكتب ملف README لأداة CLI هذه.
اكتب التثبيت وأول عملية تصدير كدليل تعليمي: أخبر القارئ في كل خطوة بالمخرجات التي يجب أن يراها.
ضع جميع الخيارات في قسم مرجعي منفصل، بناءً على مخرجات --help الفعلية. لا تختلق أي خيارات.
عندما تنتهي، اتبع الدليل التعليمي من البداية في مجلد فارغ، وتأكّد من عمل كل أمر، والصق مخرجات الطرفية.
أخيرًا، شغّل /unslop عليه: بدون شرطات طويلة (—)، وبدون «قوي»، وبدون «بلا جهد».`} />

- **«اتبع الدليل التعليمي في مجلد فارغ»**: السطر الأكثر فائدة. يمكنك الاختلاف حول الأسلوب. لكن لا جدال حول ما إذا كان الأمر يعمل أم لا.
- **«بناءً على مخرجات --help الفعلية»**: التوثيق المرجعي يذكر الحقائق، والحقائق تأتي من الكود.
- **«أخيرًا، شغّل /unslop عليه»**: يزيل طابع الذكاء الاصطناعي، بالإضافة إلى أي كلمات لا تريدها.

## أين تنظر بعد إرسال الطلب

**في البداية: كيف صنّف الأنواع**. إذا وجدت الفلسفة في قسم البداية، فصحّح ذلك فورًا.

**في النهاية: مخرجات الطرفية**. إذا فشلت أي خطوة، فهناك خطوة ناقصة في الدليل التعليمي.

## أزل طابع الذكاء الاصطناعي في النهاية: /unslop

<Copy id="doc-unslop" code="/unslop تعديلات ملف README، بدون شرطات طويلة" />

تستهدف قواعده المدمجة طابع الذكاء الاصطناعي الشائع في الإنجليزية: الإفراط في الشرطات الطويلة (—)، والقوائم الثلاثية المتكلّفة، والخواتيم الفارغة. أضف إلى القواعد أي كلمات تهمّك، مثل: بدون «سلس»، بدون «تمكين».

## الكود الذي سيستدعيه الآخرون: اكتب الدليل التعليمي أولًا

لأي حزمة أو واجهة API سيستخدمها كود آخر، يمكنك كتابة التوثيق قبل الكود:

<Copy id="doc-readme-first" title="اكتب الدليل التعليمي أولًا" code="/poteto-mode اكتب أولًا دليلًا تعليميًا لكيفية استخدام حزمة config الجديدة. ثم استخدم /teach لتشرح لي لماذا تتفوق على الحالية." />

كتابة الدليل التعليمي أولًا تجعله يفكّر مثل المستخدم: ماذا ستكتب أولًا، وماذا سترى. كما يصبح الدليل التعليمي هو الهدف الذي تتحقّق من الكود على أساسه.

## لست متأكّدًا أنك طلبت الشيء الصحيح: /sharpen

<Copy id="doc-sharpen" code="/sharpen اكتب دليلًا تعريفيًا (onboarding) لخدمة الفوترة الجديدة." />

لا يكتب التوثيق. بل يعيد صياغة طلبك ليصبح أدق. مثلًا: ما الذي سيفعله خبير أيضًا، ومن أي مصادر سيبدأ، وما الذي يثبت صحة النتيجة. اقرأ الصياغة الجديدة. إذا بدت صحيحة، أرسلها.

<Callout type="tip" title="وصف طلب PR توثيق أيضًا">
عندما يفتح <Term k="PR" />، يكتب الوصف باستخدام <code>/technical-writing</code> ثم يشغّل <code>/unslop</code> عليه. الوصف ملخّص يُقرأ في دقيقة للمراجعين. وتُحذف الأقسام الفارغة.
</Callout>

## توقفت عند خطوة؟

<Q q="ما زال ملف README يحتوي على خليط من كل شيء.">
ردّ عليه: «قسّمه بأسلوب technical-writing: أبقِ الدليل التعليمي فقط في قسم البداية، وانقل جدول الخيارات إلى قسم المرجع، وخصّص لأفكار التصميم قسم شرح مستقلًا. لا تخلط بينها».
</Q>
<Q q="شغّلت /unslop، وما زال يبدو وكأن الذكاء الاصطناعي كتبه.">
اذكر الكلمات والعبارات التي تزعجك بالضبط، وأضفها بعد الأمر. مثلًا: «/unslop هذا القسم، بدون شرطات طويلة، وبدون ‹سلس› أو ‹تمكين›، وجمل أقل من 20 كلمة». كلما كانت القواعد أدق، كان أداؤه أفضل.
</Q>
<Q q="لم يكتب /sharpen التوثيق.">
يعيد صياغة الطلب فقط. أرسل الطلب بعد إعادة صياغته إلى <code>/poteto-mode</code> أو <code>/technical-writing</code>.
</Q>
<Q q="وصف طلب PR طويل جدًا.">
ردّ عليه: «وصف طلب PR ملخّص يُقرأ في دقيقة واحدة. من جملة إلى ثلاث جمل لكل قسم. ضع البيانات التفصيلية في ملف، وأضف رابطًا إليه».
</Q>
