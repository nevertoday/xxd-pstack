## What this step does

You use <Term k="poteto-mode" /> to do one small, real thing. Pick a requirement from your own project that's **real but not big**, and explain it the way you'd hand work to a coworker.

The author's advice for beginners fits in one sentence: <mark><strong>give it a goal and a way to check, in your own words.</strong></mark> You don't need to name a playbook or list skills.

## An example first

Say you have a command-line tool and want to add a `--json` flag:

<Copy id="first" title="The first task from the official guide" code="/poteto-mode Add a --json flag to this command. The existing text output must not change by a single byte. Verify both outputs." />

Now swap in your own project, for example the settings page of a Chrome extension:

<Copy id="first-ext" title="With your own project" code="/poteto-mode Add an “Export settings” button to the settings page that downloads the current settings as a JSON file. The existing settings and save logic must not change. Verify: the exported file parses as JSON, and its values exactly match what's stored in chrome.storage. Show me the actual contents of both." />

## What goes in a good prompt

Up to five things, one sentence each is enough:

| What to write | Why | Example |
| --- | --- | --- |
| **The goal** | Say what's wrong, or what you want | Add an export button |
| **What counts as done** | It has to be a clear pass or fail | The exported file parses, and the values match storage |
| **What evidence you want** | Something you can check yourself | Actual contents of both / a screenshot / before-and-after numbers |
| **What you already know** | Saves it a round of searching | An error line, steps to reproduce, a link |
| **Real constraints** | Things that change how it works | Reproduce first / don't change code yet / behavior must not change / show me before you do it |

Two things are **better left out**:

- **Exactly how to do it.** Say what you want to achieve, and leave it room to find a better way.
- **Your guess at the cause (at least at first).** Once you say it, it only looks where you pointed. Wait until it has restated the problem in its own words, then add your guess.

<Callout type="no" title="“Make it better” or “spend an hour on it” is not a check">
It can't tell whether that's a pass or a fail, so in the end it just goes by feel. Replace it with a command it can run, or a result you can look at.
</Callout>

## What to watch for once it's sent

**The first reply**: it restates your goal in its own words, what problem you're solving, and what it expects the smallest change to be. It won't wait for your OK before moving on, so if it got it wrong, interrupt right away.

**The <Term k="待办清单" />**: the first few items are the steps of the <Term k="剧本" /> it matched, copied in as is. The example above matches the Feature playbook: read the relevant code with `/how` first, settle the design with `/architect`, then send subagents to write the code and verify it in the real UI, and finally tidy it into small commits and open a <Term k="PR" />. Steps it decides to skip don't disappear. They stay on the list marked `skip: reason`.

**The final reply**: it should come with the evidence you asked for, like the real commands and their output. When it can't verify something, a good reply says "not sure." <strong>A confident reply with no evidence is a red flag.</strong>

## Keep going: shorter is better

Once the conversation already has context, follow-ups can be very short:

<Copy id="short" title="Any of these is enough" code={`/poteto-mode go ahead
continue
keep going until it's done`} />

They can be this short because the playbook remembers the structure. Your words only need to carry the intent.

**When you switch tasks, say "new task."** Otherwise it treats your new question as the next step of the last task:

<Copy id="newtask" code="/poteto-mode new task. Find out why the cache is still there after logging out. Don't change any code yet." />

"Don't change any code yet" pins this task to the read-only Investigation playbook.

<Callout type="tip" title="If you use Cursor">
Choose `/poteto-mode` from the `/` menu and press Option+Enter (Mac) or Alt+Enter (Windows). It becomes a <Term k="Custom Mode" /> that stays on every turn, so you don't have to type it each time. A plain Enter applies to that one message only.
</Callout>

## Don't line up skills in your prompt

"First use /how, then /architect, then /arena..." is the number one pitfall the official guide calls out. The playbook already has the order worked out, and an order you write by hand often scrambles it or drops steps it would have done. Only name a skill when you want to override one of its default choices.

## Stuck?

<Q q="It misunderstood what I meant.">
<p>Just say so: "No, my goal is...". A misunderstanding is cheapest to catch in that first restatement. It costs you one message. For messy requirements (a long discussion, a bug you can't quite describe), you can have it only restate things first: <code>/poteto-mode Read this discussion and restate the root problem in plain words. Don't change any code yet.</code></p>
</Q>
<Q q="It skipped a step I think matters.">
<p>Look at the <code>skip:</code> reason after that item on the list. If you disagree, say: "Don't skip step 2. Reproduce first."</p>
</Q>
<Q q="The reply is too long and too technical to follow.">
<p>Type <code>/bro</code>, and it will say the last reply again in plain words.</p>
</Q>
