## Why this step comes late

This is where all the earlier steps pay off: only an AI you trust, one that can verify its own work, is an AI you can leave alone with hard work. What makes that safe isn't luck. It's three things: **a done condition it can check, an isolated working directory, and a <Term k="决策日志" /> you can review in the morning.**

## Earn trust before you let it loop

A loop you don't trust just turns out unchecked work faster, and the mess snowballs. Before you let it run on its own, all four of these should hold:

1. You've done it once yourself, or watched the AI do it once, and you know what good looks like.
2. It has the tools and signals you'd use yourself: a verification skill, a profiler, logs.
3. Every phase can prove its own results, and can call a stop when they fall short.
4. You've read a few transcripts and turned repeated failures into tools, skills or checks.

<mark>Until all four hold, run it while you're watching.</mark>

## The bedtime contract

A good handoff has a goal, a done condition, permissions and an escape hatch. It doesn't need to be long:

<Copy id="contract" title="Bedtime contract" code={`/poteto-mode I'm going to bed. In a fresh worktree off main, migrate every caller to the new parser.
Done means: no old callers left, every parser fixture passes, and the old API is deleted.
Keep a decision log. You don't need to ask me before committing.
/loop until done. If you've been stuck for hours and truly can't go on, stop and write down why.`} />

Every sentence buys you something:

| This sentence | What it buys |
| --- | --- |
| I'm going to bed | Tells it not to ask you this time, just keep going |
| Done means... | Turns the goal into a check it can run every round |
| A fresh worktree off main | Doesn't collide with anything else you have open |
| You don't need to ask me before committing | Answers ahead of time the permission question it would otherwise stop and wait on |
| `/loop` until done | Makes it recheck the done condition on events or on a timer (built into Cursor and Claude Code, not a pstack skill) |
| If you're stuck, stop and write down why | When it really hits a dead end, stopping to write down the reason beats eight hours of "creatively reinterpreting the goal" |

Because you'll come back to review it, `/poteto-mode` hands this to `/figure-it-out`: it designs the phases of the run first, then hooks up the decision log.

## What it does all night

Every round is the same four things:

1. Check the done condition.
2. Make the smallest change it has a reason for.
3. Verify against the real artifact.
4. Commit if it made progress, discard if it didn't. Either way, write one line in the log.

One change, one check, one log line. A change that didn't help gets thrown away, not left in to slip through. Hitting a plateau means changing direction, not stopping. And the done condition is **never quietly loosened** to declare victory.

To stop it on purpose, tell it "pause", or say you're going offline or restarting the tool. The safe-pause playbook finishes or backs out the current step, commits a work-in-progress checkpoint, and writes a resume note that a new chat can pick up from. Saying "continue" never triggers a pause.

## The next morning: review decisions, don't reread the night

<Copy id="audit" code="/show-me-your-work Walk me through what you did last night" />

Each log line records the time, phase, decision, reason, where the evidence is, and the outcome. It's stored in `decisions.tsv` (or `.audit/<task-name>.tsv` when several tasks share a directory). By default it stays local. Commit it to the repo only when the work matters enough that reviewers need the record to feel confident.

Before handing back its summary, it sends a reviewer from **a different model family** to read the log and the chat, and the reply ends with a "needs attention" section. <strong>Read that section first, then look at the lines it points to.</strong> You're reviewing decisions, not a whole night.

If you just want progress, not a review: type `/ketchup` in the chat running the task. It's read-only. It tells you in plain words what changed since your last message, and lists everything waiting on your call (merge, approve, pick one of several options) with its recommendation, evidence and risks, so you can decide from the reply alone.

## More than one thing overnight

| What you have | Which playbook | In one line |
| --- | --- | --- |
| A queue of unrelated PRs you want all merged by morning | Autopilot-full | One owner per PR, a fresh group of verifiers checks them, **only verified ones get merged** |
| Same, but you want to look before merging | Autopilot-stack | You wake up to a row of verified PRs, and you review and merge them yourself |
| A big project that takes days | Orchestrate | A standing coordinator assigns and checks work, and doesn't write code itself |

<Copy id="autopilot" code="/poteto-mode Autopilot these five changes, but don't merge. I'll merge them myself in the morning." />

<Callout type="no" title={`"Work for 4 hours" isn't a done condition`}>
A duration gives it nothing to check. You'll wake up to four hours of busyness, not a result. Give `/loop` a condition that clearly passes or fails.
</Callout>

## Stuck?

<Q q="I'm not comfortable letting it commit on its own.">
<p>Then leave out "you don't need to ask me before committing", or use Autopilot-stack so it stops once things are verified. After you've read its decision log a few times and know what to expect, give it more room.</p>
</Q>
<Q q="I woke up and it had been going in circles all night.">
<p>Most likely the done condition wasn't firm enough, or the verification tools weren't good enough. Use <code>/reflect</code> to record what you learned this time, and <code>/correct</code> to turn repeated failures into checks. The next run will go much better.</p>
</Q>
