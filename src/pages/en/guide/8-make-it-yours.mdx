## Start small

You don't need many skills on day one. <mark><strong>Prompt normally and watch where it slips. When the same slip happens twice, add a skill or a check.</strong></mark>

## Correct it in one line: say a principle name

pstack has 24 <Term k="原则" text="principles" />, and each has a name. For example, "delete before adding" is called `subtract before you add`. pstack knows these names, so typing one as is works.

- **It calls it a success because it compiles**: "prove it with real results". Reply `apply prove it works. Run the real import flow and show me the records it wrote.`
- **It adds a check after the failure point and calls it fixed**: "find the real cause". Reply `fix root causes. Find where it first goes wrong.`
- **It keeps trying a fix that failed twice**: "question the assumption". Reply `attack the premise. Write down the assumption those fixes share, and test it directly.`
- **It wants a fourth adapter on top of three old ones**: "delete before adding". Reply `subtract before you add. Delete the outdated adapters first, then design what's left.`

It should say which decision the principle changed. See [the 24 principles](/en/wiki/principles/), and more lines in [Pull it back on track in one sentence](/en/howto/steer/).

## That took a detour: /reflect

<Copy id="reflect" code="/reflect That was too slow. Write down what you learned so it doesn't happen again." />

**What you get**: suggestions sorted into "accept", "reject" and "undecided". <strong>It changes skills only after you approve.</strong> Approve only the ones that would change how future work is done.

## The same mistake keeps coming back: /correct

<Copy id="correct" code="/correct The AI keeps bypassing the repository layer and calling the database client directly" />

**What you get**: it reads recent commits and review comments, and groups the mistakes into kinds. It makes one commit per kind, using the firmest fix it can:

<Fig id="g8-guard" />

Type just `/correct` with no argument, and it searches the history on its own.

`/reflect` changes skills. `/correct` changes your repo.

## Build your own mode: /automate-me

<Copy id="automate" code="/automate-me" />

**What you get**: it reads your chats in this project and finds your habits. After checking with you, it writes a `<your-name>-mode` skill and opens a PR for you to review.

When your habits change, run it again: "/automate-me Update my mode skill with everything since the last change."

## Test a skill before you change it

<Copy id="eval" code="/poteto-mode Update the review skill so it catches missing database migrations, and run an eval on the change." />

**What you get**: several AIs do the same task without knowing they're tested, and a judge scores them. Look at each result yourself too.

<Callout type="warn" title="Don't change a skill in the middle of a task">
If a skill does poorly, note it down and fix it later in its own PR. Reviewers can't see a skill change buried in a feature change.
</Callout>
