## The hard part is not breaking the old stuff

Ask an AI to add a feature and it can usually build it. The trouble is elsewhere. It tweaks the old output format a little along the way, changes a default that long-time users rely on, or adds a check somewhere you didn't notice. The new feature works, and the old one quietly changed.

pstack's Feature <Term k="剧本" /> is built for exactly this. It wants two things settled before any code is written: **what the new feature's data looks like**, and **which existing behavior must stay exactly as it is**. <mark>Say the second one in your prompt, and it becomes a check it has to verify.</mark>

## The one-line version

<Copy id="feat-min" title="The shortest version" code="/poteto-mode add a --json flag. text output stays byte-identical. verify both forms." />

This is the example prompt from pstack's own docs. Each of the three sentences does one job:

- "Add a --json flag" is the goal.
- "Stays byte-identical" is what must not change. It can compare the output from before and after the change directly. One byte different means it failed.
- "Verify both forms" stops it from testing only the new JSON and forgetting the old text.

If you installed pstack as a Claude Code plugin, type the command as `/pstack:poteto-mode`. See [Using pstack in Claude Code](/en/howto/claude-code/).

## What it will do

After you send it, the steps of the Feature playbook show up in its <Term k="待办清单" />, roughly:

1. Read the code it's about to change with `/how`, to understand how it works today.
2. Design with `/architect`. It writes down "how callers will use this" first, then decides on types and how to split modules.
3. Write a "how to split the work" checkpoint with four items: which steps must come first, what can run in parallel, whether several workers need to change the same data, and what the smallest safe split is. Items that don't apply aren't deleted. They get `n/a: reason`.
4. Hand the coding to a <Term k="子代理" />, spelling out which files to change, **what structure represents the data**, and what success looks like.
5. Verify in the right place: run the real command for a CLI, click through the running app for a UI. Anything it can't verify gets marked "inconclusive," not passed.
6. Tidy the work into a few small commits and open a <Term k="PR" />.

The "data structure" in step 4 deserves a closer look. The playbook asks it to pick the shape before writing logic. A pile of scattered true/false flags becomes a state machine. A long chain of if/else becomes a table. Assumptions everywhere that "this object should have some field" become a typed model. Pick the right shape, and the code that follows has far fewer branches.

## When the change spans several parts of the code

If the feature touches several files or changes who owns a module, `/poteto-mode` calls `/architect` on its own. By default it starts coding right after the design. If you want to see the design before deciding, say so in your prompt:

<Copy id="feat-arch" title="Stop and show me the design first" code="/architect with checkpoint. Stop after the design and show it to me. Don't start until I agree." />

A design isn't set in stone either. If, halfway through, the same awkward workaround keeps showing up everywhere, or the types only compile with `any` and forced casts, `/architect` treats that as evidence the design was wrong and starts over, instead of piling on patches.

## An example from a real project

Say you maintain a Chrome extension and want to add a setting to the options page: "which group to show by default when the side panel opens." There was no such setting before, and the side panel always showed "All."

<Copy id="feat-ext" title="Chrome extension example" code={`/poteto-mode Add a setting to the options page: which group to show by default when the side panel opens.
Before writing code, tell me how this setting will be stored in chrome.storage.sync.
What must not change: users who never set it still see "All" in the side panel, just like now. All other existing settings read back unchanged.
Verify both cases: a brand-new profile that never set it, and a profile set to the "Work" group.
Show me what's actually in chrome.storage.sync in both cases, plus a screenshot of the side panel when it opens.`} />

A few things in this prompt are worth copying:

- **"Tell me how it will be stored first"**: it has to say the data shape out loud. You can catch problems at this step, like it wanting a new storage key when you'd rather put it inside the existing settings object.
- **"Users who never set it see the same thing"**: an existing user upgrades the extension and touches nothing. That's the case most likely to break, so it gets named on its own.
- **Two profiles**: one check that can clearly pass or fail for each case, old and new.
- **Storage contents and a screenshot**: a UI that looks right isn't enough. You also want the value that was really saved.

<Callout type="tip" title="Let it open your extension itself">
"Click through the running app" means it needs to know how to launch and drive your project. If it keeps saying it can't verify the UI, run <code>/create-verification-skill</code> once to generate a <a href="/en/wiki/verify-skill/">verification skill</a> for your project. See <a href="/en/guide/6-verify-ship/">step 6 of the guide</a>.
</Callout>

## Stuck?

<Q q="It changed the old output format while it was at it.">
Reply: "The original text output must not change. Show me the diff between the output before and after your change. It must be empty." Next time, put what must not change in your very first prompt instead of waiting until it's done.
</Q>
<Q q="It only verified the new feature, not the old behavior.">
"Verify both" has to be in the prompt. If you forgot, add: "apply prove it works. Run the real command for both cases and paste the output." <code>prove it works</code> is the name of a <a href="/en/wiki/principles/">principle</a>. Saying it tells it you want real output, not "it compiles."
</Q>
<Q q="Does a tiny feature really need the whole design process?">
Not necessarily. When the change stays in one file and doesn't cross modules, the steps it doesn't need are marked <code>n/a</code> or <code>skip</code> in the todo list, with a reason. You can see why it skipped them. If you disagree with a reason, say so.
</Q>
<Q q="It added features I didn't ask for.">
Remind it of the scope: "Only build the one setting I asked for. List your other ideas for me, but don't build them." The playbook already asks it to list "open decisions" in its reply. Extra ideas belong there, not in the code.
</Q>
