## First, make sure it's ready for an overnight run

Letting an AI run on its own all night <mark>only works if it can check its own work</mark>. Otherwise the loop just produces unchecked code faster, and the mess keeps piling up.

Before you let go, check these four things:

1. You've done this task yourself once, or watched the AI do it once, and you know what done right looks like.
2. It has the tools and signals you'd use yourself: a <Term k="验证技能" />, a profiler, logs.
3. Every step proves it was done right, and it can stop when something falls short.
4. You've read a few of its transcripts and turned the mistakes that kept coming up into tools, skills, or checks.

Only let it run on its own once all four are true. Until then, run it with the session open and keep an eye on it.

## What to say before bed

A good handoff has a goal, a done condition, permission given in advance, and a way out. It doesn't need to be long:

<Copy id="mig-contract" title="The bedtime handoff" code={`/poteto-mode I'm going to bed. In a fresh worktree off <base>, migrate every caller to the new parser.
Done means: zero old callers, all parser fixtures pass, and the old API is deleted.
Keep a decision log. You don't need to ask me before committing.
/loop until done. If you're truly stuck after a few hours, stop and write up why.`} />

Here is the original wording, as pstack's docs give it:

<Copy id="mig-contract-en" title="The original wording" code={`/poteto-mode im going to bed. migrate every caller to the new parser in a fresh worktree off <base>.
done means zero old callers, all parser fixtures pass, old api deleted.
keep a decision log. don't ask me before committing.
/loop until done. if you're truly stuck after a few hours, stop and write up why.`} />

Each line does one job:

| This line | What it gets you |
| --- | --- |
| "I'm going to bed" | Tells it not to stop and ask you anything in this conversation, just keep going |
| "Done means…" | Turns the goal into a check it can run every round |
| "Fresh worktree" | Keeps it from colliding with your other open work. See [worktree](/en/wiki/worktree/) |
| "You don't need to ask me before committing" | Answers in advance the question it would otherwise stop and wait on |
| `/loop` | The loop command built into Cursor and Claude Code, not a pstack skill. It makes the AI keep coming back to check the done condition |
| The way out | When it truly hits a dead end, stopping to write up why beats eight hours of "creatively reinterpreting the goal" |

If you installed pstack as a Claude Code plugin, write `/pstack:poteto-mode`. See [Using pstack in Claude Code](/en/howto/claude-code/). `/loop` is built into the host, so it has no prefix.

<Callout type="no" title="Time spent isn't a done condition">
"Work on this for 4 hours" gives it nothing it can check. When you wake up, you'll see 4 hours of activity, not a result. Give <code>/loop</code> a condition that can clearly pass or fail.
</Callout>

## An example from a real project

Say your Chrome extension has dozens of files that call `chrome.storage.sync` directly. You've written a new `settings` module and want to move every call over to it, then delete the old `getPref` helper.

<Copy id="mig-ext" title="Chrome extension example" code={`/poteto-mode I'm going to bed. In a fresh worktree off main, move every direct call to chrome.storage.sync over to the new settings module.
Done means:
1. grep -rn "chrome.storage.sync" src/ finds only the one call inside the settings module;
2. npm test passes completely;
3. the getPref function and its tests are deleted;
4. opening the options page with a test profile that had the old version installed shows every setting exactly as before the migration. Send me a screenshot.
Keep the behavior exactly the same. If you find bugs during the migration, note them down. Don't fix them along the way.
Keep a decision log. You don't need to ask me before committing.
/loop until done. If you're truly stuck, stop and write up why.`} />

Each of the four done conditions can clearly pass or fail: the output of one grep, the result of one test run, whether two names still exist, and one screenshot. In the morning, those four are all you need to look at.

"Don't fix bugs along the way" keeps the before and after directly comparable. If it fixes things while migrating, you can't tell which differences are fixes and which are breakage.

## What it does overnight, and how to stop it

Since this work will wait for you to review it, `/poteto-mode` hands it to `/figure-it-out`, which first designs the whole run: what phases it has and how each gets verified. Only then does it write code. After that, every round is the same loop:

1. Check the done condition.
2. Make the smallest change the evidence supports.
3. Verify it on the real output.
4. If it made progress, commit. If not, throw the change away.
5. Write a line in the <Term k="决策日志" />.

Changes that "might help" don't stay. When it hits a plateau, it tries a different approach instead of stopping. The done condition is never quietly loosened to declare success.

To stop it **on purpose**, say because you need to close your laptop or restart your editor, tell it clearly "pause" or "I'm going offline." That runs the Pause safely <Term k="剧本" />: it finishes or backs out of the current step, commits any uncommitted changes as a `wip:` commit, and writes a note on how to resume. Later, start a new conversation, and it picks up from the note through the Session pickup playbook.

Note: phrases like "keep going" or "continue" never trigger a pause.

## What to look at in the morning

When you're back, have it package the whole night's work into something you can review:

<Copy id="mig-audit" title="Morning audit" code="/show-me-your-work tell me what you did last night" />

The decision log is a TSV file, by default `decisions.tsv` in the working directory, and it isn't committed to the repo. Each line has: time, phase, decision, reason, evidence (commit hash, file and line, screenshot path), and outcome.

Before handing back its summary, it sends a <Term k="子代理" /> from a **different model family** to read the log and the transcript. At the end of the reply there's an **Attention** section listing what deserves a closer look: decisions with thin evidence, verification it claimed but that doesn't show up in the records, and choices that look risky in hindsight. **Read Attention first**, then follow it to the log lines it points to. What you're reviewing is the decisions, not the whole night all over again.

If you only want a quick progress check, not an audit, type `/ketchup` in the conversation that's running the work. It only reads, never changes anything. It tells you in plain words what has changed since your last message, then lists what's waiting on your decision, each with its recommendation, evidence, and risk.

## More than one thing in a night

The handoff above is one task with one done condition. If you have a series of independent changes, or a big project that will run for days, there are three playbooks:

| Playbook | Good for | Does it merge? |
| --- | --- | --- |
| Autopilot-stack | A series of changes you want to look over yourself in the morning before merging | No. You wake up to verified PRs, each with its verdict |
| Autopilot-full | A series of independent PRs you want merged by morning | Yes. Each PR merges only after a verifier who didn't write it signs off |
| Orchestrate | A big project spanning days, many PRs, and many subagents | Each PR's owning agent merges it. The coordinator writes no code itself |

If you're unsure, pick Autopilot-stack. You still get a say before anything merges. These three playbooks were designed for Cursor's cloud agents. In other hosts, some steps are skipped, with the reason written down.

## Stuck?

<Q q="I woke up, it says “done,” but I'm not sure.">
Don't trust the summary. Look at the evidence: rerun each check in the done condition yourself, like that grep and that test run. Then read the Attention section in the <code>/show-me-your-work</code> reply.
</Q>
<Q q="It stopped in the middle of the night to ask me a question, and sat waiting all night.">
Your handoff was missing permission given in advance. Next time, include "You don't need to ask me before committing" and "I'm going to bed." The only things that should really need your decision are irreversible actions, or product choices an experiment can't answer.
</Q>
<Q q="It loosened the done condition, then declared it finished.">
The playbook doesn't allow that. Reply: "The done condition stays the same. Run the original four checks one by one and show me." If the condition itself was too vague, like "mostly migrated," that's a problem with the handoff. Next time, write it so it can clearly pass or fail.
</Q>
<Q q="I said “keep going,” and it made a pause commit.">
That shouldn't happen. "Keep going" and "continue" don't trigger Pause safely. It only pauses when you clearly say pause, going offline, or restarting. If it happens, reply: "I didn't ask you to pause. Keep going."
</Q>
