## Copy this first

<Copy id="bug-min" title="The shortest version" code="/poteto-mode After a retry, users get two notifications. Reproduce it first, then fix it, then verify." />

"Reproduce" means making the problem happen again. It does that first. If it can't, it won't change the code.

The order is fixed: <mark><strong>reproduce, find the real cause, fix it, then verify with the same steps.</strong></mark>

## Give it a few more clues

<Copy id="bug-full" title="The full version" code="/poteto-mode Since yesterday's release, CSV export drops the last row. The failing job id is 4812. Reproduce it first, then fix it. It's fixed when the 60,000-row test dataset exports with no rows missing. Show me the row counts before and after the fix." />

Each part does one job:

- **Symptom and when it started**: since the release, export drops the last row.
- **A clue you have**: the job id. It saves a round of searching.
- **What counts as fixed**: all 60,000 rows export.
- **What to show you**: row counts before and after.

<Callout type="warn" title="Hold back your guess">
Say "I think it's the pagination code," and it only looks there. Let it give its own read first. Then add yours.
</Callout>

## A Chrome extension example

Users report: saved items in the side panel sometimes show up twice after a refresh.

<Copy id="bug-ext" title="Chrome extension example" code={`/poteto-mode Users report that the saved list in the side panel sometimes shows duplicate items after a refresh.
I tried it myself, and clicking "Save" twice quickly makes it more likely. Reproduce it first. Don't change any code yet.
It's fixed when clicking Save ten times leaves exactly one item in the list, and exactly one in chrome.storage.
Show me what's actually in storage before and after the fix.`} />

- **"Exactly one in chrome.storage"**: the UI might hide duplicates while the data still has two. Check the stored value.
- **"Clicking Save ten times"**: turns "sometimes" into a check that passes or fails every time.

## Where to look after you send it

**At the start: its restatement.** If it describes a different problem, stop it right away.

**In the middle: the <Term k="待办清单" />.** It lists a few possible causes and rules them out, until it finds the first place things go wrong. The fix belongs there, not in a later check.

**At the end: before and after.** Both use the same repro steps.

## Easy to test? Add /tdd

<Copy id="bug-tdd" code="/poteto-mode Reproduce the duplicate write first. If there's a cheap test path, use /tdd: write a failing test, then fix it, then run it again." />

Keep "if there's a cheap test path." A test propped up by piles of fake data proves less than running the real command.

## Stuck?

<Q q="It says it can't reproduce the bug.">
That's good. It isn't changing things blindly. Be more specific: which page, what data, what you clicked, which version. You can also paste a log or a recording.
</Q>
<Q q="It said “fixed” but showed no evidence.">
Reply: "apply prove it works. Run the repro steps again and show me the real output." <code>prove it works</code> means: show real results that it works. It's the name of a pstack <a href="/en/wiki/principles/">principle</a>. Type it as is, and it knows what you mean.
</Q>
<Q q="It added an if check later on and called it fixed.">
Reply: "fix root causes. This state should never happen. Find where it first goes wrong." <code>fix root causes</code> means fix the real cause. It's also a principle name. A check only counts as a fix if that state is actually valid.
</Q>
