## Why bug fixing gets its own page

The most common way AI fixes a bug: it sees the symptom, adds a check in the first place that looks reasonable, and tells you "fixed." The symptom goes away for now. The root cause is still there, and a few days later it comes back in a different shape.

pstack's bug-fix <Term k="剧本" /> locks the order in place: <mark><strong>reproduce → find the root cause → fix → verify with the same repro steps</strong></mark>. Describe the symptom in your prompt, say "reproduce first," and it handles the rest.

## The one-line version

<Copy id="bug-min" title="The shortest version" code="/poteto-mode After a retry, users get two notifications. Reproduce it first, then fix it, then verify." />

"Reproduce it first" isn't politeness. It's a real constraint: the playbook makes the bug happen before anything else, and if it can't, it won't touch the code.

## Give it everything you know

One line works, but a few more clues save it a lot of time. A good bug prompt has these pieces, one sentence each:

| What to include | Example |
| --- | --- |
| The symptom | The last row goes missing when exporting CSV |
| When it started | Since yesterday's release |
| Clues you have | The failing job id is 4812, and the log has a line `offset out of range` |
| What counts as fixed | The 60,000-row test dataset exports with every row present |
| What evidence you want | Row counts before and after the fix |

Put together:

<Copy id="bug-full" title="The full version" code="/poteto-mode Since yesterday's release, CSV export drops the last row. The failing job id is 4812. Reproduce it first, then fix it. It's fixed when the 60,000-row test dataset exports with no rows missing. Show me the row counts before and after the fix." />

<Callout type="warn" title="Hold back your guess at first">
Resist saying "I think it's something in the pagination code" at the start. Once you say it, it only looks where you pointed. Let it restate the problem and give its own read first, then add your guess.
</Callout>

## What it will do

After you send it, watch its <Term k="待办清单" />. The first items are the steps of the bug-fix playbook:

1. Restate your goal and the problem in its own words (if it misunderstood, you'll see it here).
2. Make the bug happen in a real environment and write down the repro steps.
3. List a few possible causes, read the relevant code with `/how`, and rule them out one by one until only one is left: **the first place things go wrong**.
4. Fix it there (running `/architect` first if the fix crosses modules), instead of patching a check further downstream.
5. Run the repro from step 2 again and show a before-and-after comparison.
6. Tidy up the commits (with "reproduce" ordered before "fix," so the history shows it broken and then working) and open a <Term k="PR" />.

Skipped steps don't vanish. They stay on the list, marked `skip: reason`.

## An example from a real project

Say you maintain a Chrome extension, and users report: "Items I saved in the side panel sometimes show up twice after a refresh."

<Copy id="bug-ext" title="Chrome extension example" code={`/poteto-mode Users report that the saved list in the side panel sometimes shows duplicate items after a refresh.
I tried it myself, and clicking "Save" twice quickly makes it more likely. Reproduce it first. Don't change any code yet.
It's fixed when clicking Save ten times leaves exactly one item in the list, and exactly one in chrome.storage.
Show me what's actually in storage before and after the fix.`} />

Two details are worth copying:

- **"Exactly one in chrome.storage"**: checking the UI isn't enough. The UI might dedupe while the data still has two entries. Make it read the value that's really stored.
- **"Clicking Save ten times"**: this turns a "sometimes" problem into a check that reliably passes or fails.

## When there's a cheap test path, use /tdd

If the bug is easy to capture in a unit test, have it write a failing test first:

<Copy id="bug-tdd" code="/poteto-mode Reproduce the duplicate write first. If there's a cheap test path, use /tdd: write a failing test, then fix it, then run it again." />

The "if there's a cheap test path" part matters. A test forced into existence and held up by a pile of mocks proves less than just running the real command. The playbook lets it say so.

## Stuck?

<Q q="It says it can't reproduce the bug. Now what?">
That's a good sign. It means it isn't changing things blindly. Describe your environment in more detail: which page, what data, what you clicked, which version. You can also paste a log or a screen recording. If it can't reproduce the bug, it shouldn't be fixing it.
</Q>
<Q q="It said “fixed” but showed no evidence.">
Reply: "apply prove it works. Run the repro steps again and show me the real output." `prove it works` is the name of one of pstack's <a href="/en/wiki/principles/">principles</a>. It has read them, so naming it tells it exactly what you want.
</Q>
<Q q="It added an if check downstream and called it fixed.">
Reply: "fix root causes. This state should never happen in the first place. Find where it first goes wrong." Adding a check only counts as a fix when that state is actually valid.
</Q>
