## First thing: agree it only reads

When you take over an unfamiliar project, the worst move is changing things before you understand them. That's true for people, and it's true for AI. If it hasn't worked out how the code flows, it will start editing in the first place that looks reasonable. It fixes the surface and plants a new problem.

So your first prompt should tell it clearly: <mark><strong>don't change any code yet</strong></mark>.

<Copy id="nc-first" title="Your first prompt" code="/poteto-mode Help me understand this project: what it does, how to run it locally, and where the main code lives. Tell me which files you read and what sources you used. Don't change any code yet." />

"Don't change any code yet" sends the task into the Investigation <Term k="剧本" />. This playbook only reads and never opens a <Term k="PR" />. What comes back is a write-up with sources, usually in these parts: overview, key concepts, how it works, where things live, and common traps.

"Tell me what sources you used" makes it write evidence and guesses separately. You can see at a glance which parts it read in the code and which parts it inferred.

If you installed pstack as a Claude Code plugin, type the command as `/pstack:poteto-mode`, and add the `pstack:` prefix to the other commands too. See [Using pstack in Claude Code](/en/howto/claude-code/).

## Four tools for asking about details

Once you have the big picture, ask specific questions directly with these four commands. The Investigation playbook uses the first two on its own as well.

| Command | What it answers | Example |
| --- | --- | --- |
| `/how` | How this code works right now | How are notifications deduplicated? |
| `/why` | Why it was written this way, and whether the reason still holds | Why is the retry limit 5? |
| `/teach` | The two above combined, explained until you really get it | Teach me how this PR changed the retry logic |
| `/recall` | Where you yourself left off | How far did I get on the export feature last week? |

A few tips for using them:

- **`/how`**: just ask the question you actually want answered. For a big question, it first sends out two to four read-only <Term k="子代理" text="subagents" /> to read the code in parallel. For a small one, it reads and explains directly.
- **`/why`** checks the Git history first, then any other sources you've connected, like issues, docs, and chat logs. The report keeps direct evidence and inference apart, and says "it looks like" when evidence is thin. If it finds nothing, it says so. "Nobody wrote down the reason" is an answer too.
- **`/teach`** is for when a summary isn't enough. Add "convince me" to the prompt, and the explanation becomes an argument you can check.
- **`/recall`** only looks through your own chat history in this project, plus shared information like issues and fix records. By default it covers the last 7 days.

## An example from a real project

Say a friend hands you a member site on Cloudflare Workers, with data in D1. Next you need to change how membership expiry works.

Start with the big picture, using the prompt from the first section. Then follow the thread toward the part you'll change:

<Copy id="nc-how" title="First, ask how it works now" code="/how After a user logs in, how does their membership status make its way to the page? Where is the session stored? Where is membership expiry checked?" />

<Copy id="nc-why" title="Then ask why" code="/why Why is the membership expiry check written twice, in two different places? Does that reason still hold?" />

<Copy id="nc-teach" title="Finally, until you really get it" code="/teach I need to change the membership expiry logic. Teach me how this part works, and convince me that changing it in only one place won't kick out users who already paid." />

The order is `/how` then `/why`: first understand how the code runs today, then dig into why it's that way. If you suspect history is what made it such a mess, you can flip it and do `/why` before `/how`.

After those three, ask it to make the change. By then, you and it have the same picture in mind.

## Taking over a half-finished branch

Another kind of takeover: a different AI conversation (or you, last week) got halfway through something on a branch. For this, use the Session pickup playbook:

<Copy id="nc-pickup" title="Pick up where it left off" code="/poteto-mode Take over this branch. Read the decision log, work out what's already done, and continue from there. Don't redo anything that's already done." />

It will:

1. Find the records left behind: chat transcripts, pushed branches, the <Term k="决策日志" />.
2. Reconstruct the scene: which branch and <Term k="worktree" />, what's already committed, what's still on the todo list, and what decisions were made.
3. Compare "what was planned" with "what was done," and say which step to continue from.
4. Hand the remaining work to the right playbook.
5. Check, against the original goal and on the real output, what the previous conversation claimed it finished. The previous conversation saying "it passed" doesn't count as evidence.

<Callout type="tip" title="Don't mix up /recall and Session pickup">
To continue one specific conversation, use Session pickup. To pull back the story of your last few related conversations before starting new work, use <code>/recall</code>. For example: "/recall the work I did on the virtual list yesterday, then read this bug report."
</Callout>

## Stuck?

<Q q="I told it not to change anything, and it changed code anyway.">
If this is a new question in the same conversation, start with "new task": "/poteto-mode new task. Figure out why the cache is still there after logging out. Don't change any code yet." Without "new task," a conversation that's in the middle of a feature can easily treat your question as the next step of that feature.
</Q>
<Q q="/why says it can't find the original reason.">
That's a normal result, not a failure. It will tell you which sources it checked. If you know the answer might be somewhere, like an issue link or an old doc, paste it in.
</Q>
<Q q="The explanation was thorough, but I didn't follow it.">
Type <code>/bro</code>, and it will say its last reply again in plain words, and shorter. You can also tell <code>/teach</code> "start from the basics," and it will go at your pace.
</Q>
<Q q="When it took over the branch, it redid the earlier work from scratch.">
Reply: "The earlier records are trustworthy. Don't start over. Tell me which step you're continuing from." The Session pickup playbook already says not to redo finished work, only to verify its conclusions.
</Q>
