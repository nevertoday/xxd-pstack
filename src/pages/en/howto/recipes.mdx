These prompts are casual on purpose. That's how people really type, and the skills understand what you mean. Swap the parts in angle brackets for your own: paths, commands, what "done" means. Keep skill names and principle names exactly as written, because those are the names the AI recognizes.

If you use the plugin version in Claude Code, add `pstack:` before the command, like `/pstack:poteto-mode`.

## Understand first, then act

**Explain how it works, then dig into the history**

<Copy id="r-how-why" code="Use /how to figure out how this initialization works, then /why to find out why it broke recently." />

Mechanism first, history second. Each skill's report lists the sources it checked, so you know what the answer rests on.

**A long discussion? Have it restate the problem first**

<Copy id="r-restate" code="/poteto-mode read this thread. In your own words, in plain language, restate the root problem. Don't change any code yet." />

If it misunderstood, you'll see it in the restatement, and fixing that costs one message. Hold back your own guess until it's done. If you only want the restatement without a playbook, use `/in-your-own-words`.

**Sharpen the prompt before you send it**

<Copy id="r-sharpen" code="/sharpen write an onboarding doc for the new billing service." />

It points out what an expert would do that you didn't mention, which raw material to start from, and how to check the result outside of you and the AI. Then it hands back a rewritten prompt. It doesn't do the work. Send the rewrite once you're happy with it.

**Pick up context after a few days away**

<Copy id="r-recall" code={`/recall what I did on <topic> last week, then read <issue link>.`} />

The AI in a new conversation doesn't remember the old one. Have it go through your own history first, so you don't have to explain everything again.

**Make it convince you**

<Copy id="r-teach" code={`/teach me why you built it this way instead of <another approach>. What did you trade off?`} />

An argument is easier to check than a summary. You can spot the holes in an argument at a glance.

## Fix bugs, add features, refactor, chase slowness

**Fix a bug**

<Copy id="r-bug" code={`/poteto-mode <symptom>. Reproduce it first, then fix it, then verify.`} />

"Reproduce it first" is a real constraint, and the bug-fix <Term k="剧本" /> follows it. For the full approach, see [Fix a bug](/en/howto/fix-bug/).

**If you have a verification skill, ask for a video as proof**

<Copy id="r-bug-verify" code={`/poteto-mode use /verify-<your-app> to reproduce this. If it reproduces on main, fix it and give me a video as proof.`} />

"If it reproduces on main" lets it stop early when the bug is already gone. The video lets you see the result before you read any code.

**If there's a cheap way to test, write the test first**

<Copy id="r-tdd" code="/poteto-mode reproduce the duplicate write first. If there's a cheap test path, /tdd it: write a failing test, then fix, then run it again." />

"If there's a cheap test path" matters. A test held together with a pile of mocks proves less than just running the real command.

**Add a feature without breaking the old one**

<Copy id="r-feature" code={`/poteto-mode add <new behavior>. <current output> must not change by a single byte. Verify both.`} />

"Must not change by a single byte" is a check that passes or fails. It's much more concrete than "don't break existing features."

**Refactor with zero change in behavior**

<Copy id="r-refactor" code={`/poteto-mode move <this code> into one module with zero behavior change. Record the current output before you start, and prove it hasn't changed when you're done.`} />

Record the "before" first, so there's something to compare against after.

**Chase slowness with numbers**

<Copy id="r-perf" code={`/poteto-mode <some operation> takes <how long> on <some test data>. Capture a performance trace, fix the cause it shows, and show me before and after numbers.`} />

"Faster" only means something when you have a starting number and fixed test data.

## Settle a design, make a plan

**Build a few prototypes, then pick**

<Copy id="r-proto" code="/poteto-mode build a few prototypes of the settings page layout. Put them behind a toggle and send me a screenshot of each." />

You pick from things that run, not from written descriptions. The AI can also run them itself to answer layout and timing questions instead of asking you.

**A bigger design: settle the structure, with a review point**

<Copy id="r-architect" code="/poteto-mode we need to add rate limiting to external webhooks. /architect first, and answer anything uncertain with prototypes. Let me review before you continue." />

"Let me review before you continue" makes it stop and wait for you before it writes the real code.

**A package other people will use: write the tutorial first**

<Copy id="r-tutorial" code="/poteto-mode first write a tutorial showing how I'd use this new config package. Then /teach me why it's better than what we have now." />

Writing the tutorial first forces it to think like the caller. The tutorial also becomes a target it can check itself against.

**Get a second opinion**

<Copy id="r-arena" code="Have /arena give a second opinion on this discussion and our plan." />

Your current design becomes one of several candidates. In the end it tells you whether another model found something better, or confirms what you had.

**Once the design is settled, write the plan**

<Copy id="r-plan" code="/poteto-mode turn this design into a plan. Break it into small, verifiable PRs, each with its own verification steps." />

Don't ask for a plan before the design is settled. The plan is the deliverable. It won't start implementing on the side.

**Migration plan: keep the bugs too**

<Copy id="r-migrate" code={`/poteto-mode plan the migration from <some library> to <new approach>. Break it into small, verifiable PRs. The results must match the old ones exactly, bugs included.`} />

"Bugs included" stops it from fixing things along the way. Otherwise you can't compare old and new results.

## Review, verify, ship

**Pick it apart before you commit**

<Copy id="r-interrogate" code="/interrogate the whole branch, and be picky. Don't change anything yet. Don't report nitpicks unless it's a real bug or a regression." />

"Don't change anything yet" keeps it read-only. "Don't report nitpicks" filters out noise up front. Also glance at the section of the report that lists what it threw out.

**Check many things in parallel**

<Copy id="r-swarm" code="/swarm run each package's check.sh under packages/. One worker per package, then give me one report." />

Each worker handles one piece. At the end you read one summary, not everyone's raw output.

**For cases tests can't reach, use formal verification**

<Copy id="r-formal" code="/create-formal-verification-skill for the retry queue. A message must never be delivered twice." />

It checks this one rule across every case within the given bounds, and it creates a project skill you can rerun after every change. See <Term k="形式化验证" />.

**Check a number before you publish it**

<Copy id="r-bench" code="/benchmark-checklist check this 40% speedup before it goes in the PR description." />

The verdict is always one of: faster, slower, no difference, or can't tell. It comes with how many runs, how much variance, and where the bottleneck is.

**Stop correcting the same mistake by hand**

<Copy id="r-correct" code="/correct the AI keeps adding new config options without registering them in the schema." />

The fix lands in the repo (architecture, types, lint, or tests), so the next AI can't make that mistake even if it tries.

**Open a PR and watch it until it can merge**

<Copy id="r-pr" code={`/poteto-mode open a PR. Small commits, in order, with evidence in the description.`} />

<Copy id="r-babysit" code={`/poteto-mode watch this PR and get it green.`} />

If you only want the status, say "check on pr 123, what's still open?" It keeps pushing until the PR can merge. It won't merge unless you ask.

## Leave and come back

**Before bed**

<Copy id="r-overnight" code={`/poteto-mode I'm going to bed. In a new worktree (branched from <base branch>), <goal>.
Done means: <a check that passes or fails>.
Keep a decision log. No need to ask me before committing.
/loop until done. If you're truly stuck after a few hours, stop and write down why.`} />

"I'm going to bed" stops it from pausing to ask you things. "Done means" gives every round something to check. The last line gives it a clean way out. See [Let it run](/en/guide/7-overnight/).

**Come back and see what it did**

<Copy id="r-smyw" code="/show-me-your-work walk me through what you did last night." />

Read its "needs attention" part first. Every line in the <Term k="决策日志" /> has a reason and evidence.

**Just want to know what changed in this conversation**

<Copy id="r-ketchup" code="/ketchup" />

It tells you in plain language what changed since your last message, and lists everything waiting on your decision: its recommendation, the evidence, the risk. It only reads. It doesn't change anything.

**Just want to ask how, without it starting work**

<Copy id="r-help" code="/poteto-help how do I keep poteto-mode on for every turn?" />

You get an answer, a prompt you can send as-is, and links to the source. Nothing runs unless you send that prompt.

**Can't follow the reply**

<Copy id="r-bro" code="/bro" />

That one word is enough. It says the last reply again in plain words, shorter and without jargon.

**Write down what you learned**

<Copy id="r-reflect" code="/reflect this was too slow. Write down what we learned so it doesn't happen again." />

It only proposes changes. It edits skills only after you approve. Approve only the ones that would change a decision next time.

The one-line ways to pull it back when it drifts have their own page: [Pull it back in one line](/en/howto/steer/).

## Mistakes everyone makes once

- **Ordering skills in the prompt.** "First /how, then /architect, then /arena" scrambles the steps the playbook already lined up. Stating the goal and constraints is enough. Name a skill only when you want to override one default.
- **A vague definition of done.** "Make it better" gives `/loop` a goal it can't check. Give it a command or result that runs and passes or fails.
- **Leading with your guess about the cause.** It will only look where you pointed. Have it restate the problem first, then share your guess.
- **Going with the first design.** Do it once and you're locked into whatever shape the model thought of first. Ask for prototypes, or use `/architect` to pick from evidence.
- **Polishing a plan on paper.** Put a plan with no code through adversarial review and you get risks that will never happen. Answer the questions with prototypes first, then review what you built.
- **Several AIs crammed into one working folder.** They overwrite each other, and afterward nobody can tell who changed what. Use cloud agents, or say "each attempt gets its own worktree."
- **Starting a loop before you trust it.** A loop that can't verify itself just produces unchecked work faster. Get your <Term k="验证技能" /> working first.
- **Believing a number you haven't checked.** A warm cache or a skipped code path can fake a speedup. Run `/benchmark-checklist` before you publish a number.
- **Correcting the same mistake by hand, again and again.** A correction in chat only covers this one time. `/correct` changes the repo, so it won't happen again.
- **Using `/arena` for coverage.** `/arena` does the same task several times and picks the best. `/swarm` splits the work into pieces and does them separately.
- **Accepting every review comment.** Comments from bots and people mix real problems with noise. `/interrogate` keeps only what a rerun can prove, and lists what it dropped and why, so you can overrule it.
- **Treating `auto` as a model name.** `auto` and `inherit-parent` mean "leave the model blank and follow the main conversation." See [Control the cost](/en/howto/cost/).
- **Calling a passing build a success.** Compiling only proves it compiles. Ask for real command output, a real flow, real stored values, and ask for the evidence in the reply.
- **Writing SKILL.md by hand.** Have `/poteto-mode` follow its "write a skill" playbook. It brings validation and review along.

## Stuck?

<Q q="I copied it exactly, but it did something different from what I wanted.">
<mark>Most likely, what "done" means wasn't clear</mark>. Add one check that passes or fails, like "this command returns 0" or "the exported row count matches the old one." Still unsure? Run the prompt through `/sharpen` before you send it.
</Q>
<Q q="Can I write prompts in a language other than English?">
Yes, the model understands what you mean. Just keep skill names (`/how`, `/arena`) and principle names (`prove it works`) in English. Those are the names the AI recognizes.
</Q>
<Q q="I don't know which one to copy for this task.">
Ask `/poteto-help` directly. It will give you a ready-made prompt. You can also read <a href="/en/howto/which-skill/">Not sure which skill to use</a>.
</Q>
