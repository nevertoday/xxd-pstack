## 原因不明：先让它查，别让它修

<Copy id="inv" code="/poteto-mode 查一下为什么后台任务每隔几小时会超时。告诉我已知的事实、你用了哪些数据、你最有把握的几个猜测。先别改代码。" />

「先别改代码」会让它只调查、不动手。最后它给你一份解释，每条都写了出处。

「你用了哪些数据」这半句，会让它把证据和猜测分开写。

查清楚了要修，说「new task」，开一个新任务去修。

## 改之前，先让它讲清楚

<mark>改没看懂的代码，是藏着的 bug 上线的头号原因。</mark>AI 也一样。

pstack 有四个技能专门干这件事：

| 技能 | 回答什么 |
| --- | --- |
| `/how` | 现在怎么工作？ |
| `/why` | 当初为什么这样写？ |
| `/teach` | 讲到我真的懂 |
| `/recall` | 我之前做到哪了？ |

它们都会把自己的理解讲出来。你能检查它理解得对不对。

## 问它现在怎么工作：/how

<Copy id="how" code="/how 通知是怎么去重的？查订阅者的时候有没有 N+1 查询？" />

问你真正想知道的。它会读代码，像老同事带你熟悉模块那样讲：代码怎么跑、关键的数据、容易忽略的地方。

模块很大时，它会先派几个帮手 AI 分头去读。

## 问它当初为什么这样写：/why

<Copy id="why" code="/why 重试上限为什么是 5？这个理由现在还成立吗？" />

它先翻 Git 历史，再查你接入的其他地方，比如 issue、文档、聊天记录。每条结论都带出处，并分开写哪些是证据、哪些是推测。

查不到它也会直说。「当时没人写下原因」也是一个答案。

想两个一起用，就说「先 why 再 how」。

## 讲到你真的懂：/teach

<Copy id="teach" code="/teach 讲讲这个 PR 是怎么改重试的。说服我它修的是真正的原因，不是表面症状。" />

光看摘要不够时用它。它会跑 `/how` 和 `/why`，再写成一篇大白话的讲解。

「说服我」值得常用：你可以对它的讲解提出质疑。也能拿来问 AI 自己的选择：

<Copy id="teach2" code="/teach 讲讲你为什么这么实现、而不是用队列。你放弃了什么，为什么？" />

## 找回你之前做到哪：/recall

<Copy id="recall" code="/recall 帮我回忆上周导出功能那块做到哪了" />

它翻你最近的对话，加上共享的记录（issue、以前的修复），告诉你现在到哪了、下一步做什么。

在老话题上开始新工作时，先让它找回前面的内容，再给新材料：

<Copy id="recall2" code="/recall 我昨天在虚拟列表上的工作，然后读一下这个 bug 报告。" />

## 接手没做完的活

<Copy id="pickup" code="/poteto-mode 接手这个分支。读一下决策日志，弄清楚哪些做完了，从那里接着做。别重做已经完成的部分。" />

它会读之前留下的记录，说出从哪里接着做。别人说「做完了」的部分，它会对照原来的目标再核实一遍。

## 卡住了？

<Q q="/why 说查不到原因。">
<p>正常。它只能查你接入的地方。想让它查 issue、聊天记录、文档，先在你的工具里接上对应的 MCP（比如 GitHub、Linear、Slack、Notion）。没接的话，它至少会翻 Git 历史。</p>
</Q>
<Q q="讲得太专业了。">
<p>说「讲给第一次接触这个项目的人听」，或者讲完打 <code>/bro</code>。</p>
</Q>
