## 这一步讲什么

一个难的设计只试一次，定下来的就是模型第一个想到的样子。最常见的两个设计错误是：**直接用 AI 的第一版设计**，和**反复打磨一份没被代码检验过的计划**。

pstack 的做法是：<mark>用代码做计划</mark>。原型回答悬而未决的问题，README 或教程定下目标，书面计划放在最后。

## 先看一张「要不要设计」的梯子

<u>大部分改动用不着下面这些</u>。按这张表判断：

| 你的情况 | 用什么 |
| --- | --- |
| 改动不大、已经写完，但心里没底 | 只用 `/interrogate` |
| 要跨函数边界，或者要挪动所有权、分层 | `/architect`（它会自己带上 `/arena`） |
| 一个单独的决定，几个独立方案有帮助：命名、格式、算法 | 直接 `/arena` |
| 一堆互不相干的检查，或者要比赛的几个方案 | `/swarm` |
| 一个能「跑一下就知道」的问题：布局、时间、做法 | <u>做原型，别争论</u> |
| 有争议、以后很难改的设计 | `/architect`，交付前再 `/interrogate` |
| 跨好几个 PR 的活 | 设计定下来之后，再写计划 |

`/poteto-mode` 已经在用这张梯子：跨边界的活它自己会叫 `/architect`。你直接点名，主要是想要**比默认更多或更少**的审视时。

## 定形状：/architect、/arena、/swarm、/interrogate

<Copy id="arch" code="/architect 先设计导入流程，别急着写代码。我最在意调用方怎么用。" />

`/architect` 先读相关代码，再让几个方案比一比，每个方案都先写「调用方怎么用」，再写类型、函数签名和模块划分。默认它设计完就直接开始实现；想先看设计，说「with checkpoint，<u>实现之前停下来给我看</u>」。实现中如果到处出现同样的变通写法、或者类型只能靠 `any` 才编得过，它会认定设计错了，推倒重来。

<Copy id="arena" code="/arena 这个缓存键的格式以后很难改，来 5 个方案。" />

`/arena`：几个 AI 各写一份，换一个模型家族的评委打分，挑最好的当底子，再把其他方案的好点子嫁接进来。`/swarm` 是另一回事：把一份大活切成几块，一人一块，最后汇总。区别见 [/arena 和 /swarm 的区别](/wiki/arena-swarm/)。

<Copy id="interro" code="/interrogate 审一下整个分支，挑剔一点。除非是真 bug 或行为倒退，别报小毛病。" />

`/interrogate` 让几个不同模型去「攻击」你的改动，<u>只留下用命令跑出了失败的问题</u>，被丢掉的也会列出来告诉你为什么。它什么都不改。**丢掉的那一栏也要看**，你可以推翻它的判断。

## 拿不准就做原型

<Copy id="proto" code="/poteto-mode 给新的下拉菜单做几个原型。截图或者录屏给我比较。" />

「原型」剧本在一个临时目录里做几个一次性的草稿，放在一个切换器后面，逐个操作、截图或计时。界面、行为、算法都能这么做。原型就是用代码做计划：它让 AI 自己跑一下来回答问题，而不是问你，还可能冒出一个你没想到的方案。

<Callout type="tip" title="给别人用的代码，先写 README">
做一个给其他代码调用的包或接口时，先让它写「使用者会读的那份文档」：`/poteto-mode 先写一篇教程，讲我会怎么用这个新的配置包。然后 /teach 我为什么它比现在的好。` 文档会逼出调用方的视角，也成了它检查自己工作的目标。
</Callout>

## 动手：说你观察到的，让剧本要证据

不同的活，提示词里要写的东西不一样：

| 活 | 提示词要点 | 例子 |
| --- | --- | --- |
| 修 bug | 症状 + 先复现 | 重试之后会写两条记录。先复现，再修，再验证。 |
| 加功能 | 新行为 + 什么不能变 | 加一个 --json 参数，文本输出一个字节都不能变。 |
| 重构 | 行为完全不变 + 先录下现在的输出 | 把解析挪到一个模块里，行为不变。先录下现在的输出，改完证明没变。 |
| 性能 | 一个测量值，不是一个感觉 | 这份数据启动要 1.8 秒。抓一下轨迹，修掉测出来的原因，给我前后对比。 |

剧本会补上你没写的那些步骤：<mark>修之前先复现、实现之前先定数据结构、重构之前先锁住行为、优化之前先测量</mark>。每一类的完整做法见 How-to 里的[修 bug](/howto/fix-bug/)、[加功能](/howto/add-feature/)、[重构](/howto/refactor/)、[查慢](/howto/perf/)。

bug 有便宜的本地测试路径时，两个字就够：

<Copy id="tdd" code="/tdd implement" />

它先写一个因为正确原因而失败的测试，再修，再跑。测试要靠一大堆 mock 才写得出来时，它会直说，改用最接近的真实命令来证明。改 TypeScript 时，记得点名 `/typescript-best-practices`，<u>它不会自己加载</u>。

## 交付前清理

<u>清理不是可有可无的润色</u>。满是解说性注释和防御性代码的改动，在审核的人看来就是没做完，多出来的代码也正是下一个 bug 藏身的地方。

- **文字**：`/unslop` 去掉 AI 味。可以加你自己的规矩：`/unslop 改一下 README 的新内容，不要破折号`。
- **注释**：`/no-comments` 派一个**不是作者**的只读审查员来审注释（作者总会替自己的注释辩护）。只留许可证、公开 API 的文档、解释代码表达不了的链接、外部依赖强加的行为；声称「别动这里」的注释，它会提议改成类型、测试或 lint 来保证。
- **代码**：`/deslop` 不在 pstack 里（在 Cursor 的 cursor-team-kit 插件里）。没有的话，直接说：「删掉解说性的注释、没有依据的防御判断、死掉的兼容代码、和这次无关的改动。」

## 卡住了？

<Q q="它直接用了第一个方案，没给我选。">
<p>说「先别定，做两三个原型并排比较」，或者点名 <code>exhaust the design space</code>（这是一条<a href="/wiki/principles/">原则</a>）。</p>
</Q>
<Q q="我想让它写个计划再动手。">
<p>可以，但放在设计定下来之后：<code>/poteto-mode 把这个设计写成计划。拆成可以单独验证的小 PR，每个都带验证步骤。</code>「多阶段计划」剧本只出计划不实现，还会告诉你该用哪个剧本来执行。</p>
</Q>
