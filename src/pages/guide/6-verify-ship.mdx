## 第一句就写明怎么算做完

<Copy id="done" code="/poteto-mode 给这个命令加 JSON 输出。文本输出要和原来逐字一样，JSON 要能被解析，两种都在示例项目上跑一遍。把证据给我看。" />

回复里应该有真实的命令和输出。跑不了的，它会写「说不准」。

<mark><strong>「能编译」不算证据。</strong></mark> 按改动要证据：

| 改了什么 | 要什么证据 |
| --- | --- |
| 命令行 | 跑一遍真实命令 |
| 界面 | 在运行的应用里走一遍 |
| 解析器、数据迁移 | 回放一份存好的输入 |
| 性能 | 前后两次测量对比 |
| 存储 | 把写进去的值读出来 |

## 让 AI 自己在应用里验证

AI 没法自己操作你的应用时，先跑：

<Copy id="cvs" code="/create-verification-skill" />

**你会得到**：一个 `/verify-<你的应用名>` <Term k="验证技能" />。它主要读你的代码，交给你之前会自己试跑一遍。<u>试跑没通过，就别用它生成的东西。</u>

之后这样要证据：

<Copy id="use-vs" code="/poteto-mode 做批量归档功能。用 /verify-<你的应用名> 验证，给我录屏和截图当证据。" />

把验证技能提交进仓库，用 `/maintain-verification-skill` 定期复查（最好每天）。它会生成什么、怎么检查、作者自己怎么用，看[给项目配一个验证技能](/howto/verify-app/)。

## 开 PR

<Term k="PR" /> 是一组交给别人审核、再合并的改动。

<Copy id="pr" code="/poteto-mode 开 PR。小而有序的提交，证据写进描述里。" />

**你会得到**：它在一个 <Term k="worktree" /> 里整理出几个小提交，最后给你 PR 链接。

## 修到能合并：盯 PR

<Copy id="babysit" code="/poteto-mode 盯一下这个 PR，把它弄绿。" />

**你会得到**：它依次处理冲突、评审意见、CI（每次推送后自动跑的检查）。真问题就修，没道理的就回复理由。

<strong>它停在「可以合并」，不会替你合并。</strong>

## 合并：land the stack

stack 指一串叠在一起的 PR。

<Copy id="ship" code="/poteto-mode land the stack." />

**你会得到**：每个 PR 由一个没写过它的 AI 再验一遍。它从最底下开始，只合并连着通过的几个，并告诉你卡在哪。

<Callout type="tip" title="用 Claude Code 的话">
开 PR 要用 `gh`，先在本机登录 GitHub：`gh auth login`。
</Callout>

## 卡住了？

<Q q="它说「已完成」，但没贴任何证据。">
<p>回它：「apply prove it works. 给我看真实的输出，不是构建日志。」prove it works 意思是「拿真实结果证明能用」，是 pstack 认识的原则名。</p>
</Q>
<Q q="测出了提速，怎么确认是真的？">
<Copy id="bench" code="/benchmark-checklist 这个导出提速写进 PR 之前先核一下" />
<p>它会问 7 个问题。结论只有四种：更快、更慢、没有可测的差别、说不准。</p>
</Q>
<Q q="小改动，但我不放心。">
<p>用 <code>/blast-radius</code>。它会找出「这个改动为什么安全」，再跑代码证明。</p>
</Q>
<Q q="有些情况测试碰不到，比如两次重试撞在一起。">
<p>用<Term k="形式化验证" />：<code>/create-formal-verification-skill 任务租约和重试逻辑。同一个任务绝不能同时跑两次。</code>什么时候值得用、反例怎么读，看<a href="/howto/formal-verify/">测试碰不到的 bug：形式化验证</a>。</p>
</Q>
