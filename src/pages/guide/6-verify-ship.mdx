## 为什么这一步最重要

<mark><strong>「能编译」不是证据。</strong></mark> pstack 的「证明它能用」原则要求 AI 在报告成功之前，对照**真实产物**检查。你的任务是让「真实产物」变得可以检查。

验证是大部分 AI 工作里最慢的一步，因为它通常要等人来做。让 AI 自己能验证，<u>你就不再是瓶颈</u>；跳过它，开再多的 AI 也只是多出更多没检查过的活等你审。

## 第一句话就写明怎么算做完

<Copy id="done" code="/poteto-mode 给这个命令加 JSON 输出。文本输出一个字节都不能变，JSON 要能被解析，两种都在示例项目上跑一遍。把证据给我看。" />

这样它手上有三个能跑的检查，而不是一个要讨好的心情。回复里应该带着<u>确切的命令和输出</u>；有检查跑不了，好的回复会写「说不准」。

按改动选证据：

| 改了什么 | 证据 |
| --- | --- |
| 命令行 | 跑真实的命令 |
| 界面 | 在运行的应用里把改动的流程走一遍；要和参考图像素级一致时，用「视觉一致」剧本对着固定的截图比 |
| 解析器、数据迁移 | 回放一份保存好的输入 |
| 性能 | 前后两份 profile 对比 |
| 存储 | 把写进去的值读出来 |

**要一个你能自己检查的产物**：先失败后通过的测试、前后对比的录屏、轨迹、截图。修复已经合进去的，再让它<u>在 main 上把同一个检查跑一遍</u>。产物比一个听起来合理的解释强，因为你不用重放整个过程就能质疑它。

对一个小改动不放心，用 `/blast-radius`：它找出「这个改动之所以安全」的那一条事实，并用跑代码来证明。

## 生成验证技能：让 AI 自己能验证

上面「界面」那一行藏着一个前提：AI 得有办法用脚本操作你的应用。项目里没有的话：

<Copy id="cvs" code="/create-verification-skill" />

它主要「采访」你的代码：用户会碰到什么、应用怎么在本地启动、用什么来操作（已有的测试工具，否则浏览器、终端或 HTTP）、什么算证据、能不能同时开两个。只有代码回答不了的才问你。交付之前它会自己完整跑一遍：启动、自检、操作一个功能、拿证据、清理，再确认证据在清理之后还在。**这一遍没通过，就别用它的产出。**

有了它，「在应用里验证一下」就成了任何 AI 都能执行的一步：

<Copy id="use-vs" code="/poteto-mode 做批量归档功能。用 /verify-<你的应用名> 验证，给我录屏和截图当证据。" />

把它当成基础设施：提交进仓库，让每个人、每个 AI 都用同样的方式操作应用。应用会变，用 `/maintain-verification-skill` 定期复查（最好每天），它只修验证技能本身，<u>从不改产品代码</u>；发现产品真的坏了，它会报告出来，而不是改文档掩盖。

测试碰不到的情况（两次重试重叠、锁在写的中途过期、状态变化乱序到达），用<Term k="形式化验证" />：`/create-formal-verification-skill 任务租约和重试逻辑。同一个任务绝不能同时跑两次。`

## 测出来的数字，先核对再报告

前后对比的数字是最容易不小心弄错的证据：缓存是热的、一边是调试版、要测的工作根本没在计时范围里跑，都能做出一个漂亮的提速。报告或者据此行动之前：

<Copy id="bench" code="/benchmark-checklist 这个导出提速写进 PR 之前先核一下" />

它会问 7 个问题，每个都要用跑出来的证据回答：是什么在限制这个数字？两边是不是都按生产环境的方式调优了？结果有没有突破物理极限？有没有报错或错误输出？交替跑多次能复现吗（中位数和范围）？对用户真正等待的那条路径有影响吗？要测的工作真的在计时范围里吗？<u>结论只有四种</u>：更快、更慢、没有可测的差别、说不准。

## 开 PR，盯到能合并，再合并

<Copy id="pr" code="/poteto-mode 开 PR。小而有序的提交，证据写进描述里。" />

「开 PR」剧本在 <Term k="worktree" /> 里工作，把改动整理成小而有序的提交，清理代码和文字，最后给你 PR 链接。<u>五个窄的 PR 胜过一个胖的</u>。

<Copy id="babysit" code="/poteto-mode 盯一下这个 PR，把它弄绿。" />

「Babysit」剧本按顺序处理：先冲突，再评审意见，再 CI。所有已知的修复攒成一次推送，CI 只重跑一次。对评论它持怀疑态度：真问题就修，噪音就驳回并在评论下写明理由。<mark><strong>它停在「可以合并」，从不合并</strong></mark>，因为合并是另一个决定。只想问状态：「/poteto-mode 看看 PR 123，还有什么没处理的？」

<Copy id="ship" code="/poteto-mode land the stack." />

「Shipping」剧本合并之前，会为每个 PR 派一个**没写过这段代码**的 AI，在真实环境里验证一遍。然后只从底往上合并连续验证通过的那一串，并告诉你链条断在哪个 PR。一个验证过的 PR 如果压在没验证的上面，它会等着。

<Callout type="tip" title="用 Claude Code 的注意">
开 PR 用的是 `gh` 这类命令行工具，需要你本机已经登录 GitHub（`gh auth login`）。Cursor 独有的 Bugbot 在其他工具里会被跳过；PR 上已有的 Bugbot 评论照样当普通评审处理。
</Callout>

## 卡住了？

<Q q="它说「已完成」，但没贴任何证据。">
<p>回它：「apply prove it works. 给我看真实的输出，不是构建日志。」</p>
</Q>
<Q q="生成验证技能时卡在启动应用这一步。">
<p>让启动过程可重复：准备好种子数据、测试账号，最好有一条命令能每次都以同样方式把开发环境拉起来。作者还建议：AI 老是写一次性的脚本去点应用时，让它做一个小的控制命令行工具给验证技能调用，省 token，每次结果也一样。</p>
</Q>
