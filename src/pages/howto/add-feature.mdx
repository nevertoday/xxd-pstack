## 加功能，难的是「不碰坏旧的」

让 AI 加一个新功能，它多半能做出来。麻烦在别处：它顺手把旧的输出格式改了一点，把一个老用户依赖的默认值换了，或者在你没注意的地方加了个判断。新功能能用，旧功能悄悄变了。

pstack 的「功能」<Term k="剧本" />（Feature）专门管这件事。它要求两样东西在写代码之前就定下来：**新功能的数据长什么样**，以及**哪些现有行为必须保持原样**。<mark>你在提示词里把后一样说出来，它就会把它当成一条要验证的检查</mark>。

## 一句话版本

<Copy id="feat-min" title="最短的写法" code="/poteto-mode 给这个命令加一个 --json 参数。原来的文本输出一个字节都不能变。两种输出都要验证。" />

英文原版是 `add a --json flag. text output stays byte-identical. verify both forms.`。三句话各管一件事：

- 「加一个 --json 参数」是目标。
- 「一个字节都不能变」是不许变的东西。它能拿改之前和改之后的输出直接比，一个字节不同就算失败。
- 「两种输出都要验证」防止它只测新的 JSON，忘了旧的文本。

在 Claude Code 里以插件方式安装的，命令要写成 `/pstack:poteto-mode`，详见[在 Claude Code 里用](/howto/claude-code/)。

## 它会怎么做

发出去以后，<Term k="待办清单" />里会出现「功能」剧本的步骤，大致是：

1. 用 `/how` 读一遍要改的那块代码，先弄清现在怎么工作。
2. 用 `/architect` 做设计。它会先写出「调用方怎么用」，再定类型和模块怎么分。
3. 写一个「怎么分工」的检查点，四项：哪些步骤必须先做，哪些活能并行，有没有几个人同时要改的同一份数据，最小的安全拆法是什么。用不上的项不删，写 `n/a: 理由`。
4. 把写代码的活交给一个<Term k="子代理" />，交代清楚改哪些文件、**数据用什么结构表示**、怎样算成功。
5. 在对应的地方验证：命令行就跑真命令，界面就在运行的应用里点一遍。验证不了的会写「inconclusive」，不会当成通过。
6. 整理成几个小提交，最后开 <Term k="PR" />。

第 4 步里的「数据结构」值得多说一句。剧本要求在写逻辑之前就选好形状：一堆零散的 true/false 开关，换成一个状态机；一长串 if/else，换成一张表；到处假设「这个对象应该有某个字段」，换成一个有类型的模型。形状选对了，后面的代码会少很多分支。

## 改动跨了好几块代码时

如果新功能要动好几个文件、改一个模块归谁管，`/poteto-mode` 会自己调 `/architect`。它默认设计完就直接开写。想先看一眼设计再决定，就在提示词里说：

<Copy id="feat-arch" title="先停下来给我看设计" code="/architect with checkpoint. 设计完先停下来给我看，我同意了再动手。" />

设计也不是定了就不能改。写到一半如果发现同一个绕路的写法到处出现，或者类型只能靠 `any` 和强制转换才编译得过，`/architect` 会把这当成设计错了的证据，推倒重来，而不是继续打补丁。

## 一个真实项目里的例子

假设你维护一个 Chrome 插件，想在选项页加一个设置：「打开侧边栏时默认显示哪个分组」。以前没有这个设置，侧边栏总是显示「全部」。

<Copy id="feat-ext" title="Chrome 插件的例子" code={`/poteto-mode 在选项页加一个设置：打开侧边栏时默认显示哪个分组。
写代码之前，先告诉我这个设置在 chrome.storage.sync 里存成什么样。
不许变的：没设置过的用户，侧边栏还是和现在一样显示「全部」；已有的其他设置读出来不变。
验证两种情况：一个从没设置过的新 profile，一个设置成「工作」分组的 profile。
给我看两种情况下 chrome.storage.sync 里的实际内容，和侧边栏打开时的截图。`} />

这段提示词里有几处可以照着学：

- **「先告诉我存成什么样」**：让它先把数据形状说出来。你在这一步就能发现问题，比如它想新开一个存储键，而你希望放进已有的设置对象里。
- **「没设置过的用户还是一样」**：老用户升级插件后什么都没动，这是最容易被改坏的情况，单独点名。
- **两个 profile**：新旧两种情况各给一个能判断通过还是失败的检查。
- **storage 内容和截图**：界面看着对不够，还要看真正存下来的值。

<Callout type="tip" title="让它能自己点开你的插件">
「在运行的应用里点一遍」需要它会启动和操作你的项目。如果它每次都说没法验证界面，可以先跑一次 <code>/create-verification-skill</code>，生成一个项目专用的<a href="/wiki/verify-skill/">验证技能</a>。详见<a href="/guide/6-verify-ship/">主线第 6 步</a>。
</Callout>

## 卡住了？

<Q q="它把旧的输出格式也顺手改了。">
回它一句：「原来的文本输出不许变。把改之前和改之后的输出 diff 给我看，必须为空。」下次在第一句提示词里就写上不许变的东西，别等它改完再说。
</Q>
<Q q="它只验证了新功能，没验证旧的。">
「两种都要验证」要写进提示词。漏了就补一句：「apply prove it works. 两种情况都跑一遍真命令，把输出贴给我。」<code>prove it works</code> 是一条<a href="/wiki/principles/">原则</a>的名字，说出来它就知道你要真实输出，不是「编译通过」。
</Q>
<Q q="一个很小的功能，它也要走设计那一套吗？">
不一定。改动只在一个文件里、不跨模块时，用不上的步骤会在待办清单里标成 <code>n/a</code> 或 <code>skip</code>，后面写着理由。你看得到它为什么跳过。觉得理由不对，直接说。
</Q>
<Q q="它在提示词之外多加了别的功能。">
提醒它范围：「只做我说的这一个设置，其他想法列出来给我，不要实现。」剧本本来就要求它在回复里列出「还没定的决定」，多出来的想法应该放在那里，而不是直接写进代码。
</Q>
