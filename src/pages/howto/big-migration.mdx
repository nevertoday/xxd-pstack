## 先确认它配得上过夜

让 AI 整晚自己跑，<mark>前提是它能自己检查自己的活</mark>。否则循环只会更快地产出没人检查过的代码，而且越堆越乱。

放手之前，对照这四条：

1. 这个任务你亲手做过一次，或者看着 AI 做过一次，知道做好了是什么样。
2. 你自己会用的工具和信号它都有：<Term k="验证技能" />、profiler、日志。
3. 每一步都会证明自己做对了，做得不达标时能停下来。
4. 你读过几次它的对话记录，把反复出现的错误变成了工具、技能或检查。

四条都满足再让它自己跑。还没满足，就开着它跑，你在旁边看。

## 睡前那段话

一份好的交代包括：目标、完成条件、提前给的许可、和一个退路。不用很长：

<Copy id="mig-contract" title="睡前交代" code={`/poteto-mode 我去睡了。在一个从 <base> 拉出来的新 worktree 里，把所有调用方迁到新的解析器。
完成的标准：旧调用方为零，所有解析器测试用例通过，旧接口删掉。
记决策日志。提交之前不用问我。
/loop until done。如果几个小时后真的卡死了，就停下来，把原因写清楚。`} />

英文原版是：

<Copy id="mig-contract-en" title="英文原版" code={`/poteto-mode im going to bed. migrate every caller to the new parser in a fresh worktree off <base>.
done means zero old callers, all parser fixtures pass, old api deleted.
keep a decision log. don't ask me before committing.
/loop until done. if you're truly stuck after a few hours, stop and write up why.`} />

每一行各管一件事：

| 这一行 | 换来什么 |
| --- | --- |
| 「我去睡了」 | 告诉它这次对话里别再停下来问你，一直做下去 |
| 「完成的标准……」 | 把目标变成每一轮都能跑的检查 |
| 「新 worktree」 | 和你开着的其他工作互不干扰，见 [worktree](/wiki/worktree/) |
| 「提交之前不用问我」 | 提前回答了它本来会停下来等你的那个问题 |
| `/loop` | Cursor 和 Claude Code 自带的循环命令，不是 pstack 的技能。它让 AI 反复回来检查完成条件 |
| 退路 | 真走进死胡同时，停下来写清原因，好过花八个小时「创造性地重新理解目标」 |

在 Claude Code 里以插件方式安装的，要写成 `/pstack:poteto-mode`，详见[在 Claude Code 里用](/howto/claude-code/)。`/loop` 是宿主自带的，不加前缀。

<Callout type="no" title="时长不是完成条件">
「在这上面干 4 个小时」给不了它任何能检查的东西，你醒来只会看到 4 个小时的忙碌，而不是一个结果。给 <code>/loop</code> 一个能判定通过或失败的条件。
</Callout>

## 一个真实项目里的例子

假设你的 Chrome 插件里，几十个文件直接调用 `chrome.storage.sync`。你写好了一个新的 `settings` 模块，想把所有调用都迁过去，旧的 `getPref` 辅助函数删掉。

<Copy id="mig-ext" title="Chrome 插件的例子" code={`/poteto-mode 我去睡了。在一个从 main 拉出来的新 worktree 里，把所有直接调用 chrome.storage.sync 的地方迁到新的 settings 模块。
完成的标准：
1. grep -rn "chrome.storage.sync" src/ 只剩 settings 模块里的那一处；
2. npm test 全部通过；
3. getPref 函数和它的测试已经删掉；
4. 用一个装过旧版本的测试 profile 打开选项页，所有设置读出来和迁移前一样，截图给我。
行为保持完全一致，迁移途中发现的 bug 记下来，不要顺手修。
记决策日志。提交之前不用问我。
/loop until done。如果真的卡死了，就停下来写清楚原因。`} />

四条完成标准，每一条都能判定通过或失败：一条 grep 的输出、一次测试的结果、两个名字还在不在、一张截图。早上你只要看这四样。

「发现的 bug 不要顺手修」是为了让迁移前后能直接对比。边迁边修，你就分不清哪个差异是修好的，哪个是改坏的。

## 夜里它在干什么，想停怎么办

因为这份活要等你回来再审，`/poteto-mode` 会把它交给 `/figure-it-out`，先设计好整个运行分几个阶段、怎么验证，再写代码。之后每一轮都是同一个循环：

1. 检查完成条件。
2. 做证据支持的最小一步改动。
3. 拿真实产物验证。
4. 有进展就提交，没进展就丢掉这次改动。
5. 在<Term k="决策日志" />里记一行。

「可能有帮助」的改动不留。卡在平台期就换思路，不停下。完成条件永远不会被悄悄放宽来宣布成功。

想**主动**停下来，比如要合上电脑或者重启编辑器，就明确告诉它「暂停」或「我要下线了」。这会走 Pause safely <Term k="剧本" />：做完或退回当前这一步，把没提交的改动提交成一个 `wip:` 提交，再写一份续做笔记。之后开一个新对话，它会通过 Session pickup 剧本从笔记接着做。

注意，「keep going」「继续」这类话永远不会触发暂停。

## 早上起来怎么看

回来以后，让它把一整晚的工作整理成可以审的样子：

<Copy id="mig-audit" title="早上审计" code="/show-me-your-work 告诉我你昨晚做了什么" />

决策日志是一个 TSV 文件，默认放在工作目录的 `decisions.tsv`，不提交进仓库。每一行是：时间、阶段、决定、理由、证据（提交号、文件行号、截图路径）、结果。

交回总结之前，它会派一个**不同模型家族**的<Term k="子代理" />读一遍日志和对话记录，回复最后有一节 **Attention**，列出值得你仔细看的地方：证据薄弱的决定、声称做了但记录里看不到的验证、事后看有风险的选择。**先读 Attention**，再顺着它指的那几行日志去查。你要审的是决定，不是把整晚重读一遍。

只想快速知道进度，不需要审计的话，在跑活的那个对话里打 `/ketchup`。它只读不改，用大白话告诉你从你上一条消息以来变了什么，再列出等你拍板的事，每件都带它的建议、证据和风险。

## 一晚上不止一件事

上面那段交代是一个任务、一个完成条件。如果你手上是一串互相独立的改动，或者一个要跑好几天的大项目，有三个剧本：

| 剧本 | 适合 | 会不会合并 |
| --- | --- | --- |
| Autopilot-stack | 一串改动，你想早上自己看过再合 | 不合并。你醒来看到的是验证过的 PR 和各自的结论 |
| Autopilot-full | 一串互相独立的 PR，希望早上都合好 | 合并。每个 PR 只在没写过它的验证者确认后才合 |
| Orchestrate | 好几天、很多 PR、很多子代理的大项目 | 由每个 PR 的负责代理合并，协调者自己不写代码 |

拿不准就选 Autopilot-stack，合并前还有你这一关。这三个剧本是按 Cursor 的云端代理设计的，在其他宿主里有些步骤会跳过并写明原因。

## 卡住了？

<Q q="早上醒来，它说「做完了」，但我不确定。">
别信总结，看证据：把完成条件里的每条检查自己再跑一遍，比如那条 grep 和那次测试。再读 <code>/show-me-your-work</code> 回复里的 Attention 部分。
</Q>
<Q q="它半夜停下来问我问题，白白等了一晚。">
交代里缺了提前给的许可。下次写上「提交之前不用问我」和「我去睡了」。真正需要你决定的只应该是不可撤回的操作，或者没法用实验回答的产品选择。
</Q>
<Q q="它把完成条件改宽松了，然后宣布完成。">
剧本不允许这样。回它：「完成条件不变，原来的四条逐条跑给我看。」如果条件本身写得太模糊，比如「迁移得差不多」，那是交代的问题，下次换成能判定通过或失败的写法。
</Q>
<Q q="我说了「继续」，它却做了个暂停提交。">
不应该发生。「继续」「keep going」不会触发 Pause safely。只有你明确说暂停、要下线或要重启时它才暂停。遇到了，回它一句「我没让你暂停，接着做」。
</Q>
