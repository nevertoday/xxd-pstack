## 为什么要专门讲修 bug

AI 修 bug 最常见的毛病：看到症状，在第一个看起来合理的地方加一个判断，告诉你「已修复」。症状暂时没了，根因还在，过两天换个样子又冒出来。

pstack 的「修 bug」<Term k="剧本" />把这个顺序钉死了：<mark><strong>先复现 → 找根因 → 修 → 用同一个复现步骤验证</strong></mark>。你只要在提示词里说出症状和「先复现」，剩下的它会照做。

## 一句话版本

<Copy id="bug-min" title="最短的写法" code="/poteto-mode 重试之后用户会收到两条通知。先复现，再修，再验证。" />

「先复现」不是客气话，是一条真约束：剧本会先把问题跑出来，跑不出来就不会去改代码。

## 把你知道的都给它

一句话能跑，但给多一点线索能省它很多时间。好的 bug 提示词里有这几样，每样一句话就够：

| 写什么 | 例子 |
| --- | --- |
| 症状 | 导出 CSV 时最后一行丢了 |
| 从什么时候开始 | 从昨天发版之后 |
| 你手上的线索 | 失败的任务 id 是 4812，日志里有一行 `offset out of range` |
| 怎么算修好 | 那份 6 万行的测试数据，导出后行数一行不少 |
| 想看什么证据 | 修之前和修之后的行数 |

合起来就是：

<Copy id="bug-full" title="完整的写法" code="/poteto-mode 从昨天发版之后，导出 CSV 会丢最后一行。失败的任务 id 是 4812。先复现，再修。修好的标准是那份 6 万行的测试数据导出后一行不少。把修之前和修之后的行数给我看。" />

<Callout type="warn" title="先别说你猜的原因">
「我觉得是分页那里的问题」这种话，一开始先忍住。你一说，它就只在你指的地方找。等它自己复述完问题、给出判断，你再补你的猜测。
</Callout>

## 它会怎么做

发出去以后，看它的<Term k="待办清单" />。前几项就是「修 bug」剧本的步骤：

1. 用自己的话复述你的目标和问题（理解错了，这里就能看出来）。
2. 在真实环境里把 bug 跑出来，记下复现步骤。
3. 列出几个可能的原因，用 `/how` 读相关代码，一个个排除，直到只剩一个：**第一个出错的地方**。
4. 在那里修（要跨模块就先 `/architect`），而不是在下游补一个判断。
5. 再跑一遍第 2 步的复现，拿出修前修后的对比。
6. 整理提交（让「复现」排在「修复」前面，历史里能看出先坏后好），开 <Term k="PR" />。

跳过的步骤不会消失，会留在清单里，后面写着 `skip: 理由`。

## 一个真实项目里的例子

假设你在维护一个 Chrome 插件，用户反馈「侧边栏里收藏的条目，有时候刷新一下就重复了」。

<Copy id="bug-ext" title="Chrome 插件的例子" code={`/poteto-mode 用户反馈：侧边栏收藏列表刷新后偶尔会出现重复条目。
我自己试过，连点两次「收藏」比较容易出现。先复现，不要先改代码。
修好的标准：连点十次收藏，列表里只有一条，chrome.storage 里也只有一条。
给我看修之前和修之后 storage 里的实际内容。`} />

这里有两个细节值得学：

- **「storage 里也只有一条」**：只看界面不够，界面可能做了去重、数据里还是两条。让它读真实存下来的值。
- **「连点十次」**：把一个「偶尔」的问题变成一个能稳定判断通过还是失败的检查。

## 有便宜的测试路径时，用 /tdd

如果这个 bug 很容易写成一个单元测试，可以让它先写一个会失败的测试：

<Copy id="bug-tdd" code="/poteto-mode 先复现重复写入。如果有便宜的测试路径，就 /tdd：先写一个会失败的测试，再修，再跑一遍。" />

「如果有便宜的测试路径」这半句很重要：硬写一个靠一堆 mock 撑起来的测试，证明力还不如直接跑真实命令。剧本允许它这么说。

## 卡住了？

<Q q="它说复现不出来，怎么办？">
这是好事，说明它没有瞎改。把你复现时的环境说得更具体：哪个页面、什么数据、点了什么、用的什么版本。也可以直接贴一段日志或者录屏。复现不出来，它就不该修。
</Q>
<Q q="它修完说「已修复」，但没给证据。">
回它一句：「apply prove it works. 跑一遍复现步骤，把真实输出给我看。」`prove it works` 是 pstack 的一条<a href="/wiki/principles/">原则</a>名，它读过，说出名字它就知道你要什么。
</Q>
<Q q="它在下游加了一个 if 判断就说修好了。">
回它：「fix root causes. 这个状态本来就不应该出现，找到它第一次出错的地方。」只有当那个状态本来就是合法的，加判断才算修。
</Q>
