## 第一件事：说好只看不改

接手一个陌生项目，最怕的是还没看懂就开始改。人是这样，AI 也是。它没弄清代码怎么走，就会在第一个看起来合理的地方动手，修了表面，埋了新坑。

所以第一句提示词，要明确告诉它<mark><strong>先别改代码</strong></mark>：

<Copy id="nc-first" title="第一句" code="/poteto-mode 带我看懂这个项目：它是做什么的、怎么在本地跑起来、主要的代码在哪。告诉我你看了哪些文件、用了哪些资料。先不要改任何代码。" />

「先不要改任何代码」（英文原版是 `don't change any code yet`）会把任务送进「调查」<Term k="剧本" />（Investigation）。这个剧本只读，不开 <Term k="PR" />，交回来的是一份带出处的说明，通常分这几块：概览、关键概念、怎么工作、东西放在哪、容易踩的坑。

「告诉我用了哪些资料」这半句是让它把证据和猜测分开写。哪些是读代码看到的，哪些是推出来的，你一眼就能分清。

在 Claude Code 里以插件方式安装的，命令要写成 `/pstack:poteto-mode`，其他命令同样加 `pstack:` 前缀，详见[在 Claude Code 里用](/howto/claude-code/)。

## 四个问细节的工具

摸清全局以后，具体的问题用这四个命令直接问。调查剧本里也会自动用到前两个。

| 命令 | 回答什么 | 例子 |
| --- | --- | --- |
| `/how` | 这段代码现在是怎么工作的 | 通知是怎么去重的？ |
| `/why` | 当初为什么写成这样，理由现在还成立吗 | 重试上限为什么是 5？ |
| `/teach` | 把上面两个合起来，讲到你真懂为止 | 教我这个 PR 怎么改了重试逻辑 |
| `/recall` | 你自己之前做到哪了 | 上周导出功能做到哪了？ |

几个使用上的细节：

- **`/how`** 问你真正想问的问题就行。问题大，它会先派两到四个只读的<Term k="子代理" />分头读代码；问题小，它直接读直接讲。
- **`/why`** 先查 Git 历史，再查你接入的其他来源，比如 issue、文档、聊天记录。报告会把直接证据和推断分开，证据不足时会说「看起来是」。查不到也会如实说，「没人写下原因」本身就是一个答案。
- **`/teach`** 适合「看懂一个摘要不够」的时候。在提示词里加一句「说服我」，讲解就变成了一个你能检验的论证。
- **`/recall`** 只翻你自己在这个项目里的聊天记录，再加上 issue、修复记录这些公共信息，默认看最近 7 天。

## 一个真实项目里的例子

假设朋友把一个 Cloudflare Workers 会员站交给你，数据在 D1 里。你接下来要改会员到期的逻辑。

先摸全局，用第一节那句。然后顺着要改的地方问下去：

<Copy id="nc-how" title="先问现在怎么工作" code="/how 用户登录以后，会员身份是怎么一路传到页面上的？session 存在哪？会员到期是在哪里判断的？" />

<Copy id="nc-why" title="再问为什么" code="/why 为什么会员到期判断在两个地方各写了一遍？这个理由现在还成立吗？" />

<Copy id="nc-teach" title="最后讲到你真懂" code="/teach 我要改会员到期的逻辑。教我这一块是怎么工作的，说服我只改一个地方不会让已经付费的用户被踢出去。" />

顺序是先 `/how` 再 `/why`：先看懂代码现在怎么走，再追它为什么这样。如果你怀疑是历史原因造成了现在这团乱，也可以反过来，先 `/why` 再 `/how`。

问完这三个，你再让它动手改，这时它和你脑子里都有同一张图。

## 接手一个做了一半的分支

另一种接手：别的 AI 对话（或者上周的你）在一个分支上做到一半。这时用「接续会话」剧本（Session pickup）：

<Copy id="nc-pickup" title="接着做" code="/poteto-mode 接手这个分支。读决策日志，弄清哪些已经做完，从那里接着做。已经做完的不要重做。" />

它会：

1. 找到之前留下的记录：对话记录、推送过的分支、<Term k="决策日志" />。
2. 还原现场：在哪个分支和 <Term k="worktree" />，哪些已经提交，还有哪些待办，做过哪些决定。
3. 对比「计划做的」和「已经做的」，说出从哪一步接着做。
4. 把剩下的活交给对应的剧本继续。
5. 对照最初的目标，在真实产物上核实前一个对话声称做完的事。前一个对话自己说「通过了」，不算证据。

<Callout type="tip" title="/recall 和 Session pickup 别搞混">
想接着做某一个具体的对话，用 Session pickup。想在开始新活之前，把最近几次相关对话的来龙去脉找回来，用 <code>/recall</code>。比如：「/recall 我昨天做虚拟列表的那些工作，然后读一下这个 bug 报告。」
</Callout>

## 卡住了？

<Q q="说了先别改，它还是改了代码。">
如果这是同一个对话里的新问题，开头加「new task」：「/poteto-mode new task. 弄清楚为什么退出登录后缓存还在。先不要改任何代码。」不说 new task，正在做功能的对话容易把你的问题当成功能的下一步。
</Q>
<Q q="/why 说查不到当初的原因。">
这是正常结果，不是失败。它会告诉你查了哪些来源。如果你知道答案可能在某个地方，比如一个 issue 链接或者一份旧文档，直接贴给它。
</Q>
<Q q="讲得很全，但我没看懂。">
打 <code>/bro</code>，它会把上一条回复用大白话重说一遍，更短。也可以跟 <code>/teach</code> 说「从更基础的讲起」，它会顺着你的节奏往下讲。
</Q>
<Q q="接手分支时，它把前面做过的又从头做了一遍。">
回它：「之前的记录是可信的，不要从头重来。说出从哪一步接着做。」Session pickup 剧本本来就要求不重做已经完成的工作，只核实结论。
</Q>
