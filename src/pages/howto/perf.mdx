## 先有数字，再说慢

「感觉有点卡」是印象，「在这份数据上启动要 1.8 秒」是测量。<mark>性能问题只认后一种。</mark>

没有数字的时候，AI 很容易读一遍代码，猜一个「这里可能慢」的地方，改完告诉你「优化好了」。改了什么、快了多少，谁也说不清。pstack 的「性能」<Term k="剧本" />（Perf issue）要求每一处修改都对应一次测量，不许拿读代码代替测量。

## 一句话版本

<Copy id="perf-min" title="最短的写法" code="/poteto-mode 在这份测试数据上，启动要 1.8 秒。trace 一下，修掉测量出来的原因，给我看前后对比。" />

英文原版是 `startup takes 1.8s on this fixture. trace it, fix the measured cause, show me before and after.`。注意「测量出来的原因」：它要修的是 trace 里看到的那个，不是它猜的那个。

在 Claude Code 里以插件方式安装的，命令要写成 `/pstack:poteto-mode`，详见[在 Claude Code 里用](/howto/claude-code/)。

## 它会怎么做

1. 先录一份基线 trace，并用 `/benchmark-checklist` 检查这个基线可不可信。
2. 用 `/how` 读相关代码，提出假设。然后按从便宜到贵的顺序试这几招，前面某一招已经达标就停：
   - 不做：结果没人用的活，直接不做。
   - 做了就别再做第二遍。
   - 少做一点。
   - 晚点做。
   - 趁用户没在等的时候做。
   - 并行做。
   - 换个更省的做法。
3. 根据 trace 定修法，交给<Term k="子代理" />去写，它自己审 diff，再录一份修完的 trace。
4. 把前后两份数据解析出来对比。测不出结论、或者测错了地方，都会标出来，不算通过。
5. 在 <Term k="PR" /> 里写上测量结果。

最后的回复是四样：基线数字、修完的数字、差多少、数据文件放在哪。

## 另外两种情况：只诊断，或一直往下压

### 只想知道慢在哪，先别修

有时候你只想要诊断。pstack 有两个只诊断不修的剧本：

| 你手上有什么 | 用哪个剧本 | 它做什么 |
| --- | --- | --- |
| 一份已经录好的 profile（cpuprofile、trace、heap snapshot） | Trace forensics | 读这份文件，不重跑。找出最耗时的调用，对应到源码的文件和行 |
| 一个正在发生的现象（内存涨、空闲时 CPU 也在转、界面闪） | Runtime forensics | 对运行中的程序录数据，再用一个小实验证明自己找到的机制是对的 |

<Copy id="perf-trace" title="只要诊断" code="/poteto-mode 这是启动慢的时候录的 cpuprofile。告诉我时间花在哪、是哪几行代码。先别修。" />

两个剧本都只交回一份带出处的诊断。原因找到以后，你再决定是走修 bug 还是走性能剧本。

### 想把一个数字一直往下压：Hillclimb

一次性的修复用上面的剧本。如果你想持续优化同一个指标，比如打包体积、首屏时间，用 Hillclimb 剧本。你要给它三样：**指标**、**目标**、**至少试几轮**。

<Copy id="perf-hill" title="Hillclimb" code="/poteto-mode hillclimb 侧边栏首次打开时间。目标：比基线快至少 50%，并且至少试 10 轮。每轮记一行决策日志。" />

「至少试 10 轮」防止它运气好第一轮就达标、马上收工。它会先搭一个测量脚本，确认这个脚本分得出快慢，然后**冻结**它，之后每一轮都用同一个脚本量。每轮只改一处、量一次，变快了就留下并单独提交，没变快就整个撤回。每一轮都会在 `decision.tsv` 里记一行。

## 数字靠不靠谱：/benchmark-checklist

前后对比的数字最容易在不知不觉中出错：缓存是热的、一边是调试版本、或者被计时的那段代码根本没真的跑。性能剧本和 Hillclimb 剧本会自动跑这个检查。你自己测了一个数字，或者别人给的数字好得不像真的，就手动打：

<Copy id="perf-bench" code="/benchmark-checklist 这个 40% 的提速写进 PR 说明之前，先检查一遍" />

它会问七个问题，每个都要拿一次真实运行当证据：

| 问题 | 大白话 |
| --- | --- |
| 1. 为什么不是快一倍？ | 说出卡住这个数字的瓶颈是什么 |
| 2. 两边都按生产环境调好了吗？ | 不能一边是正式版本、一边是调试版本 |
| 3. 有没有超过物理极限？ | 比磁盘带宽还快，说明量的是别的东西 |
| 4. 有没有报错？ | 请求被拒绝往往很快，错误数要数出来 |
| 5. 能复现吗？ | 两边交替各跑至少 5 次，报中位数和范围 |
| 6. 对用户有意义吗？ | 占总耗时 1% 的函数，再快也只能省 1% |
| 7. 被计时的活真的做了吗？ | 没人 await 的 promise 跑得飞快 |

结论只有四种：更快、更慢、没有可测量的差别、无法下结论。说不出瓶颈，或者有一边没调好，就是无法下结论。

## 一个真实项目里的例子

假设你有一个跑在 Cloudflare Workers 上的会员站，数据在 D1 里。会员列表接口最近越来越慢。

<Copy id="perf-d1" title="Workers 加 D1 的例子" code={`/poteto-mode 会员列表接口 /api/members 在本地 wrangler dev、导入 5000 条测试会员时，p50 大约 900ms。
先测一份基线，告诉我时间花在哪。修掉测量出来的原因。
修好的标准：同样的数据，p50 低于 200ms，返回的会员条数和内容和修之前完全一样。
两边交替各跑 7 次，给我中位数和范围，再跑一次 /benchmark-checklist。`} />

几个细节：

- **「返回的条数和内容完全一样」**：对应第 4 题。改快了但返回少了数据，等于没修。
- **「交替各跑 7 次」**：对应第 5 题。单跑一次的数字随时可能是噪音。
- **具体的数据量**：5000 条是你能复现的场景。数据太少的话，问题可能根本不出现。

如果它最后发现原因是一个配置问题，比如缺了一个索引，检查表的第 2 题会把它算作「这一边没调好」，要求先补上再比。

## 卡住了？

<Q q="它没测就说「改成这样会更快」。">
回它：「先测。给我基线数字和 trace 文件路径，再说改哪里。」剧本本来就不允许没跑过就断言性能上限。
</Q>
<Q q="提升大得离谱，我不太信。">
跑 <code>/benchmark-checklist</code>。特别看第 3 题和第 7 题：超过物理极限、或者计时的活根本没做，都会让数字好看得不正常。这对应 <code>explain-the-number</code> 这条<a href="/wiki/principles/">原则</a>。
</Q>
<Q q="它只跑了一次就下结论。">
回它：「两边交替各跑至少 5 次，报中位数和范围。差距比两次运行之间的波动还小，就是没有差别。」
</Q>
<Q q="Hillclimb 卡在一个数上不动了，它就想停。">
剧本要求它遇到平台期先换思路，不能放宽目标来宣布完成。还有便宜的假设没试，也不该收工。真卡死了，它应该把情况告诉你，而不是原地打转。
</Q>
