## 重构只有一条规矩

重构的意思是：<mark><strong>代码的结构变了，程序的行为一点没变</strong></mark>。用户看到的页面、命令打出来的结果、存进数据库的值，全都和以前一样。

AI 做重构最常见的毛病有两个。一是顺手「改进」了几处行为，你没法分清哪些差异是故意的。二是改完说「类型检查通过了」，可类型检查只能说明代码能编译，不能说明行为没变。

pstack 的「重构」<Term k="剧本" />（Refactoring）先解决第二个问题：动结构之前，先把现在的行为钉住。

## 一句话版本

<Copy id="ref-min" title="最短的写法" code="/poteto-mode 把解析逻辑收到一个模块里，零行为变化。先记下现在的输出，改完证明它没变。" />

英文原版是 `move parsing into one module, zero behavior change. record the current output first and prove it's unchanged after.`。

「零行为变化」（zero behavior change）是一条真约束，它会把这次任务认作重构，而不是加功能或修 bug。「先记下现在的输出」决定了它第一步做什么。

在 Claude Code 里以插件方式安装的，命令要写成 `/pstack:poteto-mode`，详见[在 Claude Code 里用](/howto/claude-code/)。

## 它会怎么做

剧本的步骤，翻成大白话：

1. **先钉住行为。** 用 `/how` 弄清这块代码现在承诺了什么，然后写一个能记录当前行为的东西：一个描述现状的测试、一份输出快照，或者一个对比新旧输出的脚本。这块代码原来没测试，就先补这个再动结构。类型检查和 lint 不算。
2. **说出缺的结构。** 比如散落的判断该收成一张表。代码本来就清楚、只在一处用的，就不动。
3. **说出目标形状。** 如果今天从头写，模块怎么分、类型怎么定。跨函数边界的会先跑 `/architect`。
4. **先删再加。** 删死代码，去掉只有一个调用方的包装函数，去掉重复的校验，然后才引入新结构。「可能有用」的顺手清理会被撤回。
5. **小步走，每一步都让第 1 步的记录保持通过。** 改接口时，所有调用方一起迁过去，旧接口在同一波里删掉，不留兼容层。每次改名都会对着真实文件再检查一遍，因为改名最容易漏掉字符串和文档里的引用。
6. **证明行为没变。** 拿真实产物比：跑脚本对比新旧输出，或者把记下来的基线重放一遍。
7. **确认值得留。** 改完以后代码要更好读。哪儿都没变好读，就把这次改动撤回。
8. 整理提交：先一个「删除」提交，再一个「换结构」提交，最后是后续清理。

回复里会写：改了什么结构、拿什么记录做的对比、对比结果、哪些改动留下了、哪些撤回了。不会有新功能。

## 两个用得上的原则名

第 4、5 步各对应一条 pstack <Term k="原则" />。看它跑偏时，说出名字就能拉回来：

| 原则名 | 意思 | 什么时候说 |
| --- | --- | --- |
| `subtract-before-you-add` | 先删掉没用的，再在更简单的基础上加 | 它一上来就新建文件、加抽象层 |
| `migrate-callers-then-delete-legacy-apis` | 调用方迁完，同一波就删掉旧接口 | 它留了一个「为了兼容」的旧函数 |

## 一个真实项目里的例子

假设你有一个 Astro 静态站，十几个页面各自写了一段格式化日期的代码，写法还都不太一样。你想收成一个工具函数。

<Copy id="ref-astro" title="Astro 静态站的例子" code={`/poteto-mode 把各个页面里格式化日期的代码收到一个工具函数里，零行为变化。
动手之前：先跑 npm run build，把 dist 目录整个复制一份作为基线。
改完再 build 一次，和基线 diff。所有 HTML 文件的 diff 必须为空。
旧的写法全部删掉，不要留兼容的旧函数。
给我看 diff 命令和它的输出。`} />

这个例子好在检查是死的：**dist 目录的 diff 为空，就是行为没变；有一行不同，就是变了**。你不用读懂它改的每一行代码，只看这一条命令的输出就能判断。

如果 diff 不为空，让它逐条解释每一处差异。有些差异可能是你原来几个页面的日期格式本来就不一致，这正是下一节要说的情况。

## 重构中途发现了 bug

整理代码时经常会发现：「这里原来就是错的」。剧本的做法是**拆开**：

- 先按钉住的行为把结构改完、提交。旧 bug 原样保留。
- 再把 bug 当成一个新任务，走修 bug 的流程。见 [修一个 bug](/howto/fix-bug/)。

这样做的好处是，重构那一步的 diff 依然能和基线严格对比。要是边重构边修，你就分不清哪些差异是修好的，哪些是改坏的。

<Callout type="warn" title="想要的其实是重新设计？">
如果你本来就想改行为，那不是重构。直接说出来，让它按加功能的流程走。见<a href="/howto/add-feature/">加一个新功能</a>。很大的、跨很多模块的结构调整，剧本会交给 <code>/figure-it-out</code> 先设计整个流程。
</Callout>

## 卡住了？

<Q q="它说「类型检查和测试都过了」，就算没变。">
回它：「类型检查不算对比。先记下改之前的真实输出，改完拿同样的输入再跑一次，把 diff 给我看。」如果它已经改完了，可以让它切回改之前的提交重新生成基线。
</Q>
<Q q="它留了一个旧函数，说是为了兼容。">
回它：「migrate-callers-then-delete-legacy-apis. 把所有调用方迁过去，旧函数这一波就删掉。」这条原则针对的是项目内部代码。如果有外部用户依赖这个接口，先告诉它，那就是另一回事了。
</Q>
<Q q="改完代码反而更绕了。">
剧本第 7 步就是管这个的：没有变好读就该撤回。你可以直接说：「这次改动让读代码的人要多跳几层，撤回。」
</Q>
<Q q="它顺手修了一个 bug。">
让它把修 bug 的那部分拆出去：「先撤回 bug 修复，按原来的行为完成重构并验证。bug 另开一个任务。」
</Q>
