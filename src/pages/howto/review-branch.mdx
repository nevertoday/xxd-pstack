## 自己写的，自己看不出毛病

写代码的那个 AI，<u>最难发现自己代码里的问题</u>。它知道自己本来想做什么，读代码时也是按这个意图去读。

普通的 AI 评审又是另一个极端：给你列二十条意见，命名、风格、「可能存在风险」，真问题夹在中间，你得一条条去分辨。

pstack 的做法是：<mark><strong>换几个模型，让它们专门去把改动弄坏，而且每个问题都要跑出来才算数。</strong></mark>

在 Claude Code 里以插件方式安装的，命令前要加 `pstack:`，比如 `/pstack:interrogate`，详见[在 Claude Code 里用](/howto/claude-code/)。

## /interrogate：只留下跑得出来的问题

<Copy id="rv-int" title="评审整个分支" code="/interrogate 整个分支，挑剔一点。先别改任何东西。不是真 bug、不是行为回退的小毛病不要报。" />

这句话里的两个限定条件都有用：「先别改任何东西」让它只读，「小毛病不要报」提前过滤掉噪音。

它会这样做：

1. **定范围和意图。** 你没指定范围，就看当前分支相对基础分支的全部改动，包括还没提交的。然后用自己的话说一遍这个改动想做什么。意图不清楚时会问你。
2. **派对手。** 按你在 `/setup-pstack` 里配的模型，派几个对手，各自在自己的 <Term k="worktree" /> 里试着把改动弄坏。每个问题都要附上它跑的命令、命令打出来的结果、按意图应该是什么结果。<u>没跑过的不许报</u>。
3. **复核。** 每个问题都把命令重跑一遍。输出确实显示出错、而且这个错违背了改动的意图，才保留。根因相同的合并成一条。
4. **报告，不动手。** <u>它不会帮你改代码</u>。

报告有三部分：**Intent**（它理解的意图）、**Findings**（复核通过的问题）、**Dropped**（每个对手被丢掉了几条，为什么）。

<Callout type="warn" title="Dropped 也要看">
被丢掉的那些，不代表一定不是问题，<u>只是没能用一次运行证明</u>。扫一眼丢弃理由。你觉得某条被冤枉了，可以推翻它的结论，让它补一个复现。
</Callout>

## 小改动不放心：/blast-radius

只改了几行，但你隐约觉得会影响别的地方，用 `/blast-radius`。它不列一长串「可能的风险」，而是找出**这个改动之所以安全，靠的是哪一个事实**，然后写一段真代码去证明这个事实。

它会说清楚每个事实证明到了哪一级：只是嘴上说、指出了具体代码行、推演了出错路径走不通、写脚本跑过、还是在运行的应用里复现过。证明不了的，会标「unproven」。

## 一个真实项目里的例子

假设你在 Chrome 插件里把收藏数据从 `chrome.storage.sync` 挪到了 `chrome.storage.local`，因为 sync 有容量限制。改动不大，但你担心老用户升级后收藏全没了。

<Copy id="rv-blast" title="Chrome 插件的例子" code={`/blast-radius 这个分支把收藏从 chrome.storage.sync 挪到了 chrome.storage.local。
我最担心的是：老用户升级以后，原来存在 sync 里的收藏还在不在。
找出这个改动安全靠的是哪个事实，写一段脚本真跑一遍证明它，把输出贴给我。`} />

好的结果会像这样：它找到的关键事实是「插件升级后第一次启动，会把 sync 里的旧收藏搬到 local」，然后写一个脚本：往 sync 里放三条假收藏，模拟一次升级，再读 local，看是不是正好三条。<u>你要看的就是这个脚本的输出</u>。

如果它只交回一段「经分析，此改动是安全的」，回它：「把那个事实证明到能跑的级别。」

## 提交前清理：注释和文字

挑完毛病，提交前还有两步清理：

- **`/no-comments`**：交给一个没写过这些代码的评审去删注释。保留的只有几类：许可证头、公开接口的文档注释、代码表达不了的外部链接、被外部依赖逼出来的写法。其他注释都删掉。注释里写着「不要删」这种约束的，它会提议把约束写成类型、测试或 lint。
- **`/unslop`**：清理 PR 说明和提交信息里的 AI 腔。可以加你自己的规矩，比如 `/unslop PR 说明，不要用破折号`。

<Callout type="no" title="/deslop 不在 pstack 里">
pstack 文档里常出现的 <code>/deslop</code>（清理代码里的冗余）来自 Cursor 的另一个插件包，pstack 本身没有。没装的话，直接用大白话说：「删掉描述代码在干什么的注释、没有依据的防御判断、已经用不上的兼容代码、和这次任务无关的改动。」
</Callout>

## PR 开了以后：交给 Babysit

<Term k="PR" /> 一开，事情就来了：检查挂了、有人留评论、主分支往前走了。这些交给「看护」<Term k="剧本" />（Babysit）：

<Copy id="rv-babysit" title="盯到可以合并" code="/poteto-mode babysit 这个 PR，把它弄绿。" />

它按固定顺序处理：先冲突，再评审评论，最后 CI。所有已知的修复攒成一次推送，这样检查只重跑一次。评论会被怀疑地看待：真问题就修，噪音就在评论下面贴出反驳的证据再关掉。只想知道现在什么情况，就问小一点：「/poteto-mode 看一下 PR 123，还有什么没处理的？」

<Callout type="warn" title="Babysit 不会合并">
全绿了它也<u>停在「可以合并」这一步</u>。合并是另一个决定，要你明确说「land the stack」之类的话，交给 Shipping 剧本。Shipping 会先让没写过代码的代理逐个验证每个 PR，然后从最底下开始，只合并连续验证通过的那一段。
</Callout>

## 卡住了？

<Q q="/interrogate 说「no verified findings」，是不是它偷懒了？">
没有复核通过的问题，是一个合法的结果。看一眼 Dropped 部分，看每个对手报了什么、为什么被丢。如果你自己有一个具体的怀疑，把它说出来，让它针对那一点去试。
</Q>
<Q q="我觉得被丢掉的某一条其实是真问题。">
你可以推翻它的判断。回它：「Dropped 里第二个对手说的那条，写一个复现给我看。」跑出来了，就是真问题。
</Q>
<Q q="Babysit 全绿了，怎么还不合并？">
这是故意的。说「land the stack」或「合并吧」，它会转到 Shipping 剧本。
</Q>
<Q q="/no-comments 把我想留的注释删了。">
它只保留讲「我们改不了的东西」的注释。如果你那条注释解释的是自己代码里一个反直觉的地方，它会把这当成该重构的信号。觉得删错了，告诉它这条注释在讲哪个外部限制，让它重新判断。
</Q>
