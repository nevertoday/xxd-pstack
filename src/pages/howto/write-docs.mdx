## AI 写文档的老毛病

让 AI 写 README，常见的结果是这样：开头一段「这是一个强大的工具」，接着是安装步骤，中间插一段设计理念，后面跟一张所有参数的表，最后一句「希望对你有帮助」。什么都有一点，哪种读者都不好用。

想学怎么用的新手，要的是一步步跟着做；已经会用、来查参数的人，要的是一张干净的表。<u>混在一起，两边都得跳着读</u>。

pstack 管文档的主要是两个<Term k="技能" />：`/technical-writing` 管怎么写，`/unslop` 管去掉 AI 腔。

在 Claude Code 里以插件方式安装的，命令前要加 `pstack:`，比如 `/pstack:unslop`，详见[在 Claude Code 里用](/howto/claude-code/)。

## 先选类型：/technical-writing

`/technical-writing` 的第一条规矩是：<mark><strong>一份文档只做一种事</strong></mark>。动笔之前先问两个问题：读者是要动手做，还是要弄明白？是在学，还是在干活？两个答案一组合，就是四种文档：

| | 在学 | 在干活 |
| --- | --- | --- |
| **要动手** | 教程（tutorial）：跟着做一遍，每一步都看到结果 | 操作指南（how-to）：解决一个具体问题的步骤 |
| **要弄明白** | 讲解（explanation）：为什么这样设计，有哪些取舍 | 参考（reference）：参数、选项、错误码，只陈述事实 |

一份 README 需要好几种的话，就<u>拆成几块，互相链接</u>，而不是搅在一起。比如安装和第一次使用写成教程，参数表放进参考。

<Copy id="doc-tw" title="写一份 README" code="/technical-writing 给这个 Node CLI 写 README。先告诉我每一块该是哪种文档类型，我确认了再写。" />

除了选类型，它还管句子：对读者说「你」，用现在时，一句话只说一件事，条件写在操作前面，指令写成命令句，<u>不说「简单」「轻松」「快速」</u>。代码库里叫什么就写什么，不换同义词。

## 写之前先磨一下请求：/sharpen

不确定自己的请求是不是问到了点子上，先跑 `/sharpen`：

<Copy id="doc-sharpen" code="/sharpen 给新的计费服务写一份上手文档。" />

它**不会**去写文档。它会先说四件事：这个领域的高手会多做什么你没要求的事；高手会从什么最原始的材料入手；会用什么方法和工具；除了你和 AI，还有什么能证明结果是对的。然后把你的请求改写一遍，问得更深而不是更大，<u>该你做的决定仍然留给你</u>。你读一遍改写，觉得对，再发出去。

## 共享代码，先写 README

如果你要做的是一个别的代码会调用的包或接口，可以反过来：**先写文档，再写代码**。

<Copy id="doc-readme-first" title="先写教程" code="/poteto-mode 先写一份教程，讲我会怎么用这个新的 config 包。然后 /teach 我：为什么它比现在这个好。" />

英文原版是 `write a tutorial for how i would use the new config package first. then /teach me why it beats the current one.`。

先写教程，逼着它站在调用方的角度想：用的人会怎么写、第一步做什么、会看到什么。写出来的教程也成了一个具体的目标，后面写代码时可以拿它来对照检查。

## 写完去掉 AI 腔：/unslop

`/unslop` 后面接要改的对象，再加上你自己的规矩：

<Copy id="doc-unslop" code="/unslop README 的改动，不要用破折号" />

英文原版是 `/unslop the readme changes, no emdashes`。它内置的规则针对的是英文里常见的 AI 腔，比如滥用破折号、「不仅是 X，更是 Y」、凑三个排比、空洞的结尾。写中文文档时，<u>把你在意的中文词也写进规矩里</u>，比如「不要用赋能、无缝、一站式」。

写熟了，一句很短的话它也能读懂，比如「unslop 一下，再紧凑点」。

<Callout type="tip" title="PR 说明也是文档">
开 <a href="/wiki/pr/">PR</a> 的剧本会用 <code>/technical-writing</code> 写标题、说明和提交信息，再过一遍 <code>/unslop</code>。说明是给评审者的一分钟简报，固定几节：Why、What changed、Scope、Tradeoffs、Blast Radius、Verification，没内容的节直接删掉。详细的运行记录放链接里，不塞进正文。
</Callout>

## 一个真实项目里的例子

假设你有一个 Node CLI，作用是把 Markdown 笔记批量导出成 HTML。现在要写 README 发到 GitHub。

<Copy id="doc-cli" title="Node CLI 的例子" code={`/technical-writing 给这个 CLI 写 README。
安装和第一次导出写成教程：每一步告诉读者应该看到什么输出。
所有参数单独放一节参考，从 --help 的真实输出里整理，不要自己编参数。
写完以后，在一个空目录里照着教程从头跑一遍，每条命令都要跑通，把终端输出贴给我。
最后 /unslop 一遍，不要用破折号，不要用「强大」「轻松」。`} />

这里最有用的是「在空目录里照着跑一遍」。<mark>文档写得通不通顺可以争，命令跑不跑得通没法争</mark>。哪一步跑不通，就是教程写漏了一步。

「从 --help 的真实输出里整理」也一样：参考类文档只陈述事实，事实就从代码里来。

## 卡住了？

<Q q="写出来的 README 还是什么都有一点。">
回它：「按 technical-writing 的分法拆开：上手部分只留教程，参数表移到参考那一节，设计理念单独一节讲解。不要混在一起。」
</Q>
<Q q="/unslop 过了，中文读起来还是有 AI 味。">
它的内置规则主要针对英文。把你看着别扭的具体词句列出来，作为额外规矩加在命令后面，比如「/unslop 这一段，不要用破折号，不要用『赋能』『无缝』，一句话不超过 30 个字」。<u>规矩越具体，它改得越准</u>。
</Q>
<Q q="/sharpen 没帮我写文档。">
这是设计如此。它只改写你的请求。读完改写，觉得对，再把改写后的请求发出去，比如交给 <code>/poteto-mode</code> 或 <code>/technical-writing</code>。
</Q>
<Q q="PR 说明写得太长。">
回它：「PR 说明是一分钟简报。每节一到三句，详细数据放进链接的文件里。」
</Q>
