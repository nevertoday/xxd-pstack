## 最初の 1 文で完了条件を伝える

<Copy id="done" code="/poteto-mode このコマンドに JSON 出力を追加してください。テキスト出力は変更前とバイト単位で同じままにし、JSON は正しくパースできるようにしてください。両方ともサンプルプロジェクトで実行して、証拠を見せてください。" />

返答には、実際に実行したコマンドとその出力が含まれるはずです。チェックを実行できなかった場合は、「判定不能」と答えます。

<mark><strong>「コンパイルが通った」は証拠になりません。</strong></mark>変更内容に合った証拠を求めてください：

| 変更した内容 | 求める証拠 |
| --- | --- |
| コマンドライン | 実際のコマンドを実行する |
| UI | 起動中のアプリ上で一通り操作する |
| パーサー、マイグレーション | 保存済みの入力を再実行する |
| パフォーマンス | 変更前後の計測値を比べる |
| ストレージ | 書き込んだ値を読み戻す |

## AI にアプリ上で検証させる

AI がアプリを操作する手段を持っていない場合は、まずこれを実行します：

<Copy id="cvs" code="/create-verification-skill" />

**得られるもの**：`/verify-<your-app-name>` という<Term k="验证技能" />です。主にコードを読み込んで作成し、渡す前に一通り試運転します。<u>試運転に失敗した場合、作られたものは使わないでください。</u>

そのあとは、次のように証拠を求めます：

<Copy id="use-vs" code="/poteto-mode 一括アーカイブ機能を作ってください。/verify-<your-app-name> で検証して、証拠として画面録画とスクリーンショットを出してください。" />

検証スキルはリポジトリにコミットしておきましょう。`/maintain-verification-skill` で定期的に見直してください（毎日が理想です）。何が生成されるか、どう確かめるか、作者がどう使っているかについては、[プロジェクトに検証スキルを用意する](/ja/howto/verify-app/)をご覧ください。

## PR を作成する

<Term k="PR" />（プルリクエスト）とは、レビューのために送り、そのあとマージする変更のまとまりです。

<Copy id="pr" code="/poteto-mode PR を作成してください。コミットは小さく順序立てて分け、説明欄に証拠を載せてください。" />

**得られるもの**：<Term k="worktree" />（同じ Git リポジトリの別作業フォルダ）の中で小さなコミットに整理し、最後に PR のリンクを返してくれます。

## マージできる状態にする：PR を babysit（見守り・自動対応）する

<Copy id="babysit" code="/poteto-mode この PR を babysit して、チェックがすべて通る状態にしてください。" />

**得られるもの**：まずコンフリクト、次にレビューコメント、最後に CI（プッシュのたびに走るチェック）の順に対応します。本当に問題がある箇所は修正します。妥当でないコメントには、理由を添えて返信します。

<strong>「マージ可能」な状態で止まります。代わりにマージすることはありません。</strong>

## マージする：land the stack

PR スタックとは、前の PR の上に次の PR を積み重ねた一連の PR のことです。

<Copy id="ship" code="/poteto-mode land the stack." />

**得られるもの**：それぞれの PR を書いていない別の AI が、改めて検証します。スタックの一番下から順に、途切れずに検証を通った分だけをマージします。どこで途切れたかを教えてくれます。

<Callout type="tip" title="Claude Code を使う場合">
PR の作成には `gh` を使います。あらかじめ手元のマシンで GitHub にログインしておいてください：`gh auth login`。
</Callout>

## つまずいたときは？

<Q q="「完了しました」と言うだけで、証拠を見せてくれません。">
<p>こう返してみてください：「apply prove it works. ビルドログではなく、実際の出力を見せてください。」prove it works は「実際の結果で動くことを証明する」という意味です。pstack が認識する原則の名前です。</p>
</Q>
<Q q="計測したら速くなっていましたが、本当に速くなったのかどう確かめればいいですか？">
<Copy id="bench" code="/benchmark-checklist PR に入れる前に、このエクスポートの高速化をチェックしてください" />
<p>7 つの質問を 1 つずつ実際に確かめます。判定は「速くなった」「遅くなった」「計測できる差がない」「判定不能」の 4 つだけです。</p>
</Q>
<Q q="小さな変更なのですが、少し不安です。">
<p><code>/blast-radius</code> を使います。その変更が安全な理由を見つけ出し、実際にコードを実行して証明します。</p>
</Q>
<Q q="2 つのリトライが同時にぶつかるような、テストでは届かないケースがあります。">
<p><Term k="形式化验证" />を使います：<code>/create-formal-verification-skill タスクのリースとリトライ処理。同じタスクが同時に 2 回実行されてはならない。</code> 使う価値がある場面と反例の読み方：<a href="/ja/howto/formal-verify/">テストでは届かないバグ：形式検証</a>。</p>
</Q>
