## まずはこれをコピー

<Copy id="mig-contract" title="寝る前の引き継ぎ" code={`/poteto-mode これから寝ます。<base> から新しい worktree を切って、すべての呼び出し元を新しいパーサーへ移行してください。
完了条件：古い呼び出し元が 0 件であること、パーサーのフィクスチャがすべて通ること、古い API が削除されていること。
判断ログを残してください。コミット前に確認は不要です。
/loop until done. 数時間かけても本当に行き詰まったら、そこで止まって理由をまとめてください。`} />

pstack のドキュメントにある元の表現：

<Copy id="mig-contract-en" title="元の表現" code={`/poteto-mode im going to bed. migrate every caller to the new parser in a fresh worktree off <base>.
done means zero old callers, all parser fixtures pass, old api deleted.
keep a decision log. don't ask me before committing.
/loop until done. if you're truly stuck after a few hours, stop and write up why.`} />

## 各行の役割

- **「これから寝ます」**：質問のために止まらず、そのまま進め続けるよう伝えます。
- **「完了条件」**：各ラウンドで AI が実行できるチェックです。
- **「新しい worktree」**：同じ Git リポジトリの別作業フォルダ（<Term k="worktree" />）なので、進行中のほかの作業に触れません。
- **「コミット前に確認は不要です」**：そのままでは AI が止まって聞いてくる質問に、あらかじめ答えておきます。
- **`/loop until done`**：完了条件へ何度でも立ち戻らせます。`/loop` は Cursor と Claude Code の組み込み機能です。pstack のスキルではありません。
- **行き詰まったときの出口**：本当に行き詰まったら、一晩中空回りせず止まって理由を説明します。

<Callout type="no" title="かけた時間は完了条件になりません">
「4 時間作業してください」では、AI が確かめる基準がありません。<code>/loop</code> には、合否がはっきり決まる条件を渡してください。
</Callout>

## Chrome 拡張の例

何十ものファイルが `chrome.storage.sync` を直接呼んでいます。新しい `settings` モジュールを作ったので、すべての呼び出しをそちらへ移し、古い `getPref` を削除したいとします。

<Copy id="mig-ext" title="Chrome 拡張の例" code={`/poteto-mode これから寝ます。main から新しい worktree を切って、chrome.storage.sync への直接の呼び出しをすべて新しい settings モジュールへ移してください。
完了条件：
1. grep -rn "chrome.storage.sync" src/ で見つかるのが settings モジュール内の 1 か所だけであること。
2. npm test がすべて通ること。
3. getPref 関数とそのテストが削除されていること。
4. 旧バージョンが入っていたテスト用プロファイルでオプションページを開いたとき、すべての設定がマイグレーション前とまったく同じに表示されること。スクリーンショットを送ってください。
挙動はまったく同じに保ってください。マイグレーション中にバグを見つけても、メモだけ残してください。途中でバグを直さないでください。
判断ログを残してください。コミット前に確認は不要です。
/loop until done. 本当に行き詰まったら、そこで止まって理由をまとめてください。`} />

- **4 つの完了条件**：grep を 1 回、テスト実行を 1 回、2 つの名前が残っているかどうか、スクリーンショットを 1 枚。それぞれ合否が決まります。翌朝はこの 4 つだけ確認します。
- **「途中でバグを直さないでください」**：前後をそのまま比べられるようにするためです。

## 任せる前に：自分で確かめられるか？

<mark>一晩かけて走らせるのがうまくいくのは、AI が自分の作業を自分で確かめられるときだけです。</mark>そうでなければ、未検証のコードが速く積み上がるだけです。次の 4 つがすべて当てはまるときだけ、任せて走らせてください：

1. **一度自分でやったことがある**。手作業でも、AI の作業を見ながらでも構いません。完了がどんな状態かわかっています。
2. **AI に道具がそろっている**。普段使う<Term k="验证技能" />、プロファイラ、ログです。
3. **各ステップで正しさを確かめられる**。ステップが基準に届かないときは止まれます。
4. **繰り返すミスに対策してある**。会話ログを読み、繰り返すエラーをチェックに変えてあります。

そうでなければ、見守りながら走らせてください。

## 翌朝どこを見るか

<Copy id="mig-audit" title="翌朝の確認" code="/show-me-your-work 昨夜やったことを教えてください" />

**まず末尾の Attention（要確認）セクションを読んでください**。他社のモデルで動くヘルパーの AI が、先にログを読みます。Attention には、根拠の弱い判断など、よく確認すべき点が並びます。そこに挙がったログ行をたどってください。

<Term k="决策日志" />はデフォルトで作業フォルダ内の `decisions.tsv` にあり、コミットされません。1 行が 1 つの判断で、その理由と根拠が書かれています。

状況だけ手早く知りたいですか？実行中の会話で `/ketchup` と入力してください。読み取り専用です。何が変わったか、どの判断を待っているかを教えてくれます。

## 途中で止めるとき

ノート PC を閉じたりエディタを再起動したりする必要があるときは、「一時停止して」または「オフラインになります」と伝えてください。未保存の作業を `wip:` コミットとして残し、あとで再開するためのメモを書きます。新しい会話を始めて引き継がせてください。メモから続きを進めてくれます。

「このまま進めて」や「続けて」と言っても、一時停止にはなりません。

## 一晩で複数の作業を走らせるとき

互いに関係のない変更がいくつもあるときは、2 つの<Term k="剧本" text="プレイブック" />があります：

- **Autopilot-stack：マージしない**。翌朝に検証済みの PR（プルリクエスト）を確認し、自分で判断できます。
- **Autopilot-full：マージする**。各 PR は、別のヘルパーの AI が検証したあとでのみマージされます。

何日もかかるプロジェクトには専用のプレイブックがありません。`/poteto-mode` はそれを `/figure-it-out` に渡し、その場で進め方を設計します。

迷ったら Autopilot-stack を選んでください。マージ前の最終判断を手元に残せます。

## つまずいたときは？

<Q q="翌朝「完了」と出ていますが、本当か不安です。">
まとめの文章は鵜呑みにしないでください。証拠を見てください。grep やテスト実行など、完了条件のチェックを自分で再実行します。そのうえで、<code>/show-me-your-work</code> の返答にある Attention セクションを読んでください。
</Q>
<Q q="夜中に質問して止まり、そのまま待機したままでした。">
引き継ぎに事前の許可が抜けていました。次回は「これから寝ます」と「コミット前に確認は不要です」を入れてください。
</Q>
<Q q="完了条件を緩めて「完了」と宣言されました。">
本来あってはならない動きです。「完了条件は変えません。最初の 4 つのチェックを 1 つずつ実行して見せてください。」と返してください。
</Q>
<Q q="「続けて」と言ったのに、一時停止コミットを作られました。">
それは起きないはずです。「一時停止は頼んでいません。このまま進めてください。」と返してください。
</Q>
