## まずはこれをコピー

<Copy id="ref-min" title="最短バージョン" code="/poteto-mode パース処理を 1 つのモジュールにまとめてください。挙動は一切変えないこと。先に今の出力を記録して、変更後に変わっていないことを証明してください。" />

リファクタリングとは、<mark><strong>コードの構造だけを変えて、動きは一切変えないこと</strong></mark>です。

- **挙動は一切変えない**：ユーザーから見えるものは何も変えません。AI はこの作業をリファクタリングとして扱います。機能追加もバグ修正もしません。
- **先に今の出力を記録する**：あとで比べられるよう、「変更前」の状態を保存しておきます。「型チェックが通った」だけでは証明になりません。それはコードがコンパイルできることを示すだけです。

## Astro 静的サイトの例

十数ページそれぞれに日付フォーマットのコードがあり、どれも少しずつ違います。これを 1 つのユーティリティ関数にまとめたいとします。

<Copy id="ref-astro" title="Astro 静的サイトの例" code={`/poteto-mode 全ページにある日付フォーマットのコードを 1 つのユーティリティ関数にまとめてください。挙動は一切変えないこと。
作業前に npm run build を実行し、dist フォルダ全体をベースラインとしてコピーしてください。
終わったら再度ビルドし、ベースラインと diff を取ってください。すべての HTML ファイルで diff が空になること。
古いコードはすべて削除してください。互換性のために古い関数を残さないこと。
実行した diff コマンドとその出力を見せてください。`} />

- **dist の diff が空であること**：空なら何も変わっていません。1 行でも出れば、どこかが変わっています。すべての行を読む必要はありません。その出力 1 つで十分です。
- **古い関数を残さない**：呼び出し元をすべて移行し、古いコードも同じ作業の中で削除します。

diff が空にならなかったら、1 つひとつの差分を AI に説明させてください。もともと日付のフォーマットが違っていたページが原因かもしれません。

## 送ったあと、どこを見るか

**最初：今の動きをどう記録したか**。テストか、出力のスナップショットか、比較スクリプトです。

**途中：足す前に消す**。まず使っていないコードを消してから、新しい構造を加えます。

**最後：比較の結果**。返答には、どの構造を変えたか、何を比べたか、結果はどうだったか、どの変更を元に戻したかが書かれます。コードが読みやすくなっていなければ、その変更を元に戻します。

## 途中でバグを見つけたとき

コードを整理していると、「もともとここがおかしかった」と気づくことはよくあります。作業を分けましょう。

1. **リファクタリングを終えてコミットする**。古いバグはそのまま残します。
2. **新しいタスクとしてバグを直す**。[バグ修正](/ja/howto/fix-bug/)を参照してください。

こうしておけば、リファクタリングの結果をベースラインときれいに比べられます。リファクタリングの途中でバグまで直すと、修正なのか壊したのか区別がつかなくなります。

<Callout type="warn" title="実は動きも変えたいときは？">
それならリファクタリングではありません。そう伝えて、機能追加として扱ってください。<a href="/ja/howto/add-feature/">機能追加</a>を参照してください。多くのモジュールにまたがる大きな変更では、まず <code>/figure-it-out</code> に引き継いで全体の計画を立てます。
</Callout>

## つまずいたときは？

<Q q="「型チェックとテストが通った」から何も変わっていないと言われます。">
「型チェックは比較になりません。変更前の実際の出力を記録し、変更後に同じ入力で実行して diff を見せてください」と返してください。すでに作業が終わっているなら、前のコミットをチェックアウトしてベースラインを作り直させてください。
</Q>
<Q q="最初に新しいファイルや抽象レイヤーを追加し始めます。">
「subtract-before-you-add」と返してください。まず不要なものを消し、シンプルになった土台の上に組み立てるという意味です。pstack の<Term k="原则" text="原則" />の名前です。そのまま打てば意味が通じます。
</Q>
<Q q="「互換性のため」として古い関数を残しました。">
「migrate-callers-then-delete-legacy-apis. 呼び出し元をすべて移行して、今回の作業で古い関数を削除してください」と返してください。この原則名は、まさにその意味です。対象はプロジェクト内のコードだけです。外部ユーザーがそのインターフェースに依存しているなら、先に伝えてください。
</Q>
<Q q="変更後のほうがコードが入り組んでいます。">
「この変更のせいで、読む人がたどる層が増えています。元に戻してください」とそのまま伝えてください。読みやすくなっていなければ、元に戻すべきです。
</Q>
<Q q="途中でバグまで直してしまいました。">
「バグ修正は元に戻し、元の挙動のままリファクタリングを終えて検証してください。バグは別のタスクにしてください」と返してください。
</Q>
