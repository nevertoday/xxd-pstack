## まずはこれをコピー

<Copy id="doc-tw" title="README を書く" code="/technical-writing この Node CLI の README を書いてください。まず各セクションをどの種類のドキュメントにするか教えてください。こちらで確認してから書いてください。" />

AI が書いた README には、インストール手順、設計思想、オプション一覧など、少しずつ何でも混ざりがちです。初心者も、オプションを調べたい人も、あちこち読み飛ばすことになります。

`/technical-writing` の最初のルール：<mark><strong>1 つのドキュメントに役割は 1 つだけ。</strong></mark>各セクションを次の 4 種類のいずれかに分類します。

- **チュートリアル**：一度手順どおりに進め、各ステップで結果が見えるもの。
- **How-to ガイド**：特定の問題を 1 つ解決するための手順。
- **解説**：なぜこの設計なのか、どんなトレードオフがあるのか。
- **リファレンス**：オプション、フラグ、エラーコード。事実のみ。

1 つの README に複数の種類が必要な場合は、パートを分けて互いにリンクでつなぎます。

## Node CLI の例

Markdown のメモを HTML に一括エクスポートする CLI 用に、GitHub 向けの README を作る場合です。

<Copy id="doc-cli" title="Node CLI の例" code={`/technical-writing この CLI の README を書いてください。
インストールと最初のエクスポートはチュートリアルとして書き、各ステップでどんな出力になるか読者に示してください。
オプションはすべて別のリファレンスセクションにまとめ、実際の --help の出力から作成してください。存在しないオプションを勝手に作らないでください。
書き終わったら、空のフォルダでチュートリアルを最初から試して、すべてのコマンドが動くことを確かめ、ターミナルの出力を貼ってください。
最後に /unslop をかけてください。エムダッシュは禁止、「パワフル」「手軽」も禁止です。`} />

- **「空のフォルダでチュートリアルを最初から試す」**：最も役に立つ一文です。文章の好みは議論できても、コマンドが動くかどうかは議論の余地がありません。
- **「実際の --help の出力から作成」**：リファレンスは事実を書くドキュメントです。その事実はコードから来ます。
- **「最後に /unslop をかける」**：AI っぽいトーンに加え、使いたくない言葉も取り除きます。

## 送信後に確認するところ

**最初：どの種類に分類したか**。設計思想が入門パートに紛れ込んでいたら、すぐ直します。

**最後：ターミナルの出力**。どこかのステップが失敗していれば、チュートリアルに手順が抜けています。

## 最後に AI っぽいトーンを取り除く：/unslop

<Copy id="doc-unslop" code="/unslop README の変更箇所、エムダッシュ禁止" />

組み込みのルールは、英語でよくある AI っぽいトーンを対象にしています。エムダッシュの多用、無理やり 3 つ並べる列挙、中身のない締めくくりなどです。気になる表現があれば、「シームレスは禁止、エンパワーは禁止」のようにルールへ足せます。

## 他のコードから呼ばれるもの：先にチュートリアルを書く

他のコードから使うパッケージや API なら、コードより先にドキュメントを書くこともできます。

<Copy id="doc-readme-first" title="チュートリアルを先に書く" code="/poteto-mode まず新しい config パッケージの使い方を説明するチュートリアルを書いてください。そのあと /teach で、今の実装より優れている理由を教えてください。" />

先にチュートリアルを書かせると、AI は使う側の目線で考えるようになります。最初に何を書くのか、どんな結果が見えるのか、という視点です。そのチュートリアルは、コードを確かめる基準にもなります。

## 頼み方が合っているか迷うとき：/sharpen

<Copy id="doc-sharpen" code="/sharpen 新しい課金サービスのオンボーディング用ドキュメントを書いてください。" />

ドキュメント自体は書きません。依頼文をより的確に書き直してくれます。たとえば、専門家ならほかに何をするか、どの資料から調べ始めるか、結果が正しいと何で示せるか、といった点です。書き直された内容を読みます。よさそうなら、そのまま送ります。

<Callout type="tip" title="PR の説明文もドキュメントの 1 つ">
AI が <Term k="PR" /> を作成するときは、<code>/technical-writing</code> で説明文を書き、<code>/unslop</code> をかけます。説明文はレビュアーが 1 分で読める要約です。空のセクションは削除されます。
</Callout>

## つまずいたときは？

<Q q="README がまだ何でもごちゃ混ぜになっています。">
こう返してください。「technical-writing のやり方で分けてください。入門パートにはチュートリアルだけを残し、オプション一覧はリファレンスセクションに移し、設計の考え方は独立した解説セクションにしてください。混ぜないでください。」
</Q>
<Q q="/unslop を実行しても、まだ AI っぽい文章のままです。">
気になる言葉やフレーズを具体的に書き出し、コマンドの後ろに追加します。たとえば「/unslop このセクションに適用、エムダッシュ禁止、シームレスやエンパワーは禁止、1 文は 40 字以内」のようにします。ルールが具体的であるほど、仕上がりはよくなります。
</Q>
<Q q="/sharpen を使ってもドキュメントが書かれませんでした。">
依頼文を書き直すだけです。書き直された依頼文を <code>/poteto-mode</code> か <code>/technical-writing</code> に送ってください。
</Q>
<Q q="PR の説明文が長すぎます。">
こう返してください。「PR の説明文は 1 分で読める要約にしてください。各セクションは 1〜3 文にして、詳しいデータはリンク先のファイルにまとめてください。」
</Q>
