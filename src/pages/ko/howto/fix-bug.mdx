## 먼저 이것부터 복사하세요

<Copy id="bug-min" title="가장 짧은 버전" code="/poteto-mode 재시도 후 사용자에게 알림이 두 번 가요. 먼저 재현하고, 고친 뒤, 검증해 주세요." />

“재현”은 문제를 다시 일으켜 보는 거예요. AI가 이걸 가장 먼저 해요. 재현하지 못하면 코드를 바꾸지 않아요.

순서는 정해져 있어요. <mark><strong>재현하고, 진짜 원인을 찾고, 고친 뒤, 같은 단계로 검증해요.</strong></mark>

<Fig id="h-bug" />

## 단서를 조금 더 주세요

<Copy id="bug-full" title="전체 버전" code="/poteto-mode 어제 릴리스 이후로 CSV 내보내기에서 마지막 행이 빠져요. 실패한 job id는 4812예요. 먼저 재현하고 고쳐 주세요. 60,000행 테스트 데이터셋이 한 행도 빠짐없이 내보내지면 고쳐진 거예요. 고치기 전과 후의 행 수를 보여 주세요." />

각 부분은 한 가지 역할을 해요.

- **증상과 시작 시점**: 릴리스 이후로 내보내기에서 마지막 행이 빠져요.
- **알고 있는 단서**: job id예요. 찾는 과정을 한 번 줄여 줘요.
- **고쳐졌다고 볼 기준**: 60,000행이 모두 내보내져야 해요.
- **보여 달라고 할 내용**: 고치기 전과 후의 행 수예요.

<Callout type="warn" title="추측은 아껴 두세요">
“페이지네이션 코드 문제인 것 같아요”라고 하면 AI가 거기만 파고들어요. AI의 판단을 먼저 들어 보세요. 그다음에 생각을 덧붙이세요.
</Callout>

## Chrome 확장 프로그램 예시

사용자 제보: 새로고침하면 사이드 패널에 저장된 항목이 가끔 두 번 보여요.

<Copy id="bug-ext" title="Chrome 확장 프로그램 예시" code={`/poteto-mode 새로고침하면 사이드 패널의 저장 목록에 항목이 가끔 중복으로 보인다는 사용자 제보가 들어왔어요.
직접 해 보니 “저장”을 빠르게 두 번 누르면 더 자주 생겨요. 먼저 재현해 주세요. 아직 코드는 바꾸지 마세요.
저장을 열 번 눌러도 목록에 항목이 정확히 하나, chrome.storage에도 정확히 하나만 남으면 고쳐진 거예요.
고치기 전과 후에 storage에 실제로 무엇이 들어 있는지 보여 주세요.`} />

- **“chrome.storage에도 정확히 하나”**: UI에서는 중복을 가렸어도 데이터에는 두 개가 들어 있을 수 있어요. 저장된 값을 확인하세요.
- **“저장을 열 번 눌러도”**: “가끔” 생기는 문제를 매번 통과하거나 실패하는 확인 기준으로 바꿔 줘요.

## 보낸 뒤에는 여기를 보세요

**처음: AI가 다시 정리한 내용.** 다른 문제를 말하고 있다면 바로 멈추세요.

**중간: <Term k="待办清单" />.** 가능한 원인을 몇 가지 적어 두고 하나씩 제외하면서 문제가 처음 생기는 지점을 찾아요. 고쳐야 할 곳은 뒤쪽의 검사 코드가 아니라 바로 거기예요.

**끝: 고치기 전과 후.** 둘 다 같은 재현 단계를 써요.

## 막혔나요?

<Q q="버그를 재현할 수 없다고 해요.">
좋은 신호예요. AI가 무턱대고 코드를 바꾸지 않고 있어요. 더 구체적으로 알려 주세요. 어느 페이지인지, 어떤 데이터인지, 무엇을 클릭했는지, 어느 버전인지요. 로그나 녹화 영상을 붙여 넣어도 돼요.
</Q>
<Q q="“고쳤어요”라고만 하고 근거를 안 보여 줘요.">
이렇게 답하세요. “apply prove it works. 재현 단계를 다시 돌리고 실제 출력을 보여 주세요.” <code>prove it works</code>는 실제로 작동하는 결과를 보여 달라는 뜻이에요. pstack <a href="/ko/wiki/principles/">원칙</a>의 이름이에요. 그대로 입력하면 AI가 알아들어요.
</Q>
<Q q="뒤쪽에 if 검사만 하나 덧붙이고 고쳤다고 해요.">
이렇게 답하세요. “fix root causes. 이런 상태 자체가 생기면 안 돼요. 문제가 처음 생기는 지점을 찾아 주세요.” <code>fix root causes</code>는 진짜 원인을 고치라는 뜻이에요. 이것도 원칙 이름이에요. 그 상태가 실제로 유효한 경우에만 검사를 덧붙이는 게 해결책이 돼요.
</Q>
