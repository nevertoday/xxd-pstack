테스트는 사람이 떠올려 적어 둔 경우만 확인해요. <Term k="形式化验证" />은 정해진 범위 안의 **모든** 경우를 확인해요. 모델에서 가능한 모든 단계 순서, 일정 크기까지의 모든 입력, 혹은 아예 모든 입력 전체가 대상이에요.

어떤 버그는 아무도 밟아 보지 않는 경로에 숨어 있어요. 재시도 두 개가 겹치거나, 쓰는 도중에 락이 만료되거나, 상태 업데이트가 순서가 뒤바뀌어 도착하는 경우예요. 테스트를 열 번 돌려도 모두 통과해요. 그러다 출시 1년 뒤 딱 한 번 벌어져서 중복 결제나 데이터 손상이 생겨요.

<Fig id="h-formal" />

## 언제 쓸 만한가요

- **동시성과 락**: 여러 프로세스나 머신이 하나의 자원을 두고 경쟁하는 경우예요. 작업 리스(lease), 재고 수량 등이 해당해요.
- **재시도와 “정확히 한 번” 보장**: 메시지가 두 번 전달되면 안 되거나, 주문 하나가 멤버십을 딱 한 번만 부여해야 하는 경우예요.
- **상태 머신**: 주문 상태, 오프라인에서 고친 뒤 나중에 동기화하는 흐름, 승인 흐름 등이에요.
- **파서**: 어떤 입력이 들어와도 크래시가 나거나 잘못 읽히면 안 되는 경우예요.
- **안전하지 않은 저수준 코드**: 메모리 안전성, 정수 오버플로, 자료구조가 항상 지켜야 하는 조건이에요.

평범한 생성·조회·수정 화면, 문구, 스타일링에는 필요 없어요. 그런 건 <a href="/ko/howto/verify-app/">검증 스킬</a>이 맡아 줘요. `/setup-pstack`을 실행할 때도 이걸 한 번 제안해요. <mark>코드에 위와 같은 로직이 있고 거기서 버그가 나면 피해가 크다면 “예”라고 답하세요. 아니라면 “아니오”라고 하고, 나중에 상황이 바뀌면 그때 실행하면 돼요.</mark>

한 문장에 두 가지만 들어가면 충분해요. **어떤 코드를 확인할지**, 그리고 **어떤 규칙이 절대 깨지면 안 되는지**예요.

## 대상을 어떻게 고르나요

코드가 지켜야 할 약속 중에서, 깨지면 사용자에게 피해가 가고 테스트가 그 깨지는 경우에 잘 닿지 않는 곳을 찾아요. <u>검증하기 가장 쉬운 대상이 아니라 가장 가치 있는 대상을 골라요.</u> 영역을 지정해 주면 거기서부터 시작해요.

## 도구를 어떻게 고르나요

질문에 따라 도구가 정해져요. 무엇을 왜 골랐는지 설명해 주기 때문에, 이 언어들을 따로 배울 필요는 없어요.

| 알고 싶은 것 | 도구 유형 | 자주 쓰이는 예시 |
| --- | --- | --- |
| 이벤트가 잘못된 순서로 일어날 수 있을까요? | 모델 체커: 설계를 작은 모델로 옮겨 모든 순서를 다 밟아 봄 | TLA+(코드 언어와 상관없이 이런 질문의 기본 선택) |
| 모든 입력에서 코드 자체가 제대로 동작할까요?(메모리 안전성, 오버플로, 자료구조 조건) | 코드 위에서 직접 도는 검증기 | 언어에 따라 다름: C는 CBMC, Rust는 Kani |
| 사용하는 언어에 그런 검증기가 없을 때 | 실제 코드에 수많은 생성 입력을 넣어 확인 | 속성 기반 테스트(Property-based testing): fast-check, Hypothesis |
| 범위 제한만으로는 부족하고 모든 크기에서 성립해야 할 때 | 증명 | Lean 같은 증명 보조기 |

예시 열은 이 사이트에서 정리한 내용이에요. 스킬이 특정 도구를 정해 두지는 않아요. 팀이 설치해서 돌릴 수 있는 도구를 우선으로 골라요.

## 좋은 형식 검증은 어떤 모습일까요

스킬 자체의 기준이자, 결과를 넘겨받을 때 확인해 볼 항목이에요.

- **코드에 충실함**: 모델이나 증명의 모든 부분이 직접 열어 볼 수 있는 실제 코드를 가리켜요. 코드에서 한 단계로 일어나는 일은 모델에서도 한 단계예요. 이름도 프로젝트에서 가져와요.
- **실패할 수 있음**: <mark><strong>실패하는 걸 한 번도 본 적 없는 검증은 아무것도 증명하지 못해요.</strong></mark> 일부러 망가뜨린 코드(검사 코드를 빼거나 두 단계 순서를 바꾼 코드)에서 각 규칙이 실제로 실패하고 검증이 그걸 잡아내는 걸 한 번 보여 줘요.
- **발견은 그대로 보고함**: 현재 코드가 이미 규칙을 깨고 있다면 반례와 함께 그대로 보고해요. 통과시키려고 규칙이나 모델을 느슨하게 바꾸지 않고, 요청하지 않는 한 제품 코드도 건드리지 않아요.
- **범위를 솔직하게 밝힘**: 무엇을, 어떤 한계 안에서, 어떤 가정 아래 검증했고 무엇은 빠졌는지 적어 둬요. 통과했다는 건 그 모델과 범위 안에서만 성립한다는 뜻이지 시스템 전체를 보장하는 게 아니에요.
- **도구를 몰라도 읽힘**: 규칙과 깨졌을 때의 피해를 각각 쉬운 한 문장으로 적어요. 반례도 코드에서 쓰는 용어로 단계별로 설명해요.
- **다시 돌리기 가벼움**: 명령어 하나로 실행되고, 도구 버전도 고정돼 있어요. 다음 AI가 관련 변경이 있을 때마다 돌릴 수 있을 만큼 빨라요.
- **코드와 보조를 맞춤**: 각 검증이 어떤 파일과 함수를 다루는지, 마지막으로 일치한다고 확인한 커밋이 무엇인지 기록해 둬요. 그 코드가 바뀌면 다음 AI가 다시 살펴봐야 한다는 걸 알 수 있어요.

현재 코드에 정말 버그가 있다면 수식이 아니라 이런 단계로 보여 줘요.

<Fig id="h-formal-cex" />

각 단계가 코드의 특정 위치에 연결돼 있어서, 반례를 실제 코드로 따라가며 모델이 틀린 게 아닌지 확인할 수 있어요. PM이나 디자이너에게 보여 주려면 `/statechart`를 쓰세요. 검증이 실패했을 때는 가장 짧은 실패 경로를 쉬운 말로 풀어 주고, 통과했을 때는 시스템이 상태 사이를 어떻게 오가는지 그려 줘요.

## 무엇이 만들어지나요

검증하는 코드 이름으로 된 새 스킬이 프로젝트에 추가돼요. 다음 AI는 그 스킬만 읽고도 아래 일을 할 수 있어요.

1. 이번 변경이 검증 대상 코드를 건드리는지 판단하기
2. 명령어 하나로 검증 돌리기
3. 진짜 버그인지 모델링 실수인지 구분하기
4. 의도한 변경일 때 검증을 함께 업데이트하기

결과를 넘겨주기 전에, 실제 코드에 규칙을 깨는 임시 변경을 한 번 넣어 스킬대로 돌려 봐요. 이때 검증이 그 변경을 반드시 잡아내야 해요. 그다음 임시 변경을 되돌리고 검증이 원래 상태로 돌아왔는지 확인해요. 넘겨줄 때는 아래 내용을 정리해 줘요.

- 무엇을 어떤 도구로, 왜 그 도구를 골라, 어떤 범위 안에서 검증했는지
- 검증에서 무엇을 발견했는지 쉬운 말로 정리한 내용
- 앞으로 어떻게 돌리면 되는지
- 다루지 않는 범위는 무엇인지

비슷하게 가치 있는 두 번째 대상을 찾았을 때만 추가로 제안해요.

## 코드가 바뀐 뒤: /maintain-formal-verification-skill

위험한 경우는 검증이 실패할 때가 아니에요. <mark>코드가 바뀌었는데도 검증이 계속 통과하는 경우</mark>예요. 더 이상 존재하지 않는 코드를 설명하고 있는데도 마치 증명된 것처럼 보이거든요.

변경이 검증 스킬을 거쳐 이뤄지면 AI가 작업하면서 검증도 함께 업데이트해요. 그 과정을 거치지 않은 변경(머지, 사람이 직접 수정한 코드, 리팩터링 등)이 있었다면 아래 명령어를 돌리세요.

<Copy id="mfv" code="/maintain-formal-verification-skill" />

현재 상태 그대로 검증을 한 번 돌려 본 뒤, 마지막 확인 이후 검증 대상 코드를 건드린 모든 커밋(이름이 바뀌거나 쪼개지거나 옮겨진 함수 포함)을 읽어요. 그리고 통과할 만한 쪽이 아니라 실제 코드를 기준으로 모델을 업데이트해요. 각 검증은 아래 결과 중 하나로 끝나요.

| 결과 | 뜻 |
| --- | --- |
| in sync | 검증 대상 코드에 중요한 변경이 없고, 검증도 통과함 |
| updated | 코드가 바뀌어서 검증을 현재 코드에 맞게 고쳤고, 통과함 |
| bug | 검증은 현재 코드를 제대로 반영하는데, 코드가 규칙을 깸. 검증이 어긋난 게 아니라 실제 코드 문제 |
| blocked | 검증을 코드에 다시 맞추지 못했거나 실행하지 못함. 이유를 함께 알려 줌 |

하나의 검증이 updated이면서 동시에 bug일 수도 있어요. 업데이트로 현재 코드를 다시 반영하고 나니 규칙이 깨지는 경우예요. 업데이트한 검증이 통과하면, 새 코드를 일부러 한 번 더 망가뜨려 검증이 여전히 잡아내는지 확인해요. 규칙 자체는 약속이 의도적으로 바뀌었다는 근거(문서 주석, 테스트, 변경 이력, 커밋 메시지 등)가 있을 때만 바꾸고, 그 근거를 함께 밝혀요. 검증 업데이트는 제품 버그 수정과 섞지 않고 별도 변경으로 나눠요.

## 작성자가 쓰는 방식

- **2026년 10월 18일**, pstack v0.15.27에 베타로 출시됐어요. [출시 글](https://x.com/poteto/status/2111926622278521253)에서 poteto는 동시성 상태 머신을 검증하는 TLA+ 모델과, Rust의 미정의 동작(undefined behavior)을 확인하는 Kani 두 가지 예시를 들었어요. poteto는 코드를 TLA+로 모델링해 이미 여러 버그를 찾았다고 밝혔지만, 구체적으로 어떤 버그인지는 밝히지 않았어요.
- **“질문이 도구를 고른다”도 직접 테스트해 봤어요**. [스킬을 추가한 PR](https://github.com/cursor/plugins/pull/709)에서 작성자는 처음 보는 오픈소스 프로젝트 여섯 곳(pg-boss, swr, HikariCP, client-go, cJSON, arrayvec)에 적용해 봤어요. cJSON(C)와 arrayvec(Rust)에서는 매번 코드 위에서 직접 도는 검증기인 CBMC와 Kani를 골랐어요. TLA+를 지정해 두었던 초기 초안에서는 둘 다 TLA+를 골랐고요. 다만 작성자는 프로젝트당 한두 번씩만 돌려 표본이 작으니, 참고할 만한 단서 정도로 보라고 덧붙였어요.
- **작성자는 유지보수 스킬에 대해 솔직하게 밝혔어요**. [해당 PR](https://github.com/cursor/plugins/pull/716)에서 poteto는 Go 세마포어의 TLA+ 모델(wakeup이 빠진 버전 포함)과 Python의 cachetools를 대상으로 54번 돌려 봤어요. 결론은 이랬어요. AI 모델이 원래부터 검증을 코드에 잘 맞추기 때문에, 이 스킬을 쓴다고 결과 자체가 더 정확해지지는 않았어요. 대신 이 스킬이 더해 준 건 업데이트 뒤에 코드를 한 번 더 일부러 망가뜨려 검증이 여전히 잡아내는지 확인하는 습관이었어요. 스킬을 썼을 때는 11번 중 11번, 쓰지 않았을 때는 10번 중 5번이었어요.
- **작성자가 쓰는 조합**([10월 21일 글](https://x.com/poteto/status/2112736749281759566)): 먼저 `/statechart`로 AI에게 상태도를 그리게 해 코드를 이해한 다음, 만들어진 TLA+ 검증 스킬로 사용자보다 먼저 버그를 찾아요.

## 지금 시도해 볼 만한 이유

형식 검증은 원래 드물었어요. 모델과 증명을 만드는 데 품이 많이 들고, 할 줄 아는 사람도 적었거든요. AI가 그 비용을 낮추면서 요즘 이야기가 많이 나오고 있어요.

- Martin Kleppmann은 AI가 형식 검증을 주류로 만들 거라고 봐요. 증명을 쓰는 비용이 싸지고, 증명 검증기는 딱 AI가 저지르는 실수를 잡아내거든요([글](https://martin.kleppmann.com/2025/12/08/ai-formal-verification.html), 2025년 12월).
- TLA+를 오래 가르쳐 온 Hillel Wayne은 AI 덕분에 쓸 수 있는 명세의 양이 몇 배로 늘었다고 말해요([2025년 6월](https://buttondown.com/hillelwayne/archive/ai-is-a-gamechanger-for-tla-users)). 동시에 AI가 대충 써 내려간 명세는 명세의 본래 목적을 놓치기 쉽다고 경고해요([2026년 3월](https://buttondown.com/hillelwayne/archive/llms-are-bad-at-vibing-specifications)). 위에서 말한 “실패할 수 있음”과 “코드에 충실함”이 그만큼 중요해요.
- Datadog은 TLA+ 명세, 시뮬레이션 테스트, Kani로 AI가 짠 코드를 검증해요([Closing the verification loop](https://datadoghq.com/blog/ai/harness-first-agents), 2026년 3월).
- AWS는 오래전부터 TLA+와 자체 언어인 P로 분산 서비스 설계를 검증해 왔어요([Systems Correctness Practices at AWS](https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services)).

스킬 전문은 이 사이트에서 바로 볼 수 있어요: [`/create-formal-verification-skill`](/ko/skills/create-formal-verification-skill/), [`/maintain-formal-verification-skill`](/ko/skills/maintain-formal-verification-skill/), [`/statechart`](/ko/skills/statechart/).

## 막혔나요?

<Q q="사용 중인 언어에는 코드 위에서 도는 검증기가 없다고 해요.">
솔직한 답변이에요. 코드가 아마 이렇게 동작할 거라고 손으로 모델을 쓰는 대신, 실제 코드에 수많은 생성 입력을 넣어 테스트해요. 순서와 관련된 질문은 영향을 받지 않아요. TLA+는 코드가 무슨 언어든 상관없거든요.
</Q>
<Q q="검증이 너무 오래 걸려요.">
“몇 분 안에 끝나도록 범위를 줄이고, 줄어든 범위를 넘겨줄 때 함께 적어 주세요.”라고 말해 보세요. 너무 느린 검증은 코드가 바뀔 때마다 안 돌리게 되고, 그러면 없는 것과 마찬가지예요.
</Q>
<Q q="반례가 나왔는데 진짜 버그인지 모델링 실수인지 모르겠어요.">
“반례를 실제 코드에서 한 단계씩 따라가 주세요.”라고 부탁해 보세요. 실제 코드에서는 일어날 수 없는 단계가 있다면 모델이 틀린 거니 모델을 고치면 돼요. 모든 단계가 실제로 일어날 수 있다면 진짜 버그예요. 단계가 따라가기 어렵다면 `/statechart`를 써 보세요.
</Q>
<Q q="검증을 통과시키려고 규칙을 느슨하게 바꾸려 해요.">
안 돼요. “규칙은 그대로 두세요. 현재 코드가 규칙을 깨고 있으니, 반례를 코드 기준 단계로 적어 주세요.”라고 답하세요. 발견한 문제는 그대로 보고돼야 해요. 고칠지, 어떻게 고칠지는 직접 결정하면 돼요.
</Q>
<Q q="통과했어요. 그러면 버그가 없다는 뜻인가요?">
그 모델과 그 범위 안에서만 그래요. 넘겨받을 때 적혀 있던 “다루지 않는 범위” 부분을 꼭 읽고, 코드가 바뀌면 `/maintain-formal-verification-skill`을 돌리세요.
</Q>
