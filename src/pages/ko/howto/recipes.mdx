꺾쇠괄호 부분은 자신의 경로, 명령어, “완료” 기준으로 바꿔 넣으세요. 스킬 이름은 AI가 알아보는 이름이라 그대로 두세요.

## 먼저 파악하기

**어떻게 돌아가는지 먼저 묻고, 왜 깨졌는지 묻기**

<Copy id="r-how-why" code="/how로 이 초기화 과정이 어떻게 돌아가는지 파악한 다음, /why로 최근에 왜 깨졌는지 찾아 주세요." />

각 보고서에 확인한 출처가 함께 적혀 나와요.

**논의가 길어졌나요? 문제를 다시 정리하게 해 보세요**

<Copy id="r-restate" code="/poteto-mode 이 스레드를 읽어 주세요. 근본 문제를 이해한 대로 쉬운 말로 다시 정리해 주세요. 코드는 아직 바꾸지 마세요." />

AI가 잘못 이해했다면 다시 정리한 내용에서 바로 드러나요. 정리가 끝난 뒤에 자신의 추측을 말해 주세요.

**보내기 전에 프롬프트 다듬기**

<Copy id="r-sharpen" code="/sharpen 새 결제 서비스의 온보딩 문서를 작성해 주세요." />

빠뜨린 내용을 채워서 다시 쓴 프롬프트만 돌려줘요. 실제 작업은 하지 않아요.

**만들고 있는 것에 맞는 용어 찾기**

<Copy id="r-reframe" code="/reframe 설정 페이지에서 어떤 필드는 바로 저장되고 어떤 필드는 제출할 때만 저장돼서 사람들이 수정한 내용을 잃어버려요." />

전문가가 쓰는 용어를 각각 실제 프로젝트 링크와 함께 알려 주고, 그 용어로 설명을 다시 써 줘요. 다시 쓴 설명을 그대로 보내거나, 거기에 먼저 `/sharpen`을 돌려 보세요.

**며칠 전에 하던 작업 이어서 하기**

<Copy id="r-recall" code={`/recall 지난주에 <주제>에 대해 작업한 내용을 찾아본 다음, <이슈 링크>를 읽어 주세요.`} />

새 대화는 이전 대화를 기억하지 못해요. 먼저 기록을 읽게 하세요.

**설득해 보라고 하기**

<Copy id="r-teach" code={`/teach <다른 방식> 대신 이 방식으로 만든 이유를 알려 주세요. 무엇을 포기하고 무엇을 택했나요?`} />

요약보다 설득하는 논리에서 빈틈이 훨씬 잘 보여요.

## 버그 수정, 기능 추가, 리팩터링, 느린 원인 잡기

**버그 수정**

<Copy id="r-bug" code={`/poteto-mode <증상>. 먼저 재현한 다음 고치고, 검증해 주세요.`} />

“재현”은 문제를 다시 일으켜 본다는 뜻이에요. 전체 과정은 [버그 수정](/ko/howto/fix-bug/)에서 확인하세요.

**검증 스킬이 있다면 증거로 영상 요청하기**

<Copy id="r-bug-verify" code={`/poteto-mode /verify-<앱-이름>으로 이 문제를 재현해 주세요. main에서 재현되면 고치고, 증거로 영상을 보여 주세요.`} />

문제가 이미 사라졌다면 중간에 멈춰요. 영상이 있으면 코드를 읽지 않고도 확인할 수 있어요.

**테스트를 쉽게 쓸 수 있다면 먼저 쓰기**

<Copy id="r-tdd" code="/poteto-mode 먼저 중복 쓰기 문제를 재현해 주세요. 간단히 테스트할 방법이 있다면 /tdd로 해 주세요. 실패하는 테스트를 먼저 쓰고, 고친 뒤 다시 돌려 주세요." />

테스트를 쓰기 어려울 때는 실제 명령어를 돌려 보는 편이 더 확실해요.

**기존 기능을 망가뜨리지 않고 기능 추가하기**

<Copy id="r-feature" code={`/poteto-mode <새 동작>을 추가해 주세요. <현재 출력>은 바이트 단위로 완전히 같아야 해요. 둘 다 검증해 주세요.`} />

“바이트 단위로 완전히 같아야 한다”는 통과 여부를 가릴 수 있어요. “기존 기능에 영향을 주지 마라”는 그렇지 못해요.

**동작은 그대로 두고 리팩터링하기**

<Copy id="r-refactor" code={`/poteto-mode 동작은 하나도 바꾸지 말고 <이 코드>를 하나의 모듈로 옮겨 주세요. 시작하기 전에 현재 출력을 기록해 두고, 끝난 뒤에도 달라지지 않았다는 걸 증명해 주세요.`} />

“바꾸기 전” 상태를 먼저 기록해 두어야 나중에 비교할 기준이 생겨요.

**숫자를 보고 느린 원인 잡기**

<Copy id="r-perf" code={`/poteto-mode <테스트 데이터>에서 <특정 작업>이 <소요 시간> 걸려요. 성능 트레이스를 기록해서 거기 나타난 원인을 고치고, 전후 수치를 보여 주세요.`} />

출발 숫자가 있어야 “빨라졌다”는 말에 의미가 생겨요.

## 설계 정하고 계획 세우기

**프로토타입 몇 개를 만들어 보고 고르기**

<Copy id="r-proto" code="/poteto-mode 설정 페이지 레이아웃 프로토타입을 몇 개 만들어 주세요. 토글로 전환할 수 있게 넣어 두고, 각각 스크린샷을 보내 주세요." />

말로 된 설명만 보고 고르는 것보다 직접 돌아가는 걸 보고 고르는 편이 훨씬 나아요.

**규모가 큰 설계는 중간 검토 지점 두기**

<Copy id="r-architect" code="/poteto-mode 외부 웹훅에 rate limiting을 추가해야 해요. 먼저 /architect로 설계하고, 확실하지 않은 부분은 프로토타입으로 확인해 주세요. 계속하기 전에 제가 먼저 검토할 수 있게 해 주세요." />

마지막 문장을 넣으면 실제 코드를 쓰기 전에 멈추고 기다려요.

**다른 사람이 쓸 패키지라면 튜토리얼부터 쓰기**

<Copy id="r-tutorial" code="/poteto-mode 이 새 설정 패키지를 어떻게 쓰는지 보여 주는 튜토리얼을 먼저 써 주세요. 그다음 지금 쓰는 것보다 왜 더 나은지 /teach로 설명해 주세요." />

튜토리얼을 먼저 쓰게 하면 사용하는 사람 입장에서 생각하게 돼요.

**다른 의견 들어 보기**

<Copy id="r-arena" code="/arena로 이 논의와 우리 계획에 대한 다른 의견을 받아 주세요." />

다른 모델이 더 나은 방법을 찾았는지, 아니면 지금 계획에 동의하는지 알려 줘요.

**설계가 정해지면 계획 요청하기**

<Copy id="r-plan" code="/poteto-mode 이 설계를 계획으로 정리해 주세요. 검증할 수 있는 작은 PR들로 나누고, 각 PR마다 검증 단계를 적어 주세요." />

계획만 내놓아요. 코드를 쓰기 시작하지는 않아요.

**마이그레이션 계획: 버그까지 그대로 옮기기**

<Copy id="r-migrate" code={`/poteto-mode <기존 라이브러리>에서 <새 방식>으로 옮기는 마이그레이션 계획을 세워 주세요. 검증할 수 있는 작은 PR들로 나눠 주세요. 결과는 버그까지 포함해서 기존과 완전히 똑같아야 해요.`} />

마이그레이션 도중에 버그를 고쳐 버리면 이전 결과와 새 결과를 비교할 수 없어요.

## 배포 전에 확인하기

**커밋 전에 꼼꼼히 뜯어보기**

<Copy id="r-interrogate" code="/interrogate 이 브랜치 전체를 까다롭게 살펴봐 주세요. 아직 아무것도 바꾸지 마세요. 진짜 버그나 회귀 문제가 아니면 사소한 지적은 보고하지 마세요." />

보고서에서 걸러낸 항목들도 한 번 훑어보세요.

**여러 가지를 한꺼번에 확인하기**

<Copy id="r-swarm" code="/swarm packages/ 아래 각 패키지의 check.sh를 돌려 주세요. 패키지마다 작업자를 하나씩 붙이고, 마지막에 보고서 하나로 정리해 주세요." />

요약 하나만 읽으면 돼요.

**테스트가 닿지 않는 경우까지 확인하기**

<Copy id="r-formal" code="/create-formal-verification-skill 재시도 큐용으로 만들어 주세요. 같은 메시지가 두 번 전달되는 일은 절대 없어야 해요." />

이 규칙 하나를 모든 경우에서 검증하고, 나중에 코드가 바뀔 때마다 다시 검증할 수 있어요. 자세한 내용은 <Term k="形式化验证" />에서 확인하세요.

**수치를 공개하기 전에 검증하기**

<Copy id="r-bench" code="/benchmark-checklist PR 설명에 넣기 전에 이 40% 빨라졌다는 수치를 검증해 주세요." />

판정은 더 빠름, 더 느림, 차이 없음, 판단 불가 중 하나로만 나와요.

**같은 실수를 매번 손으로 고치지 않기**

<Copy id="r-correct" code="/correct AI가 스키마에 등록하지 않고 자꾸 새 설정 옵션을 추가해요." />

저장소 자체를 바꿔서, 다음 AI는 같은 실수를 할 수 없게 만들어요.

**PR을 올리고 머지될 때까지 지켜보기**

<Copy id="r-pr" code={`/poteto-mode PR을 올려 주세요. 작은 커밋으로 순서대로 나누고, 설명에 근거를 담아 주세요.`} />

<Copy id="r-babysit" code={`/poteto-mode 이 PR을 지켜보면서 체크가 모두 통과하게 만들어 주세요.`} />

따로 말하지 않으면 알아서 머지하지 않아요.

## 맡겨 두고 돌아오기

**자기 전에**

<Copy id="r-overnight" code={`/poteto-mode 이제 자러 가요. 새 worktree(<기준 브랜치>에서 분기)에서 <목표>를 해 주세요.
완료 기준: <통과 여부가 명확한 확인 기준>.
결정 로그를 남겨 주세요. 커밋하기 전에 물어보지 않아도 돼요.
/loop until done. 몇 시간 지나도 정말 막히면 멈추고 이유를 적어 두세요.`} />

“완료 기준”을 적어 두면 매 회차마다 확인할 기준이 생겨요. 자세한 내용은 [알아서 돌아가게 두기](/ko/guide/7-overnight/)에서 확인하세요.

**돌아와서 뭘 했는지 보기**

<Copy id="r-smyw" code="/show-me-your-work 간밤에 무엇을 했는지 차근차근 설명해 주세요." />

`Attention`(확인이 필요한 부분) 섹션부터 먼저 읽으세요. <Term k="决策日志" />의 모든 줄에는 이유와 근거가 적혀 있어요.

**이 대화에서 바뀐 내용만 알고 싶을 때**

<Copy id="r-ketchup" code="/ketchup" />

무엇이 바뀌었는지, 어떤 결정을 기다리고 있는지 정리해 줘요. 살펴보기만 하고 아무것도 바꾸지 않아요.

**방법만 물어보고 싶을 때**

답변과 함께 프롬프트를 하나 줘요. 직접 보내지 않으면 아무것도 실행되지 않아요.

**답변이 이해되지 않을 때**

<Copy id="r-bro" code="/bro" />

방금 한 답변을 쉬운 말로 다시 설명해 줘요.

**배운 내용 적어 두기**

<Copy id="r-reflect" code="/reflect 이번 작업은 너무 느렸어요. 같은 일이 반복되지 않게 배운 점을 정리해 주세요." />

바꿀 내용만 제안해요. 승인하기 전에는 아무것도 바뀌지 않아요.

AI가 딴길로 샐 때 한 줄로 방향을 바로잡는 방법은 [방향 잡기](/ko/howto/steer/)에서 확인하세요.

## 자주 하는 실수

- **프롬프트에 스킬 순서를 지정하기**. 목표와 요구 사항만 말하세요. 스킬 순서는 AI가 알아서 정해요.
- **완료 기준을 모호하게 적기**. “더 좋게 만들어 주세요”는 확인할 수 없어요. 통과 여부가 갈리는 명령어나 결과를 주세요.
- **원인에 대한 추측부터 말하기**. AI는 짚어 준 곳만 들여다보게 돼요.
- **첫 번째 설계를 그대로 쓰기**. 먼저 프로토타입을 요청하거나 `/architect`를 쓰세요.
- **한 폴더에 AI 여러 개를 몰아넣기**. 서로의 작업을 덮어써 버려요. 시도마다 별도의 worktree(워크트리, 같은 Git 저장소의 별도 작업 폴더)를 주세요.
- **아직 믿을 수 없는데 루프부터 돌리기**. 먼저 <Term k="验证技能" />부터 돌아가게 하세요. 그렇지 않으면 확인되지 않은 결과물만 더 빨리 쌓여요.
- **확인하지 않은 숫자를 그대로 믿기**. 먼저 `/benchmark-checklist`를 돌려 보세요.
- **`/arena`를 `/swarm`처럼 쓰기**. `/arena`는 같은 작업 하나를 여러 번 해요. `/swarm`은 일을 여러 조각으로 나누어 처리해요.
- **리뷰 코멘트를 전부 그대로 받아들이기**. `/interrogate`를 쓰세요. 증명할 수 있는 문제만 남겨 줘요.
- **`auto`를 모델 이름으로 착각하기**. “메인 대화를 따르라”는 뜻이에요. 자세한 내용은 [비용 줄이기](/ko/howto/cost/)에서 확인하세요.
- **빌드 통과를 성공으로 여기기**. 컴파일이 됐다는 건 그저 컴파일이 된다는 뜻일 뿐이에요. 실제 명령어 실행 결과를 요청하세요.
- **`SKILL.md`를 손으로 직접 쓰기**. `/poteto-mode`에게 쓰게 하세요. 확인 절차도 함께 챙겨 줘요.

## 막혔나요?

<Q q="그대로 복사해서 보냈는데 원하는 것과 다르게 움직여요.">
<mark>“완료”의 기준이 분명하지 않았을 가능성이 높아요</mark>. “이 명령어가 0을 반환한다”처럼 통과 여부가 명확한 확인 기준을 하나 넣어 보세요. 그래도 애매하다면 보내기 전에 `/sharpen`으로 프롬프트를 먼저 다듬어 보세요.
</Q>
<Q q="영어가 아닌 다른 언어로 프롬프트를 써도 되나요?">
