## 먼저 이걸 복사하세요

<Copy id="ref-min" title="가장 짧은 버전" code="/poteto-mode 파싱 코드를 모듈 하나로 옮겨 주세요. 동작 변경 없음. 현재 출력을 먼저 기록하고, 끝난 뒤 그대로라는 걸 증명해 주세요." />

리팩터링이란 <mark><strong>코드 구조는 바뀌지만 동작은 전혀 바뀌지 않는 거예요.</strong></mark>

- **동작 변경 없음**: 사용자에게 보이는 건 아무것도 바뀌지 않아요. AI가 이 작업을 리팩터링으로 다뤄요. 새 기능도, 버그 수정도 하지 않아요.
- **현재 출력을 먼저 기록**: 비교할 대상이 있도록 “변경 전” 결과를 저장해요. “타입 체크 통과”는 인정되지 않아요. 코드가 컴파일된다는 걸 보여 줄 뿐이에요.

## Astro 정적 사이트 예제

페이지 열두 개쯤에 각자 날짜 포맷 코드가 있고, 조금씩 다 달라요. 유틸리티 함수 하나로 모으고 싶어요.

<Copy id="ref-astro" title="Astro 정적 사이트 예제" code={`/poteto-mode 모든 페이지의 날짜 포맷 코드를 유틸리티 함수 하나로 모아 주세요. 동작 변경 없음.
시작하기 전에: npm run build를 돌리고 dist 폴더 전체를 비교 기준으로 복사해 두세요.
끝나면 다시 빌드해서 기준 결과물과 diff를 비교해 주세요. 모든 HTML 파일의 diff가 비어 있어야 해요.
예전 코드는 전부 삭제해 주세요. 호환성을 위해 예전 함수를 남겨 두지 마세요.
diff 명령어와 그 출력을 보여 주세요.`} />

- **dist의 diff가 비어 있음**: 비어 있으면 달라진 게 없다는 뜻이에요. 한 줄이라도 나오면 뭔가가 바뀐 거예요. 모든 줄을 다 읽을 필요는 없어요. 이 출력 하나면 충분해요.
- **예전 함수를 남기지 않음**: 호출하는 곳을 전부 옮기고, 예전 코드도 이번 작업에서 같이 지워요.

diff가 비어 있지 않다면, 차이가 난 곳마다 AI에게 이유를 설명해 달라고 하세요. 원래부터 날짜 포맷이 달랐던 페이지 때문에 생긴 차이일 수도 있어요.

## 보내고 나서 볼 곳

**처음: 현재 동작을 어떻게 기록했는지**. 테스트, 출력 스냅샷, 또는 비교 스크립트예요.

**중간: 추가하기 전에 먼저 지우기**. 안 쓰는 코드를 먼저 지운 뒤 새 구조를 추가해요.

**끝: 비교 결과**. 답변에 어떤 구조를 바꿨는지, 무엇을 비교했는지, 결과가 어땠는지, 어떤 변경을 되돌렸는지가 나와요. 코드가 더 읽기 쉬워지지 않았다면 변경을 되돌려요.

## 중간에 버그를 발견했을 때

코드를 정리하다 보면 “원래부터 잘못돼 있었네” 싶은 곳이 자주 나와요. 작업을 둘로 나누세요.

1. **리팩터링을 끝내고 커밋해요**. 원래 있던 버그는 그대로 두세요.
2. **버그는 새 작업으로 고쳐요**. [버그 수정](/ko/howto/fix-bug/)을 참고하세요.

그래야 리팩터링 결과를 비교 기준과 깔끔하게 비교할 수 있어요. 리팩터링 도중에 버그까지 고치면, 고친 건지 망가뜨린 건지 구분할 수 없어요.

<Callout type="warn" title="사실 동작을 바꾸고 싶은 건가요?">
그럼 리팩터링이 아니에요. 그렇다고 말하고 기능 추가로 다루세요. <a href="/ko/howto/add-feature/">기능 추가</a>를 참고하세요. 여러 모듈에 걸친 큰 변경이라면 AI가 <code>/figure-it-out</code>으로 넘겨 전체 계획을 먼저 세워요.
</Callout>
