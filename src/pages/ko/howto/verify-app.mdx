AI가 코드를 바꾸고 나면 보통 가장 오래 걸리는 단계는 확인이에요. AI가 “완료”라고 하면 결국 직접 앱을 켜서 하나하나 눌러 봐야 하니까요. 작성자는 공식 가이드에서 가이드에 담긴 모든 내용 가운데 프로젝트용 <Term k="验证技能" />이 가장 큰 효과를 낸다고 말해요.

이유는 간단해요. <mark><strong>자기 작업을 직접 확인할 수 있는 AI는 확인을 통과할 때까지 계속 이어 가지만, 그렇지 못한 AI는 매번 결과를 그대로 넘겨 버려요.</strong></mark> 확인이 사람을 기다리지 않으면 더는 내가 병목이 되지 않아요. 이게 없으면 AI를 더 많이 돌려도 아무도 확인하지 않은 결과물만 쌓일 뿐이에요.

## 먼저 이것부터 복사하세요

프로젝트 폴더에서 AI를 열고 이렇게 보내세요.

<Copy id="cvs" code="/create-verification-skill" />

설치할 때 실행한 `/setup-pstack`도 마지막에 이 작업을 한 번 제안해요. 거기서 하겠다고 답하면 바로 이 명령이 돌아가요.

AI는 대부분 코드를 직접 읽어 다섯 가지를 파악하고, 코드만으로 알 수 없는 것만 물어봐요.

- **사용자가 접하는 대상**: 웹 페이지, 명령줄, 데스크톱 앱, API, 모바일 앱. 여러 개라면 주된 것을 골라요.
- **실행 방법**: 프로젝트 자체 명령어(`package.json`의 스크립트, `Makefile`, README)가 우선이고, 여기에 포트, 환경 변수, 테스트 데이터, 로그인까지 파악해요.
- **조작 방법**: 프로젝트에 이미 있는 것(Playwright나 Cypress 스크립트, 디버그 포트)부터 써요. 그다음에야 범용 방법을 봐요. 웹과 Electron은 브라우저 자동화, 명령줄 도구는 가상 터미널, API는 일반 요청을 써요.
- **남길 수 있는 근거**: 스크린샷, 터미널 출력 기록, API 응답, 로그, 종료 코드, 데이터베이스 행.
- **두 개를 나란히 띄울 수 있는지**: 포트 분리, 데이터 폴더 분리. 분리할 수 없다면 스킬에 그렇게 적어 둬요. 지금 쓰고 있는 쪽을 건드리는 것보다 테스트하지 않는 편이 나아요.

프로젝트가 현재 상태에서 바로 뜨지 않으면, 먼저 그 문제부터 고치거나 정확히 어디서 막혔는지 알려 줘요. 돌아가지 않는 프로젝트에 맞춰 적은 절차는 잘못된 방법만 가르치게 되거든요.

## 만들어지는 결과물

프로젝트 안에 새 폴더가 하나 생겨요. Claude Code에서는 `.claude/skills/`, Cursor에서는 `.cursor/skills/` 아래에 놓여요.

<Copy id="tree" title="생성되는 파일 구조(예시)" code={`verify-<app>/
├── SKILL.md          실행, 진단, 조작, 근거, 정리와 스크립트 실행 방법
└── features/         기능 지도: 기능 하나당 파일 하나
    ├── README.md     기능 지도 목차와 모든 기능의 공통 규칙
    ├── create-note.md
    └── search.md`} />

<Fig id="h-verify" />

`SKILL.md`는 사람이 아니라 다음에 들어올 AI를 위해 쓰인 문서예요. 이 앱을 처음 보는 AI도 작업 도중에 열어 보고 그대로 따라 할 수 있어야 하거든요. 모든 섹션에는 “여기를 채우세요” 같은 빈칸 없이, 프로젝트의 실제 명령어와 버튼 이름이 그대로 들어가요.

| 섹션 | 담기는 내용 |
| --- | --- |
| 실행(Launch) | 어떤 명령어로 앱을 켜고, 무엇을 보고 준비가 끝났다고 판단하는지 적어요. 빈 데이터에서 시작해 마이그레이션을 돌리고 테스트 데이터를 불러오며, “준비 완료”는 실제로 쓸 수 있는 상태를 뜻해요. |
| 진단(Doctor) | 읽기 전용 점검 한 번으로 프로세스가 떠 있는지, 버전이 맞는지, 자기 포트를 쓰고 있는지, 로그인이 아직 유효한지 확인해요. 뭔가 이상해 보이면 가장 먼저 돌려요. |
| 조작(Drive) | 어떤 도구, 어떤 버튼, 어떤 명령어를 쓰는지 적어요. 버튼은 화면 좌표가 아니라 이름이나 라벨처럼 안정적인 식별자로 찾아요. |
| 근거(Evidence) | 무엇을 남길지, 어디에 저장할지, 어떤 것만 근거로 인정하는지 적어요(다음 섹션 참고). |
| 정리(Cleanup) | 이번 실행에서 띄운 것만 끄고, 프로세스 이름으로 종료하지 않아요. 근거는 정해진 위치에 그대로 남겨 둬요. |
| 보조 스크립트(Helpers) | 함께 들어 있는 스크립트는 그대로 바로 실행할 수 있고, 사용법도 스킬 안에 적어 둬요. |

`features/`는 기능 지도예요. 주요 기능 3~5개로 시작해 기능 하나당 파일 하나씩 만들고, 모든 파일은 같은 네 부분으로 이루어져요.

- **세부 기능**: 예를 들어 “메모 만들기”라면 버튼으로 열기, 저장하기, 취소하기, 명령줄에서 만들기 등으로 나눠요.
- **사용자가 진입하는 경로**: 모든 진입점을 빠짐없이 적어요. 버튼, 단축키, 명령어가 모두 포함돼요.
- **조작 방법**: 각 단계를 “무엇을 할지 → 어떤 명령어를 쓸지 → 어떻게 보여야 하는지” 형식으로 적어요.
- **주의할 점(Gotchas)**: 실행 시간을 허비하게 하거나 착각하기 쉬운 함정이에요. 예를 들면 “‘저장됨’ 메시지만으로는 부족해요. 목록에서 메모를 다시 열어 보세요” 같은 내용이에요.

테스트 데이터에 어떤 기능이 필요로 하는 항목이 빠져 있으면, 그 경로가 실패했다고 보고하고 주의할 점(Gotchas)에 이유를 기록해요. 통과시키려고 절차를 슬쩍 쉽게 바꾸지는 않아요. <u>기능 지도에 진입점이 여러 개 적혀 있으면 전부 다 실행해 봐요. 편한 경로 하나만 테스트하는 건 인정하지 않아요.</u>

## 넘겨주기 전에 한 번 직접 돌려 봐요

스킬을 만들고 나면 AI가 자기가 만든 스킬을 처음부터 끝까지 따라 해 봐요. 앱을 실행하고, 진단을 돌리고, 기능 지도에 있는 기능 하나를 조작해 근거를 남긴 뒤, 정리를 마치고도 근거가 그대로 남아 있는지 확인해요. 중간에 실패하는 단계가 나오면 고치고, 시도가 실패할 때마다 자기가 띄운 것들도 꼭 함께 종료해요.

<Callout type="warn" title="시험 실행이 실패했다면 결과물을 쓰지 마세요">
한 번도 돌려 보지 않은 검증 스킬은 초안일 뿐이에요. 만약 대체 환경(예를 들어 새 서버 대신 컨테이너)에서 시험했다면, 대체 환경에서만 돌린 단계를 따로 적어 둬요. 그 단계들은 실제 대상 환경에서 돌려 보기 전까지는 미검증 상태로 남아요.
</Callout>

검증 스킬이 제대로 돌아가기 시작하면 여러 AI가 동시에 테스트할 수도 있어요. `/swarm`이 기능 지도 항목별로 일을 나누고, 각 AI가 기능 몇 개씩 맡아 돌린 뒤 결과를 한데 모아요. 머지 전에 모든 기능을 한 번에 점검하거나, 속도 개선 효과를 의미 있는 표본 수만큼 반복 측정할 때 쓰면 좋아요.

## 근거로 인정되는 기준

만들어진 스킬에는 이런 기준이 분명하게 적혀 있어요. AI가 넘겨준 근거를 살펴볼 때도 이 기준으로 확인하세요.

- **실제 사용자가 거치는 경로**: 실제 버튼과 실제 명령어를 써야 해요. 내부 함수 호출이나 테스트 전용 뒷문은 안 돼요.
- **조작과 결과 둘 다**: 마지막 화면만 찍어서는 안 돼요. 무엇을 했고 무엇이 바뀌었는지 함께 보여야 해요.
- **부수 효과**: 화면에 보이는 것뿐 아니라 기록된 파일, 새로 생긴 데이터베이스 행, 전송된 메시지까지 같이 확인해요.
- **가능한 한 실제 환경 그대로**: 결제처럼 실제 운영 환경에서도 외부 시스템을 격리해 둔 부분에만 mock을 써요.
- **dry run도 직접 확인**: dry run이라고 해 놓고 실제로는 인터넷에 연결하거나 브라우저를 여는 경우도 있어요. 이름만 믿지 말고 실제로 무엇을 건너뛰었는지 확인하세요.

## 프로젝트 인프라로 다루세요

- **커밋해 두세요**. 그래야 팀원 모두와 모든 AI가 같은 방식으로 앱을 조작하게 돼요.
- **작은 명령줄 도구를 만들어 주세요**. AI가 매번 일회용 클릭 스크립트를 짜고 있다면, 스킬이 호출할 작은 제어 도구를 하나 만들게 하세요. 토큰도 아끼고 매번 같은 방식으로 반복 실행할 수 있어요. 좋은 제어 도구에는 몇 가지 공통점이 있어요. 각각 실질적인 일을 하는 소수의 명령어, 파괴적인 작업에 붙는 `--dry-run`, 단계별로 펼쳐지는 하위 명령어, 해결 방법을 알려 주는 오류 메시지, 자세한 `--help`, 그리고 JSON처럼 기계가 읽기 쉬운 출력이에요.
- **명령어 한 번으로 환경을 띄우세요**: 고정된 테스트 데이터, 테스트 계정, 매번 똑같은 결과가 나오게 맞추세요.

## 앱이 바뀌었을 때: /maintain-verification-skill

앱이 바뀌는 순간부터 기능 지도는 낡기 시작해요. 공식 가이드에서는 적어도 하루에 한 번 돌리기를 권해요. 누군가 일일이 기억할 필요 없이 예약 자동화로 돌려 두면 가장 좋아요.

<Copy id="mvs" code="/maintain-verification-skill" />

점검은 이렇게 돌아가요.

1. 기능 지도의 목차를 정리해요. 빠졌거나, 불필요하거나, 중복되거나, 이미 사라진 항목을 골라내요.
2. 기능 하나당 읽기 전용 AI 하나가 소스코드를 읽고, 지금 기능이 어떻게 동작하는지 설명한 뒤 지도가 낡았을 만한 곳을 짚어 내요.
3. 그런 다음 AI 하나가 실제 앱을 띄워 모든 기능을 직접 조작해 봐요. 코드상 문제없어 보여도 실제로 돌려 확인해요.
4. 찾은 결과를 분류해요. 지도가 틀렸으면 지도를 고쳐요. 기능은 되는데 도구가 조작하지 못하면 도구를 고쳐요. 앱 자체가 정말 고장 났으면 바로 보고해요.

결과는 세 가지로 나와요. **clean**(전체 커버, 바꿀 것 없음), **changed**(검증된 수정 사항을 담은 <Term k="PR" /> 하나), **blocked**(무엇에 막혔는지 알려 줌). <mark>검증 스킬 자체 폴더만 고칠 뿐, 제품 코드는 절대 건드리지 않아요.</mark> 원래 되던 기능이 실제로 깨졌다면 문서를 고쳐 감추는 대신 그대로 보고해요.

## 작성자는 이렇게 써요

pstack의 작성자 poteto는 2026년 8월에 pstack을 실제로 쓰는 법에 관한 긴 글을 썼어요([The Complete Guide to pstack, part 1](https://x.com/poteto/status/2094457600259842065)). 그 글에서 가장 큰 비중을 차지하는 주제가 바로 검증이에요.

- 작성자는 검증을 에이전트와 일하는 토대라고 부르며, 그냥 또 하나의 스킬이 아니라 핵심 인프라로 다루라고 말해요.
- `/create-verification-skill`은 작성자가 업무에서 쓰는 검증 스킬들을 “스킬을 만드는 스킬”로 압축한 거예요. 지금 만드는 앱에도 똑같은 걸 만들도록 AI에게 가르쳐 줘요.
- 작성자는 기능 지도를 “실체화된 기억(materialized memory)”이라고 불러요. 파일로 적어 둔 기억이라 토큰이 적게 들고, 프로젝트의 모든 사람과 모든 AI가 함께 읽을 수 있어요.
- 새 기능을 만들 때는 AI가 검증 스킬로 직접 확인한 뒤 영상과 스크린샷을 보내게 해요. 성능 작업에서는 AI가 어디서 시간이 걸리는지 측정하고 핵심만 고친 다음, `/swarm`으로 여러 AI를 한꺼번에 보내 정말 빨라졌는지 확인해요.
- 작성자는 Slack에 사용자가 제보한 버그를 재현하는 봇처럼 예약 자동화 안에서도 검증을 돌려요.
- 작성자는 유지보수 점검을 적어도 하루에 한 번 돌리기를 권해요. AI들이 작업하면서 검증 스킬을 같이 업데이트하긴 하지만, 놓치는 부분을 유지보수 점검이 잡아 주거든요.

## 막혔나요?

<Q q="프로젝트가 실행되지 않는다며 멈췄어요.">
정상이에요. 돌아가지 않는 프로젝트에 맞춰 적은 절차는 잘못된 방법만 가르치게 되거든요. AI가 찾아낸 원인(빠진 환경 변수, 부족한 테스트 데이터, 이미 사용 중인 포트)을 직접 고치거나 AI에게 고쳐 달라고 한 뒤 `/create-verification-skill`을 다시 실행하세요.
</Q>
<Q q="로그인이나 유료 계정이 필요한 기능이라 AI가 들어가지 못해요.">
AI는 해당 기능을 도달 불가로 표시하고, 부족한 사전 조건과 시도했던 경로를 기록해요. 프로젝트의 시드 파일에 테스트 계정을 준비하거나 필요한 상태를 테스트 데이터에 추가해 두세요. 대화창에 실제 비밀번호를 붙여 넣지는 마세요.
</Q>
<Q q="화면 좌표로 버튼을 눌러서 창 크기가 바뀌면 깨져요.">
“좌표나 탭 순서가 아니라 버튼 이름이나 data 속성으로 찾아 주세요”라고 답하세요. 생성기 자체에 원래 안정적인 식별자를 쓰라는 규칙이 있으니 바로 고쳐 달라고 하면 돼요.
</Q>
<Q q="UI가 없는 명령줄 도구 프로젝트예요.">
똑같이 쓸 수 있어요. 실행할 때마다 새 가상 터미널 세션(예를 들어 tmux)을 열어 명령어를 입력하고 출력과 종료 코드를 기록해요. 계속 띄워 둘 서버가 없으니 “실행”은 그저 먼저 빌드하거나 의존성을 설치하는 단계가 돼요.
</Q>
<Q q="AI 두 개가 동시에 검증하다가 서로 부딪쳐요.">
스킬의 실행(Launch) 섹션에 포트나 데이터 폴더를 어떻게 분리할지 적혀 있는지 확인하세요. 없다면 추가해 달라고 하세요. 정말로 분리할 수 없는 구조라면 스킬에 “한 번에 하나씩만 실행”이라고 적어 둬야 해요.
</Q>
<Q q="재시도 두 개가 겹치는 것처럼 일반 테스트로는 잡기 어려운 문제도 찾을 수 있나요?">
검증 스킬은 실제로 조작해 본 경로만 증명해요. 동시성이나 재시도처럼 가능한 모든 실행 순서가 중요한 문제에는 <a href="/ko/howto/formal-verify/">형식 검증</a>을 쓰세요.
</Q>
