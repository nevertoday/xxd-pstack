## 잘 모르겠다면 /poteto-mode를 쓰세요

<mark>잘 모르겠다면 답은 거의 항상 `/poteto-mode`예요</mark>. 목표와 “완료” 기준을 말해 주세요. 그러면 알아서 진행 방식(<Term k="剧本" />)을 고르고, 필요할 때 `/how`나 `/architect` 같은 스킬도 스스로 불러요.

`/poteto-mode`가 해 주는 것보다 **더 많이, 또는 덜** 원할 때만 스킬 이름을 직접 적으세요. 예를 들어 코드는 건드리지 않고 이해만 하고 싶다면 `/how`를 쓰세요.

`/setup-pstack`을 제외하면 모든 스킬은 직접 입력해야만 실행돼요.

## 이런 일을 하고 싶을 때 → 이걸 쓰세요

- **코드 이해하기**: 지금 어떻게 돌아가는지 `/how`; 왜 이렇게 만들었는지 `/why`; 자세히 설명 듣기 `/teach`
- **시작 전에 뜻 맞추기**: 제대로 이해했는지 확인 `/in-your-own-words`; 프롬프트를 더 정확하게 다듬기 `/sharpen`; 만들고 있는 것을 뭐라고 불러야 할지 모를 때 `/reframe`
- **하던 일 이어서 하기**: 다른 대화까지 찾아보기 `/recall`; 이번 대화에서 바뀐 것만 보기 `/ketchup`
- **설계 정하기**: 구조부터 잡기 `/architect`; 한 작업을 여러 방식으로 해 보기 `/arena`; 여러 가지를 따로 확인하기 `/swarm`
- **확인하기**: 여러 모델이 꼼꼼히 따져 보기 `/interrogate`; 그 밖에 깨질 곳은 없는지 `/blast-radius`; 실패하는 테스트부터 쓰기 `/tdd`; 성능 수치 확인 `/benchmark-checklist`; AI가 직접 앱을 조작해 보게 하기 `/create-verification-skill`
- **글쓰기**: AI 티 빼기 `/unslop`; 문서와 PR 설명 쓰기 `/technical-writing`; 쉬운 말로 풀어 쓰기 `/bro`
- **큰 작업과 긴 실행**: 아주 큰 작업 `/figure-it-out`; 결정 기록 남기기 `/show-me-your-work`; 반복되는 실수 막기 `/correct`
- **설정**: 모델 고르고 예산 정하기 `/setup-pstack`; 나만의 모드 만들기 `/automate-me`

각 스킬의 자세한 설명과 예시 프롬프트는 [스킬 한눈에 보기](/ko/skills/)를 참고하세요.

## 그래도 모르겠다면 /poteto-help에 물어보세요

<Cmd c="/poteto-help 이 브랜치를 리뷰하고 싶어요. 어떤 스킬을 써야 하나요?" />

질문에 답해 주고, 그대로 보낼 수 있는 프롬프트와 출처 링크를 알려 줘요. **작업은 시작하지 않아요**. 프롬프트를 보낼지 말지는 직접 정하세요.

<Callout type="warn" title="작업을 시키면 바로 시작해요">
“pstack으로 이 버그를 고쳐 주세요”처럼 말하면 `/poteto-mode` 규칙에 따라 바로 작업에 들어가요.
</Callout>

## 자주 헷갈리는 스킬 쌍

- **`/arena`와 `/swarm`**: `/arena`는 한 작업을 여러 번 해 보고 가장 나은 결과를 고른 뒤, 나머지에서 좋은 아이디어를 가져와 합쳐요. `/swarm`은 쌓인 작업을 나눠서 따로 처리한 뒤 하나의 보고서로 합쳐요.
- **`/how`, `/why`, `/teach`**: `/how`는 코드가 무슨 일을 하는지 설명하고, `/why`는 왜 그렇게 만들었는지 설명해요. `/teach`는 둘 중 하나나 둘 다 돌린 뒤 자세히 설명해 줘요.
- **`/interrogate`와 `/blast-radius`**: 첫 번째는 바뀐 내용 자체를 검토해요. 두 번째는 바뀐 부분 밖에서 깨질 수 있는 곳을 찾아요.
- **`/recall`과 `/ketchup`**: 첫 번째는 여러 대화에 걸쳐 진행 상황을 찾아요. 두 번째는 이번 대화에서 바뀐 내용만 다뤄요.
- **`/architect`**: 설계가 정해지면 곧바로 작성을 시작해요. 설계를 먼저 보고 싶다면 “설계부터 보여 주고, OK 할 때까지 기다려 주세요”라고 말하세요.

## 작업마다 설계가 얼마나 필요할까요?

대부분의 변경에는 설계가 필요 없어요. 작업 크기에 따라 단계를 올리세요:

- **다 썼는데 확신이 없을 때**: `/interrogate`만 돌리세요.
- **독립적인 선택 하나**(이름 짓기, 형식, 알고리즘): 바로 `/arena`를 쓰세요.
- **변경이 함수 경계를 넘을 때**: `/architect`를 쓰세요.
- **한 번 돌려 보면 답이 나오는 문제**(레이아웃, 타이밍): 따지기보다 프로토타입을 만들어 보세요.
- **의견이 갈리고 바꾸는 비용이 클 때**: 먼저 `/architect`를 쓰고, 배포 전에 `/interrogate`를 돌리세요.
- **여러 PR에 걸칠 때**: 설계가 정해지면 계획을 적으세요.

`/poteto-mode`는 이미 알아서 이 단계를 밟아 올라가요.

## 프롬프트에 스킬 순서를 적지 마세요

<Copy id="ws-bad" title="이렇게 쓰지 마세요" code="/poteto-mode 먼저 /how를 쓰고, 다음으로 /architect, 그다음 /arena, 마지막으로 /interrogate를 써서 내보내기 기능을 추가해 주세요." />

이미 순서가 정해져 있어요. 순서를 다시 지정하면 단계가 꼬이거나 빠지기 쉬워요. 대신 목표와 요구 사항을 적어 주세요:

<Copy id="ws-good" title="이렇게 쓰세요" code="/poteto-mode CSV 내보내기 기능을 추가해 주세요. 기존 JSON 내보내기는 바이트 단위로 완전히 똑같이 유지돼야 해요. 둘 다 검증해 주세요." />

기본 선택 하나를 바꿀 때만 스킬 이름을 적으세요. 예를 들면 “이번에는 선택지 5개로 /arena를 써 주세요” 같은 경우예요.

## 막혔나요?

<Q q="/how를 입력했는데 아무것도 고쳐 주지 않아요.">
맞아요. `/how`는 설명만 해요. 코드는 건드리지 않아요. 이해가 끝나면 `/poteto-mode`로 무엇을 하고 싶은지 말해 주세요.
</Q>
<Q q="하고 싶은 일이 목록에 없어요.">
`/poteto-mode`에 넘겨 주세요. 준비된 방식 중 맞는 게 없으면 `/figure-it-out`으로 작업을 넘겨 그 자리에서 새 방식을 설계해요.
</Q>
<Q q="슬래시 메뉴에 /orchestrate가 있어요. pstack 건가요?">
아니요, 메뉴에 보이는 건 다른 플러그인에서 온 거예요. pstack에서는 며칠씩 걸리는 프로젝트도 `/poteto-mode`에 맡기면 `/figure-it-out`으로 넘겨요.
</Q>
