## 먼저 이걸 복사해 보세요

<Copy id="doc-tw" title="README 쓰기" code="/technical-writing 이 Node CLI의 README를 써 주세요. 먼저 각 섹션이 어떤 문서 유형이어야 하는지 알려 주고, 확인한 뒤에 써 주세요." />

AI가 쓴 README에는 이것저것 다 섞여 있기 쉬워요. 설치 방법, 설계 철학, 옵션 표가 한데 뒤섞이죠. 처음 쓰는 분도, 옵션을 찾는 분도 이리저리 건너뛰며 읽어야 해요.

`/technical-writing`의 첫 번째 규칙: <mark><strong>문서 하나는 역할 하나만 맡아요.</strong></mark> 각 섹션을 네 가지 유형 중 하나로 나눠요.

- **튜토리얼**: 한 번 끝까지 따라 해 보면서, 단계마다 결과를 확인해요.
- **How-to 가이드**: 특정 문제 하나를 해결하는 단계를 담아요.
- **설명**: 왜 이렇게 설계했는지와 트레이드오프를 다뤄요.
- **레퍼런스**: 옵션, 플래그, 오류 코드. 사실만 적어요.

README에 여러 유형이 필요하다면, 부분을 나누고 서로 링크로 연결하세요.

## Node CLI 예시

Markdown 노트를 HTML로 일괄 내보내는 CLI에 GitHub용 README가 필요한 상황이에요.

<Copy id="doc-cli" title="Node CLI 예시" code={`/technical-writing 이 CLI의 README를 써 주세요.
설치와 첫 내보내기는 튜토리얼로 써 주세요. 각 단계마다 독자가 어떤 출력을 보게 되는지 알려 주세요.
모든 옵션은 --help의 실제 출력을 바탕으로 별도 레퍼런스 섹션에 넣어 주세요. 없는 옵션을 지어내지 마세요.
다 쓰고 나면 빈 폴더에서 튜토리얼을 처음부터 따라 해 보고, 모든 명령어가 돌아가는지 확인한 뒤 터미널 출력을 붙여 넣어 주세요.
마지막으로 /unslop 돌려 주세요. 긴 대시(em dash) 금지, “강력한” 금지, “손쉬운” 금지.`} />

- **“빈 폴더에서 튜토리얼을 처음부터 따라 해 보기”**: 가장 쓸모 있는 한 줄이에요. 문체는 의견이 갈릴 수 있어요. 하지만 명령어가 돌아가는지는 다툴 여지가 없어요.
- **“--help의 실제 출력을 바탕으로”**: 레퍼런스 문서는 사실을 적는 곳이고, 사실은 코드에서 나와요.
- **“마지막으로 /unslop 돌려 주세요”**: AI 티를 빼고, 원하지 않는 단어까지 같이 걸러 내요.

## 보내고 나서 볼 곳

**처음 볼 곳: 유형을 어떻게 나눴는지**. 설계 철학이 시작하기 부분에 들어가 있다면 바로잡아 주세요.

**마지막에 볼 곳: 터미널 출력**. 어느 단계가 실패했다면 튜토리얼에 빠진 단계가 있는 거예요.

## 마지막에 AI 티 빼기: /unslop

<Copy id="doc-unslop" code="/unslop README 변경 사항, 긴 대시(em dash) 금지" />

내장 규칙은 영어에서 흔한 AI 말투를 겨냥해요. 남발하는 긴 대시(em dash), 억지로 맞춘 세 가지 나열, 알맹이 없는 마무리 같은 것들이죠. 신경 쓰이는 단어가 있다면 “‘매끄러운’ 금지, ‘역량 강화’ 금지”처럼 규칙에 덧붙이세요.

## 다른 곳에서 불러 쓸 코드: 튜토리얼부터 쓰기

다른 코드가 불러 쓸 패키지나 API라면, 코드를 짜기 전에 문서부터 쓸 수 있어요.

<Copy id="doc-readme-first" title="튜토리얼부터 쓰기" code="/poteto-mode 새 config 패키지를 어떻게 쓰는지 튜토리얼부터 써 주세요. 그다음 /teach 써서 지금 것보다 왜 더 나은지 설명해 주세요." />

튜토리얼을 먼저 쓰면 AI가 사용자 입장에서 생각하게 돼요. 무엇을 먼저 적고 어떤 결과를 보게 될지부터 따져 보죠. 이 튜토리얼은 나중에 코드를 확인하는 기준도 돼요.

## 요청을 제대로 했는지 확신이 없다면: /sharpen

<Copy id="doc-sharpen" code="/sharpen 새 결제 서비스의 온보딩 문서를 써 주세요." />

문서를 쓰지는 않아요. 대신 요청을 더 날카롭게 다시 써 줘요. 예를 들어 전문가라면 무엇을 더 챙길지, 어떤 원본 자료에서 시작할지, 결과가 맞다는 걸 무엇으로 증명할지 같은 것들이에요. 다시 쓴 요청을 읽어 보세요. 괜찮아 보이면 그대로 보내세요.

<Callout type="tip" title="PR 설명도 문서예요">
AI가 <Term k="PR" />을 열 때는 <code>/technical-writing</code>으로 설명을 쓰고 <code>/unslop</code>을 돌려요. 설명은 리뷰어를 위한 1분 요약이에요. 비어 있는 섹션은 지워요.
</Callout>

## 막혔나요?

<Q q="README에 여전히 이것저것 다 섞여 있어요.">
이렇게 답하세요. “technical-writing 방식으로 나눠 주세요. 시작하기에는 튜토리얼만 남기고, 옵션 표는 레퍼런스 섹션으로 옮기고, 설계 의도는 별도 설명 섹션으로 빼 주세요. 섞어 쓰지 마세요.”
</Q>
<Q q="/unslop을 돌렸는데도 여전히 AI 티가 나요.">
거슬리는 단어와 표현을 그대로 적어 명령어 뒤에 덧붙이세요. 예를 들어 “/unslop 이 섹션, 긴 대시 금지, ‘매끄러운’이나 ‘역량 강화’ 금지, 한 문장은 20단어 이내로”처럼요. 규칙이 구체적일수록 더 잘 해내요.
</Q>
<Q q="/sharpen이 문서를 써 주지 않아요.">
요청을 다시 써 주는 역할만 해요. 다시 써 준 요청을 <code>/poteto-mode</code>나 <code>/technical-writing</code>에 보내세요.
</Q>
<Q q="PR 설명이 너무 길어요.">
이렇게 답하세요. “PR 설명은 1분 요약이에요. 섹션당 1~3문장만 쓰세요. 자세한 데이터는 별도 파일에 넣고 링크해 주세요.”
</Q>
