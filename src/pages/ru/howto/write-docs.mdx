## Сначала скопируйте это

<Copy id="doc-tw" title="Написать README" code="/technical-writing Напиши README для этого Node CLI. Сначала скажи, к какому типу документации отнести каждый раздел, и пиши только после моего подтверждения." />

В README от ИИ часто намешано всего понемногу: шаги установки, философия и таблица параметров — всё в одной куче. И новичкам, и тем, кто ищет нужный параметр, приходится прыгать по тексту.

Первое правило `/technical-writing`: <mark><strong>один документ решает одну задачу.</strong></mark> Навык относит каждый раздел к одному из четырёх типов:

- **Туториал**: пройти один раз и видеть результат на каждом шаге.
- **Практическое руководство**: шаги для решения одной конкретной задачи.
- **Объяснение**: почему всё устроено именно так и какие есть компромиссы.
- **Справочник**: параметры, флаги, коды ошибок. Только факты.

Если для README нужны несколько типов, разбейте его на части, которые ссылаются друг на друга.

## Пример с Node CLI

Для CLI, который пакетно экспортирует заметки Markdown в HTML, нужен README для GitHub:

<Copy id="doc-cli" title="Пример с Node CLI" code={`/technical-writing Напиши README для этого CLI.
Опиши установку и первый экспорт в формате туториала: на каждом шаге пиши, какой вывод должен увидеть читатель.
Собери все параметры в отдельный справочный раздел по реальному выводу --help. Не придумывай никаких параметров.
Когда закончишь, пройди туториал с нуля в пустой папке, убедись, что каждая команда работает, и вставь вывод терминала.
В конце прогони текст через /unslop: без длинных тире, без слов «мощный» и «без усилий».`} />

- **«Пройди туториал в пустой папке»**: самая полезная строчка. О стиле можно спорить. О том, работает ли команда, — нет.
- **«По реальному выводу --help»**: справочник фиксирует факты, а факты берутся из кода.
- **«В конце прогони текст через /unslop»**: убирает ИИ-штампы и любые слова, которых вы не хотите видеть.

## Куда смотреть после отправки

**В начале: как ИИ распределил типы.** Если философия попала в раздел быстрого старта, поправьте сразу.

**В конце: вывод терминала.** Если какой-то шаг падает, в туториале не хватает шага.

## В конце уберите ИИ-штампы: /unslop

<Copy id="doc-unslop" code="/unslop изменения в README, без длинных тире" />

Встроенные правила нацелены на типичные ИИ-штампы в английском языке: слишком частые длинные тире, натужные списки из трёх пунктов и пустые концовки. Добавляйте в правила любые слова, которые для вас важны, например: «без „бесшовный“, без „расширяет возможности“».

## Код, который будут вызывать другие: сначала напишите туториал

Для пакета или API, которые будет использовать другой код, документацию можно написать раньше самого кода:

<Copy id="doc-readme-first" title="Сначала написать туториал" code="/poteto-mode сначала напиши туториал о том, как я буду пользоваться новым пакетом конфигурации. Затем через /teach объясни, чем он лучше текущего." />

Если сначала написать туториал, ИИ будет думать как пользователь: что написать в первую очередь и что вы при этом увидите. А ещё туториал станет ориентиром, по которому можно проверять код.

## Не уверены, правильно ли сформулировали запрос: /sharpen

<Copy id="doc-sharpen" code="/sharpen Напиши вводную документацию для нового сервиса биллинга." />

Навык не пишет документацию. Он переписывает ваш запрос так, чтобы тот стал точнее. Например: что ещё сделал бы эксперт, с каких исходных материалов начал бы работу и что докажет правильность результата. Прочитайте переписанный вариант. Если всё выглядит правильно, отправляйте.

<Callout type="tip" title="Описание PR — это тоже документация">
Когда ИИ открывает <Term k="PR" /> (Pull Request — запрос на проверку и слияние изменений), он пишет описание через <code>/technical-writing</code> и прогоняет его через <code>/unslop</code>. Описание — это сводка на одну минуту для ревьюеров. Пустые разделы удаляются.
</Callout>

## Застряли?

<Q q="В README всё ещё намешано всего понемногу.">
Ответьте: «Разбей текст по правилам technical-writing: в разделе быстрого старта оставь только туториал, таблицу параметров перенеси в справочник, а идеи проектирования вынеси в отдельный раздел с объяснением. Не смешивай их».
</Q>
<Q q="После /unslop текст всё равно звучит как написанный ИИ.">
Перечислите конкретные слова и фразы, которые вас раздражают, и допишите их после команды. Например: «/unslop этот раздел, без длинных тире, без „бесшовный“ и „расширяет возможности“, предложения короче 20 слов». Чем конкретнее правила, тем лучше результат.
</Q>
<Q q="/sharpen не написал документацию.">
Навык только переписывает запрос. Отправьте переписанный запрос в <code>/poteto-mode</code> или <code>/technical-writing</code>.
</Q>
<Q q="Описание PR слишком длинное.">
Ответьте: «Описание PR — это сводка на одну минуту. От одного до трёх предложений на раздел. Подробные данные вынеси в отдельный файл и добавь на него ссылку».
</Q>
